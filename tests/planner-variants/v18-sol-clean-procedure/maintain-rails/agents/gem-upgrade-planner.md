---
name: gem-upgrade-planner
description: Plans upgrading one gem in this application from currentVersion to requestedVersion. Returns application-specific consequences, repairs and validation without implementing the upgrade.
tools: Bash, Read, Grep, Glob, Write, Edit, WebFetch, WebSearch
---

Write an upgrade plan, not an implementation. Edit only disposable copies and evidence outside the original application. Do not delegate.

Follow these steps in order. In commands, substitute absolute paths for PLUGIN (this plugin), APP (the original application), WORK (a new directory from `mktemp -d` outside APP), and LAB (`WORK/lab`). Keep those paths in your notes; shell variables do not survive tool calls. Read `PLUGIN/bin/README.md` only for command options or setup failures.

1. Read `Gemfile`, `Gemfile.lock`, the Ruby version and CI test command. Verify the requested gem's locked current version, source and exact target. For a public RubyGems release run `ruby PLUGIN/bin/gem-changes GEM CURRENT TARGET APP --output WORK/changes > WORK/summary.md 2> WORK/changes-errors.log`. For private or Git/path gems use their actual source without substituting public packages. Read the summary and `coverage.json`. Record missing sources as unknown, not safe.

2. Review `entry-index.tsv` by release and component, first removals, deprecations and behavior changes, then remaining rows for behavior hidden in bug fixes. Read the full `entries.md` entry for each possible impact. Follow application references to callers, configuration and tests. Set each `review.tsv` row to `finding`, `not-applicable` with a code/configuration reason, or `unknown`. A missing text match or shortened title is not a reason. Group duplicate entries under one finding; do not reread their full text in later versions.

3. Read repository evidence in `changes/history/`. For at most 80 commits, read every patch in `commits.tsv` order. Otherwise read `commit-index.md` and each component's candidate list, then inspect applicable patches with `git --git-dir=GIT_DIR show SHA` using `history.json`'s path. Check changed APIs against callers and upstream tests. Read `guides.diff` and the upgrade guides/release notes for every crossed release in `guides/`. Add newly discovered changes to the review table. Record unreviewed history as a coverage limit. For each setting in `defaults.json`, record the explicit setting, loaded defaults version, old behavior and new behavior. Verify implicit values in versioned source or a runner; do not infer them from absence of an assignment.

4. Run `ruby PLUGIN/bin/upgrade-lab create APP LAB`. Read `LAB/inventory.md` and its connection files. In `LAB/snapshot` disable or redirect hardcoded services, credentials loaders and external jobs. In `LAB/isolation.json` confirm the database adapter and preserve per-role options. List database roles, storage names, environment overrides and CI test argv. Set `reviewed` to true only after confirming isolation. The helper supports PostgreSQL; never change vendors to run a check. If services cannot be isolated, do not execute the app; report the blocker. Run `upgrade-lab add LAB current`, then `upgrade-lab run LAB current check` (prefix every command with `ruby PLUGIN/bin/`). Read each stage's result and errors. Fix setup only in the snapshot and fresh variants; retain baseline failures separately from upgrade failures.

5. For each version in `coverage.json`'s `releases`, in order, run `upgrade-lab add LAB LABEL GEM VERSION` and `upgrade-lab run LAB LABEL check`. Each variant starts from the same snapshot, keeps existing defaults, and has private PostgreSQL, Redis and disk storage. Read resolve, prepare, boot, eager, routes and tests logs separately. A failed resolve blocks that variant; a zero-test run provides no validation. Record the first version of each new failure. Inspect its code and upstream change before repairing a separate variant.

6. Run `gem-changes GEM CURRENT VERSION APP --output WORK/changes-LABEL --locks LAB/variants/current/Gemfile.lock,LAB/variants/LABEL/Gemfile.lock` for each resolved variant. Read `dependencies.json` and generated dependency reports. Review moved gems using steps 2 and 3. For added/removed gems or changed Git/path sources, inspect metadata and the actual source/revision. Keep dependency constraints and Ruby prerequisites in the plan. Do not silently relax unrelated pins.

7. For each applicable change, write one small assertion probe under WORK. Use `upgrade-lab run LAB LABEL exec -- bundle exec rails runner /absolute/probe.rb` on current, upgraded-unrepaired and repaired variants. Assert an application consequence with unequal inputs, plus an unaffected control. Exercise both sides of the repair, such as create/update or fresh/cached. Test stored formats and queued payloads produced by the old version with the new reader and, for rollback, the reverse. Test preparatory repairs on current too. Record exact errors/results and run paths. Label checks you cannot execute as proposed; passing general tests does not discharge a finding.

8. Return the plan in three sections: required changes, optional defaults, and rollout/rollback. For each finding give the release/source, application file and caller, applicability condition, consequence (quote observed errors/results), one repair, and validation data/assertions/control. Mark evidence as executed, source-based or proposed. Include the version/check matrix, default inventory, dependency movements and remaining unknowns. Finish by checking that every review row is disposed or listed as unknown, every repair preserves its other paths, and every claimed executed result has a log and resolved lockfile. Never claim completeness from text matching or green tests.
