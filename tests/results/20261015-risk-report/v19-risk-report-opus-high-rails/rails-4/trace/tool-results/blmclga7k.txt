# Architecture

## Starting point

Margin Notes is a reading-notebook application. Implemented so far:

- A reader (`User`) signs in with email and password through `has_secure_password`.
  `SessionsController` stores only the user ID in the Rails session.
  `ApplicationController#require_sign_in` protects the application's other
  controllers, but not Rails' Active Storage controllers.
- A reader owns `Notebook`s, and each `Note` belongs to one notebook. A note's
  owner is its notebook's owner, so `User#notes` (through notebooks) is the
  authorized note scope. There is no separate `user_id` on notes.
- `NotesController#index` serves `/notes` and its `/journal` alias. It lists the
  reader's notes newest first with an ID tie-breaker, and supports title search
  and notebook and status filters. `show` renders one note's rich body.
- Pagy 8.6.3 paginates that filtered list after ordering, 10 notes per page by
  default. The search form offers 5, 10, 25, or 50 as the `per_page` URL
  parameter. Larger requested sizes are capped at 50. Next and previous links keep
  the filters and page size. A blank, zero, negative, or nonnumeric page shows the
  first page, and a page past the end shows the last page. The form never sends
  an invalid size. A blank, zero, negative, or nonnumeric `per_page` in a URL is
  not handled, and Pagy raises `Pagy::VariableError`.
- A note's body is Action Text (`has_rich_text :body`), edited with Trix.
  Attachments are Active Storage blobs on the local Disk service. `Note` rejects
  saves that embed a blob over 1 MB. Direct uploads store blobs before this
  validation, without a size limit. Rejected or abandoned uploads remain
  unattached, and nothing purges them. No image processor is installed, so images
  use the original blobs, not variants. A migration converted existing plain-text
  bodies to escaped rich text.
- Action Text sanitizes rich text when it renders. The
  [Action Text initializer](config/initializers/action_text.rb) adds
  `details`/`summary` to the default allowlist for collapsible excerpts. Trix
  does not support those elements. Stored excerpts render as collapsible content,
  but saving them through the editor permanently flattens that structure, even
  when only tags or highlight change.
- Note tags are a JSON array in a text column, entered as a comma-separated
  list (`Note#tag_list`). The highlight color is `color` in the `settings` jsonb
  column, which the form edits as `highlight_color`.
- `NotebooksController#edit`/`update` are notebook settings. The slug is derived
  from the name on creation and is read-only afterward (`attr_readonly`). The
  settings form resubmits it unchanged. The export heading is stored in the
  serialized `preferences` hash. Markdown exports use both.
- A reader imports a CSV into one owned notebook. `ImportPreviewsController`
  reads the upload and renders a preview without saving. The preview page sends
  the CSV text back in a hidden field, and `ImportsController#create` reads and
  validates it again rather than trusting the preview. `Import#apply` saves the
  import and each row's note in one transaction. If any row cannot be saved,
  nothing from the batch remains. The receipt page and its CSV download list
  each imported note's title and DOI. Submitting the same preview twice creates
  two imports.
- `Import` accepts one format: UTF-8 CSV with the header row
  `title,body_html,doi,annotation,reminder_epoch`, at most 100 notes and 100 KB.
  Only the title is required. Previews identify rows by their source line, so a
  quoted multi-line body keeps the line where its row starts. Body HTML takes the
  same Action Text assignment and render-time sanitization as the editor.
- A `Citation` is identified by its DOI, the table's `doi` primary key, and is
  shared by every reader who cites it. A DOI is stored as given apart from
  surrounding whitespace, so case variants are different citations. Rows in one
  import share a new citation. Two simultaneous imports that introduce the same
  new DOI can conflict; the losing request fails with a server error and saves
  nothing. A reader's annotation and optional reminder epoch belong to the note,
  not the citation. Annotations are plain text in both the preview and note page;
  line breaks are preserved on the note page, but markup is displayed literally.
  Applying an import does not schedule its reminders; the reader schedules each
  one from its note.
- A reader can also enter a DOI on the note form (`Note#doi=`), which cites the
  shared citation with that exact, trimmed DOI or creates it.
- A reader requests metadata for the citation on one of their notes with
  `CitationEnrichmentsController#create`, nested under the note. It resolves the
  note through `current_user.notes`, so another reader's note, or a note without
  a DOI, is a 404. `Citation#request_enrichment` marks the citation pending and
  queues `CitationEnrichmentJob`, unless a request is already pending. The job
  calls `Citation#enrich`, which stores the provider's title and source URL and
  marks the citation completed, or records a failure message. Metadata and
  status belong to the shared citation, so every note citing the DOI shows them.
  The note page shows the state; it does not update itself while pending.
- `Citation::Provider` is the HTTP client for the metadata provider. It reads
  its URL and basic-auth credentials from [config/secrets.yml](config/secrets.yml)
  through `Rails.application.secrets`; that file reads them from the environment.
  Faraday retries a GET once on 503. A 401, 403, or 404, or a response without a
  title and an http(s) URL, fails the enrichment at once. A 429 or 5xx, timeout,
  or connection failure raises `Citation::Provider::Unavailable`. The job retries
  that with `retry_on`, three attempts in all at exponentially longer waits, then
  records the failure instead of passing the error to Sidekiq's own retries. A
  persistently unavailable provider therefore receives at most six requests per
  enrichment request. A job that fails for another reason uses Sidekiq's retries
  and leaves the citation pending meanwhile.
- [bin/citation-provider](bin/citation-provider) is a deterministic local stand-in
  for the provider, used for development and demonstrations. No real provider or
  credentials are configured.
- A reader exports an owned notebook as Markdown from its exports page
  (`ExportsController`, nested under the notebook). `Notebook#request_export`
  saves a queued `Export`, then queues the native Sidekiq job `ExportJob` and
  stores its job ID, which the page shows. The export is committed before the
  job is queued so the worker can always load it. If Redis refuses the job, the
  export is removed and the request fails. Each request creates a new export.
- `Export#generate`, run by the worker, marks the export working with the
  notebook's note count, then writes the notes oldest first (creation time, then
  ID). The file starts with the notebook's export heading, or its name when none
  is set. Each note is a second-level heading with its title on one line,
  followed by its body as Action Text plain text. Markdown characters are not
  escaped. Progress is saved after each note. A retried job starts again from
  the first note. There is no failed state: while Sidekiq retries a failing job,
  the export shows as working and the reader can cancel it.
- Cancelling (`ExportCancellationsController`) sets a queued or working export's
  persisted status to cancelled under its row lock. The worker checks that status
  before each note and before completing, then stops and keeps no file. Completed
  and cancelled exports cannot be cancelled.
- The worker uploads the file to Active Storage (`<slug>.md`) before marking the
  export completed, so a completed export always has a file. It can be downloaded
  for 24 hours (`Export::AVAILABLE_FOR`). `ExportDownloadsController` resolves the
  export through the reader's notebook, so another reader's export is a 404, and
  checks `Export#downloadable?` on every request before any conditional response.
  An expired, cancelled, or unfinished export redirects to the exports page. The
  file is sent by the application, never by an Active Storage URL, with an ETag
  and Last-Modified from the stored file and `private, must-revalidate`.
  A failed upload can leave an unattached blob row without a stored file. Nothing
  cleans up those rows, and each failed retry can leave another one.
- The exports page caches each completed export's availability indicator as a
  fragment that expires at the export's deadline. The download action does not
  read that cache. The page does not update itself while an export is queued or
  working. Nothing purges expired files; they remain in storage.
- A notebook's activity page (`ActivityReportsController#show`, nested under the
  notebook and linked from the notebooks list) shows how many of its notes were
  created on each UTC date, newest date first. It is read-only and resolves the
  notebook through `current_user.notebooks`, so another reader's notebook is a
  404. `Notebook#daily_note_counts` groups the notes by `DATE(created_at)` in
  PostgreSQL and reads the rows with a raw `select_rows`, which returns each date
  as ISO 8601 text; the method parses it with `Date.iso8601`. Every status counts,
  and dates without notes are omitted. The report is derived from the notes that
  exist when it is requested, not an activity log: deleting a note lowers its
  date's count, and nothing records past counts.
- Each reader has a time zone (`User#time_zone`, UTC by default), chosen on the
  account settings page (`AccountsController`). Reminder times use it. Digests
  follow UTC days, and other pages still show times in UTC.
- A note's reminder is its `reminder_epoch`, a time in seconds since 1970, set by
  an import or by the reader. `RemindersController#create`, nested under the
  note, reads a date and time the reader entered in their time zone
  (`User#local_time`), or, with none, uses the stored time. `Note#schedule_reminder`
  queues `NoteReminderJob` for that time with `set(wait_until:)` and stores the
  job's ID, under the note's row lock, so a failed enqueue keeps the earlier
  reminder. A local time that does not exist because of a daylight saving change
  moves forward, and an ambiguous one takes its first occurrence. A time in the
  past is sent as soon as a worker runs the job.
- Scheduling again, or postponing (`ReminderPostponementsController`), replaces the
  reminder. Earlier jobs stay in Sidekiq's schedule, but send nothing: when a job
  runs, `Note#send_reminder` takes the row lock and emails the reader only if its
  job ID is still the note's and the reminder has not been sent, then records
  `reminder_sent_at`. The note page shows whether a reminder is imported but not
  scheduled, scheduled, or sent. A job that fails after the email is written can
  send it again when Sidekiq retries it.
- Postponing moves the reminder 24 elapsed hours later. The note page previews
  that time as `reminder_at.to_time + 86_400`, which keeps the reminder's UTC
  offset. Across a daylight saving change the preview shows the right instant,
  but at a different offset and wall-clock time from the postponed reminder.
- A reader requests a digest of their ready notes from the notes page
  (`DigestsController`). `User#request_digest` reserves the reader's ID in a
  Redis set for the request's UTC date
  (`digest_requests:YYYY-MM-DD`, kept for two days) and queues `DigestJob` with
  the reader, the request time in the reader's zone, and the share of their notes
  that are ready, as a `BigDecimal`. A reader whose ID is already in the day's set
  is told the digest was already requested. If the job cannot be queued, the
  reservation is removed and the error raised, so the request fails and can be
  repeated. The reservation prevents repeated requests, not repeated emails:
  Sidekiq can run a job more than once. Each request logs redis-rb's deprecation
  warning for a single-member `sadd`, and Sidekiq warns that the job's arguments
  are not native JSON types, because of the `BigDecimal`.
- Sidekiq stores the job's arguments as JSON. Active Job 7.0 sends the request
  time with its UTC offset but deserializes it in the worker's zone, UTC, and the
  completion arrives as a decimal string such as `"0.6667"`. `DigestMailer` lists
  the reader's ready notes last updated during that UTC day, and dates the digest
  by it. The content day matches the reservation's day, even near local midnight.
  A digest is a snapshot when its job runs; notes updated afterward are not sent
  in a second digest for that UTC day.
- The mailers write plain-text email. Development writes each recipient's email
  to `tmp/mails` (Action Mailer's file delivery); tests use the `:test` delivery
  method. Production has no delivery method or link host configured.
- Active Storage serves blobs through signed URLs from its own controllers. Those
  URLs are not checked against the signed-in reader. The embedded blob redirect
  URLs do not expire, although the Disk-service URLs they redirect to do.
  The direct-upload controller checks CSRF, not sign-in; the public sign-in page
  supplies a CSRF token to anonymous clients. This sample has no private-file
  access policy or upload-abuse protection for a public deployment.

These conventions guide further features without prescribing a schema in advance.

The initial runtime is Ruby 3.3.6 and Rails 7.0.8.7 with Rails 7.0 defaults.
[Gemfile](Gemfile), [Gemfile.lock](Gemfile.lock), [.ruby-version](.ruby-version), and
[config/application.rb](config/application.rb) are the executable sources of truth.

- PostgreSQL is the application database. Use Active Record and migrations for
  application-owned records, constraints, indexes, and transactions.
- ERB renders HTML. The generated app includes Sprockets, importmap, Turbo, and
  Stimulus. Jbuilder is available for requested JSON representations, but an HTML
  feature does not automatically need a JSON API.
- Rails includes the mailer, job, storage, and cable frameworks. Their presence
  does not mean broadcasts are implemented features. Email is sent only for
  reminders and digests, and is not delivered outside development's files. File
  uploads exist only as rich-text attachments.
- Active Job uses Sidekiq 6.5 as its adapter outside tests, so queued jobs are
  kept in Redis (`REDIS_URL`, by default `redis://localhost:6379`) and run in a
  separate `bundle exec sidekiq` process. Tests use Active Job's test adapter.
  `ExportJob` is a native Sidekiq job rather than an Active Job, so its job ID can
  be shown. Sidekiq stores its arguments as JSON, and it uses Sidekiq's default
  retries.
- Action Text 7.0.8.7 bundles Trix 1.3.4. That version cannot load saved HTML
  that has attributes, such as links or attachments, so the layout loads Trix
  1.3.5 from `vendor/javascript` as a classic script. Trix 1.x is not an ES
  module, so it is not in the import map. `@rails/actiontext` is.
  The vendored build comes from the [Trix 1.3.5 release](https://github.com/basecamp/trix/tree/1.3.5)
  and includes its [MIT license](vendor/javascript/trix-1.3.5.LICENSE).
- Orb setup starts PostgreSQL and Redis. Redis holds Sidekiq's queues and the
  digest reservations; it is not an application cache. The generated production
  cable configuration names Redis. That configuration is not a verified deployment.

## Prefer Rails objects with clear responsibilities

Use the framework's ordinary directories and interfaces:

| Responsibility | Home |
| --- | --- |
| HTTP verbs, paths, and resource nesting | `config/routes.rb` |
| Parameter selection, authorized lookup, response negotiation | `app/controllers/` |
| Persistent state and domain operations | `app/models/` |
| A cohesive capability of one model | A namespace beneath `app/models/` |
| Behavior genuinely shared across models | `app/models/concerns/` |
| HTML, Turbo stream, and JSON representations | `app/views/` |
| Presentation helpers | `app/helpers/` |
| Browser interaction around rendered HTML | `app/javascript/controllers/` |
| Background execution and retry boundary | `app/jobs/` |
| Mail composition | `app/mailers/` and its views |

A controller can call Active Record directly for a simple save. A multi-step
domain transition belongs behind a meaningful model method, not a sequence of
unrelated updates in the controller. Use a plain Ruby object or Active Model when
an operation needs its own object but no database table. Do not introduce a
mandatory service, repository, presenter, or command layer between every pair of
Rails objects.

Fizzy models closing a card as a singular closure resource. Its controller calls
`Card#close`, and `Card::Closeable` owns the association, predicates, and transaction.
The [closure sources](docs/references/fizzy.md#card-closure) illustrate a resource
boundary and a domain method, not a requirement to add cards to Margin Notes.

## Model resources, not collections of verbs

Use the conventional REST actions, including `new` and `edit` for HTML forms.
When a new operation does not fit an existing resource, look for the resource it
creates, updates, or removes before adding a custom action. Keep nesting shallow
enough that the parent conveys ownership rather than reproducing the whole schema.

Use route helpers in views and responses. Controllers choose the representation.
Models do not construct controller responses or reach into request parameters.

## Keep data ownership and effects explicit

- PostgreSQL owns durable application facts. Derive a value from those facts
  unless storing it solves a demonstrated query, history, or concurrency need.
- Put invariants used outside HTTP in the domain model. Add database constraints
  when integrity must also hold across concurrent requests and non-model writes.
- Keep related database writes in one transaction. Do not assume it can undo a
  remote request, an email, or a job already sent to another system.
- Jobs should delegate to domain behavior and carry the identifiers or context
  they need. Decide retries, duplicate delivery, and transaction timing when a
  real background feature is introduced, rather than adding a queue preemptively.
- Keep network clients at visible boundaries. Preserve failure information and
  distinguish a legitimate empty response from a failed operation.

Fizzy's [comment example](docs/references/fizzy.md#comments) enforces comment
eligibility in both the model and the controller. Callers outside HTTP must obey
the same rule.

## Authorization is not presentation

Define ownership and the authorized lookup scope together. Resolve records
through the signed-in reader: `current_user.notebooks` and `current_user.notes`.
Direct lookups outside that scope raise `ActiveRecord::RecordNotFound`, which is
a 404 in production. A submitted `notebook_id` is resolved through
`current_user.notebooks.find_by`, never assigned directly. A missing or foreign
notebook fails validation and renders the form with 422, without saving the note.
Resolve nested records through their authorized parent. Neither an unguessable ID
nor a hidden or disabled button grants or checks permission.

Keep actor-dependent decisions explicit in domain APIs and reusable rendering.
If request-local state is introduced, set and reset it at the request boundary.
Jobs, mailers, and tests must not rely on a previous request having populated it.
Do not adopt a tenancy or identity scheme solely because a reference application
uses one.

## Render on the server, enhance in the browser

Use HTML forms and links for their native semantics. Turbo handles navigation,
frames, and targeted replacements. Stimulus supplies local interaction that HTML
does not provide. Keep persistence and authorization on the server, not in a
second client-side model of the domain.

Partials take the resources and presentation inputs they need. A template may
compose several resources. A reusable partial should not depend on a particular
controller's incidental instance variables or on undeclared request context.
See the [view guide](docs/guides/views.md) for HTML, accessibility, Turbo, and JSON.

## Optimize the actual representation

Start with correct queries and clear response contracts. Filter and order before
pagination. Use a stable tie-breaker where page membership must be deterministic.
Load the associations that the rendered representation uses rather than adding
a universal preload list to every request.

Define cache keys and invalidation rules before introducing caching. Include
permissions, locale, and related-record changes when they affect the output, or
keep those parts outside the shared fragment. The
[board example](docs/references/fizzy.md#boards-and-caching) illustrates why a
warm cache must be tested with another viewer, not just the same request twice.

## Scope and reference boundaries

The [public examples](docs/references/fizzy.md) are evidence for design ideas, not
a compatible application template. Their Ruby, Rails, database adapters, asset
pipeline, editors, and helper libraries differ from this repository. Use the
locked local APIs, and introduce new infrastructure only for a requested feature.

As features land, document their ownership and invariants here. Keep detailed
layer practices in the [model](docs/guides/models.md),
[controller](docs/guides/controllers.md), and [view](docs/guides/views.md) guides,
and verification rules in [TESTING.md](TESTING.md).
# Developing Margin Notes

## Prepare the environment

Use the Ruby version in [.ruby-version](.ruby-version) and Bundler version in
[Gemfile.lock](Gemfile.lock). PostgreSQL must be available, with a local role that
can create the development and disposable test databases configured in
[config/database.yml](config/database.yml).

For an Amp orb, [.agents/setup](.agents/setup) installs the toolchain, database
services, and gems, then prepares the databases.
[.agents/resume](.agents/resume) starts the database services after activation.
These scripts change the environment and databases. Do not run them on a
production machine.

When using mise without shell activation, prefix a command with `mise exec --`,
for example `mise exec -- bin/rails test`. The repository's
[mise configuration](mise.toml) enables the Ruby version file.

With the toolchain and PostgreSQL installed, run:

```sh
bundle install
bin/rails db:prepare
bin/rails server
```

Citation metadata requests, notebook exports, reminders, and digests are
background jobs. To complete them in development, also run a Sidekiq worker and,
for citations, the local stand-in provider, each in its own terminal:

```sh
bundle exec sidekiq
bin/citation-provider
```

The worker needs Redis. The provider listens on `127.0.0.1:9393` and accepts the
development credentials in [config/secrets.yml](config/secrets.yml). Its header
comment lists the DOI endings that simulate a missing record or an unavailable
provider. To use another provider, set `CITATION_PROVIDER_URL`,
`CITATION_PROVIDER_USER`, and `CITATION_PROVIDER_PASSWORD` for both the server and
the worker.

Reminder and digest email is not sent. In development, each recipient's
messages are appended to a file named after their address in `tmp/mails`.

Development caching is off by default, so the exports page renders its
availability indicator without a cache. Run `bin/rails dev:cache` to toggle Rails'
development cache and exercise the cached indicator.

Do not commit decrypted credentials, the master key, local connection secrets,
or recordings containing personal information. Supply real credentials through
the environment or the application's credential mechanism only when needed.

## Implement one observable behavior

Read the relevant [task skill](CLAUDE.md#task-skills) and its guide. Start with the
existing route, model, representation, and test closest to the requested change.
For a new feature, build a small working path through these layers before adding
abstractions for hypothetical variants.

Decide what a caller should observe, including the important rejection or empty
case. For a bug, reproduce the wrong result before changing its implementation
when practical. Keep refactoring separate from a deliberate contract change.

Run focused tests while working, then the broader commands in [TESTING.md](TESTING.md).
For UI changes, inspect the affected states in a browser. A passing request test
cannot establish that a layout or interaction works. Report which checks ran,
including failures, skipped checks, and empty suites.

## Review and delivery

- Inspect the complete diff, including generated files and dependency changes.
- Preserve unrelated local work. Do not reset a database or discard a file to
  make a check pass without understanding what it contains.
- Keep commits coherent. Explain behavior and non-obvious choices rather than
  listing edited files. This repository has no ticket-prefix convention.
- Commit, push, or open a pull request only within the user's requested delivery
  scope. A successful local check does not mean a change has been published.
- When commands, ownership, or conventions change, update their existing guide
  rather than adding a competing instruction elsewhere.
# Testing

## Test the contract at its boundary

Use Rails' Minitest integration with real application objects and the test
PostgreSQL database. Exercise the route, controller, model, and rendering stack
for HTTP behavior. When needed, substitute a controlled response at an external
boundary. Do not stub the domain behavior under test.

Choose the smallest boundary that can catch the likely mistake:

| Contract | Test |
| --- | --- |
| A domain decision, transition, or query | `ActiveSupport::TestCase` in `test/models/` |
| Routing, permissions, persistence, HTML, Turbo, or JSON | `ActionDispatch::IntegrationTest` in `test/controllers/` |
| A workflow across endpoints | An integration test in `test/integration/` |
| Browser execution, focus, navigation, or JavaScript interaction | `ApplicationSystemTestCase` in `test/system/` |
| Scheduling, delivery, and job-specific failure behavior | Rails job and mailer test helpers, usually in the request test that queues the job |

Do not add a separate test for every method. Prefer assertions that would survive
an internal refactor. A useful regression test fails for a plausible wrong
implementation, not just a syntax error.

## Commands and current configuration

Use only a disposable test database. Rails may create, reload, or replace its
data. Never point test configuration at development data you need to keep, a
shared environment, or production.

Run commands from the repository root with the pinned Ruby active:

```sh
bundle check
bin/rails zeitwerk:check
bin/rails test
bin/rails test:system
```

`bin/rails test` does not include system tests. The generated
[system test base](test/application_system_test_case.rb) uses Selenium with Chrome,
not headless Chrome. Until that configuration changes, system tests require a
display and a suitable browser and driver.

For focused feedback, run a test directory:

```sh
bin/rails test test/controllers
bin/rails test test/models
```

To run one file, pass its path to `bin/rails test`. Append `:LINE` to that path to
select a test.

The Gemfile keeps Minitest on 5.x because Rails 7.0's test runner fails under
Minitest 6. No RuboCop, security-audit command, or `bin/ci` is configured.

[test/test_helper.rb](test/test_helper.rb) loads all fixtures and configures
processor-count parallel workers.

The [test environment](config/environments/test.rb) disables caching and raises
application exceptions. For error-response or cache tests, set the required mode
explicitly and restore it afterward. Do not assume production behavior. The mail
delivery method is `:test`.

## Make scenarios distinguish the right behavior

- Name the domain fact or user outcome: a rejected edit leaves the body unchanged,
  not merely that an update action runs.
- Keep arrangement, action, and assertions recognizable. Share setup only for
  facts every test in that group needs. Do not hide the decisive input in a helper.
- Establish meaningful preconditions when the operation could otherwise be a
  no-op. Reload records when checking what was persisted.
- Use asymmetric values and contrasting records. A permission test needs another
  user's record. A filter needs both an included and an excluded candidate.
- Derive expected results independently. Do not call the production scope or
  serializer to compute the value the same scope or serializer should return.
- Assert order only where ordering is promised. For membership, include/exclude
  assertions can express the rule better than an exact count of unrelated fixtures.
  Assert total counts when pagination, duplicates, or filtering totals are contractual.
- Test both a successful result and the relevant failure or boundary. A denial
  should check that no unauthorized write or side effect occurred.

Fizzy's [closure tests](docs/references/fizzy.md#card-closure) combine an initially
open card, a state change, and recorded actor/event information. Its
[comment request tests](docs/references/fizzy.md#comments) check that someone
cannot edit another person's comment and that the stored body remains unchanged.
Those are behavioral contracts, not expectations about private method calls.

## Fixtures and time

Use named, coherent fixtures for shared test data. Change or build a record inside
a test when the variation belongs to that scenario alone. See the
[fixture guide](docs/guides/fixtures.md) before adding shared data.

For time-sensitive behavior, freeze or travel to an explicit instant using Rails'
test helpers and exercise the boundary from both sides. Do not make a test depend
on the current wall clock, execution order, or an arbitrary first fixture.

Keep expected text, dates, IDs, and permission outcomes visible where they explain
the test. Helpers should remove setup mechanics, not choose expected results.

## Requests and representations

Use real verbs, route helpers, and request formats. Check status and the important
response contract as well as persistence: redirect destination, `Location`, field
values, absent versus null fields, or the relevant rendered controls.

For HTML, use `assert_select` for semantic elements, labels, error messages, and
form targets. For JSON, assert the intended public representation rather than the
whole Active Record attribute hash. For Turbo streams, check the action, target,
and meaningful content. A stream response does not prove the browser applied it.

For a browser interaction, drive the visible UI and wait on an observable result
instead of sleeping. Include the failure or non-default state the change affects.
Inspect the rendered result at representative widths when appearance changes.

The [view guide](docs/guides/views.md) distinguishes ordinary forms, enhanced
submissions, and interactions that genuinely require browser coverage.

## Queries and caches

An N+1 regression needs several parent records with different associated records.
Measure the query work inside the request or operation, not fixture loading.
Use the database and supported instrumentation; do not assert private ORM calls
or assume helpers from another repository exist here.

For cache tests, enable caching and use a test-local store. Restore the store and
settings in `ensure` or teardown. Exercise a miss, a hit, a relevant data change,
and a contrasting viewer when output varies by permission. A repeat request with
caching disabled proves nothing about a cache.

Fizzy's [board tests](docs/references/fizzy.md#boards-and-caching) request the same
settings as privileged and unprivileged users with partial caching enabled. The
assertion concerns the disabled control, not merely the number of cache calls.
Fizzy's helper uses renderer internals and is not a drop-in helper for this Rails
version.

## External effects and asynchronous work

Use Rails' job and mailer test helpers for enqueuing/delivery contracts. A test of
enqueueing does not establish successful job execution. Exercise domain behavior
separately, and execute the job when its context, serialization, or retries matter.

Native Sidekiq jobs such as `ExportJob` do not use the Active Job adapter.
[test/test_helper.rb](test/test_helper.rb) loads Sidekiq's fake testing mode, which
keeps each pushed job in memory after a JSON round trip, as Redis would. Assert
`ExportJob.jobs` for the enqueued arguments, call `ExportJob.drain` to run them,
and clear them in setup.

The Active Job test adapter serializes arguments, but does not round-trip them
through JSON as Sidekiq does: a `BigDecimal` argument stays a `BigDecimal` in
tests and arrives as a string in a worker. A time with zone is deserialized in
UTC in both.

Digest requests reserve the reader in a real Redis set, so those tests need Redis
(`REDIS_URL`, by default `redis://localhost:6379`). Set `REDIS_URL` to a disposable
Redis database separate from development, for example
`REDIS_URL=redis://localhost:6379/1 bin/rails test`. Reservations are outside the
database transaction, so each test releases the readers and dates it uses before
starting, and uses dates no other test uses. A refused enqueue is substituted at
the queue boundary with Minitest's `stub`.

Keep remote services out of ordinary tests. The citation enrichment tests serve
scripted responses from a loopback HTTP server in the test process, so Faraday's
retry and authentication run for real without an external service. One test boots
a fresh Rails process to verify environment credentials before configuration is
cached. Use a local fake or an already available substitution facility at the
client boundary. Do not introduce a mocking library just to avoid constructing a
model, and do not record real tokens or personal data in fixtures or HTTP recordings.

# Margin Notes

A full-stack Rails reading-notebook application. Readers sign in, keep private
notebooks, and write rich-text notes with small attachments, tags, a highlight
color, and a draft/ready status. The note list at `/notes` (also bookmarked as
`/journal`) supports title search and notebook and status filters. Each notebook
has settings for its name and export heading, and a slug fixed at creation. The app uses Ruby 3.3.6, Rails 7.0.8.7, PostgreSQL, and Rails'
generated importmap/Turbo/Stimulus frontend.

A reader can import notes into a notebook from a UTF-8 CSV file of up to 100
notes and 100 KB, with this header row:

```csv
title,body_html,doi,annotation,reminder_epoch
```

Only `title` is required. `body_html` becomes the rich-text body. A `doi` looks
like `10.1234/example`. `annotation` is the reader's plain-text comment on the
citation, and `reminder_epoch` is a time in seconds since 1970 (UTC). An imported
reminder is scheduled from its note. The import shows a preview with each row's
source line and errors before anything is saved, then imports all rows or none.

A DOI can also be entered on the note form. From a note's page, a reader can fetch
the cited work's title and source URL from a citation metadata provider. The page
shows whether that request is pending, completed, or failed. Citations, and so
their metadata, are shared by every reader who cites the same DOI. Requests run in
a Sidekiq worker; development uses a local stand-in provider (see
[Contributing](CONTRIBUTING.md#prepare-the-environment)).

A reader can export a notebook as a Markdown file. The export runs in the
Sidekiq worker; its page shows whether it is queued, working, complete, or
cancelled, how many notes it has processed, and its job ID. A queued or working
export can be cancelled. A completed file can be downloaded for 24 hours.

Each notebook has an activity page listing how many of its notes were created on
each UTC date, newest first, skipping dates without notes. It counts the notes the
notebook has now, so it is not a permanent history: a deleted note is no longer
counted.

A reader can schedule an email reminder for a note at a date and time in their
time zone, chosen on the account settings page, and postpone it by a day. From
the notes page, a reader can request an email digest of the ready notes updated
that day, once per UTC day. The digest's day and the request limit both use the
UTC date of the request, which can differ from the reader's date near midnight.
Email is written to files in
development rather than sent (see [Contributing](CONTRIBUTING.md#prepare-the-environment)).

`bin/rails db:seed` creates two development readers, `reader@example.com` and
`other@example.com`, each with the password `password`. There is no registration
or password recovery.

#!/usr/bin/env ruby
# A deterministic local stand-in for the citation metadata provider, for
# development and demonstrations. It never contacts a real service.
#
#   GET /works?doi=10.1234/example with basic authentication answers
#   {"title": "Sample record for 10.1234/example", "url": "https://doi.org/10.1234/example"}
#
# Wrong or missing credentials get 401. These DOI endings simulate failures:
#
#   /not-found          404
#   /unavailable        503 on every request
#   /unavailable-once   503 on the first request since this server started, then 200
#
# Settings: CITATION_PROVIDER_PORT (default 9393), CITATION_PROVIDER_USER and
# CITATION_PROVIDER_PASSWORD (defaults match config/secrets.yml for development).
require "bundler/setup"
require "erb"
require "json"
require "set"
require "rack"
require "rack/handler/puma"

port = Integer(ENV.fetch("CITATION_PROVIDER_PORT", "9393"))
credentials = [ENV.fetch("CITATION_PROVIDER_USER", "margin-notes"), ENV.fetch("CITATION_PROVIDER_PASSWORD", "local-only")]
failed_once = Set.new
lock = Mutex.new

app = lambda do |env|
  request = Rack::Request.new(env)
  auth = Rack::Auth::Basic::Request.new(env)
  doi = request.params["doi"].to_s

  status =
    if !(auth.provided? && auth.basic? && auth.credentials == credentials) then 401
    elsif !request.get? || request.path != "/works" || doi.empty? || doi.end_with?("/not-found") then 404
    elsif doi.end_with?("/unavailable") then 503
    elsif doi.end_with?("/unavailable-once") && lock.synchronize { failed_once.add?(doi) } then 503
    else 200
    end

  body =
    if status == 200
      { title: "Sample record for #{doi}", url: "https://doi.org/#{doi.split("/").map { |part| ERB::Util.url_encode(part) }.join("/")}" }
    else
      { error: Rack::Utils::HTTP_STATUS_CODES[status] }
    end

  $stdout.puts "#{Time.now.utc.iso8601(3)} #{request.request_method} #{request.fullpath} -> #{status}"
  $stdout.flush
  [status, { "Content-Type" => "application/json" }, [body.to_json]]
end

# "-" keeps Puma from loading the application server's config/puma.rb.
Rack::Handler::Puma.run(app, Host: "127.0.0.1", Port: port, Threads: "0:4", config_files: ["-"])
