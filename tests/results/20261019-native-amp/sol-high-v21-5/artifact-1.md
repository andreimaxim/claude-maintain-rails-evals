Evidence labels:

- **App source**: application/configuration/locked dependency code read directly.
- **Upstream source**: released gem source, endpoint diff, upstream tests, or commit implementation read directly.
- **Changelog**: behavior explicitly described in an upstream release entry.
- **Inference**: application consequence inferred from those sources; runtime/data exposure remains unverified.

## 2. High-risk changes

“High” follows the requested rubric: silent behavior/data-format/cache/time-zone changes or incompatibility of queued data across versions. It does not mean every item has equal business impact. Findings generally become reachable after the mechanical boot/API fixes in section 4.

### H1. Failed CSV imports can commit a partial batch

- **Before:** Rails 7.0 rolls back a transaction with writes when its block is exited by a non-local `return`.
- **After:** Rails 7.2 removes that rollback behavior; Rails 8.1 commits an otherwise successful transaction even when the block exits through `return`, `break`, or `throw`. Keeping 7.0 defaults does not retain the removed behavior.
- **Application use:** [Import#apply:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import, then rows, then executes `return false unless row.note.save`. [ImportsController:12–19](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L12-L19) renders an unsuccessful import when false is returned.
- **What could go wrong — inference:** an invalid later row leaves the import and earlier notes/citations/rich text committed although the response says the import failed. Retrying can duplicate earlier rows. Review explicit rollback/error handling rather than relying on control flow.
- **Evidence:** **Changelog** [7.1 transaction explanation](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md#L304-L330), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L371-L377); **upstream source** endpoint transaction-manager diff. The existing [invalid-second-row test:48–72](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L72) already states the atomicity contract; it was read, not run.

### H2. Digest contents switch from UTC days to reader-local days

- **Before:** Active Job serializes a zoned time with an offset, but reconstructs it in the worker's `Time.zone`—UTC in the checked configuration.
- **After:** the serializer also stores the named time zone and restores it. Old payloads without `time_zone` still fall back to the worker zone.
- **Application use:** [User#request_digest:35–41](file:///home/user/workspace/repo/app/models/user.rb#L35-L41) reserves a **UTC** date but enqueues a reader-zone timestamp. [DigestMailer:8–9](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L8-L9) derives both the subject date and SQL `all_day` range from the deserialized timestamp.
- **What could go wrong — inference:** at October 5, 2026, 03:30 UTC, an Eastern reader requests at October 4, 23:30 local. Before, the digest covers October 5 UTC; after, it covers October 4 in Eastern time, while the reservation remains October 5 UTC. Notes can be omitted/included differently without an exception. Old queued jobs and newly queued jobs can cover different kinds of day during the transition. Decide whether digests should remain UTC or become local, and make that explicit.
- **Evidence:** **Changelog** [7.2 entry](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L47-L49); **upstream source** [8.1 serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb). The application's [near-midnight digest test:5–37](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37) independently documents the old UTC expectation; not executed.

### H3. BigDecimal job arguments change format and break old workers

- **Before:** Active Job treats BigDecimal as a primitive; Sidekiq's JSON round trip turns the digest completion into a decimal string.
- **After:** BigDecimal is serialized as a tagged object naming `ActiveJob::Serializers::BigDecimalSerializer`, and restored as BigDecimal. The 7.1 transition switch no longer exists in 8.1.
- **Application use:** [User:41,54–56](file:///home/user/workspace/repo/app/models/user.rb#L41-L56), [DigestJob:6–7](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L6-L7), [DigestMailer:10](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L10). The mailer's conversion already accommodates either string or BigDecimal.
- **What could go wrong — inference:** a Rails 7.0 worker cannot resolve the serializer named by a Rails 8.1 producer, so new digest jobs can fail deserialization during a rolling upgrade or rollback. Conversely, old string payloads remain readable by the new application. Worker/producer upgrade order and rollback/queue draining need an explicit plan; the native ExportJob's scalar payload is not the affected format.
- **Evidence:** **Changelog** [7.1 fix and explicit mixed-version warning](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L157), [7.2 primitive-serializer removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L59-L67); **upstream source** [8.1 serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

### H4. Import-preview annotations silently disappear

- **Before:** `HashWithIndifferentAccess#stringify_keys` duplicates the hash without converting existing integer keys.
- **After:** Rails 8.0 fixes it to stringify **all** keys, including integers. Indifferent access converts symbols, not integer lookups.
- **Application use:** [Import#annotations:38–41](file:///home/user/workspace/repo/app/models/import.rb#L38-L41) stores annotations under integer source-line keys. [preview:22,42–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys` and then looks up integers.
- **What could go wrong — inference:** the lookup misses and the preview omits annotations without an error. Annotation assignment to saved notes is separate and remains present; this is a preview defect, not inferred deletion of stored annotations. Review whether this hash needs stringification at all.
- **Evidence:** **Changelog and upstream before/after example** [8.0 entry](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md#L30-L48). Existing [preview assertions:20–24](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L20-L24) cover the visible contract; not run.

### H5. CSV receipts lose DOI values from custom-primary-key citations

- **Before:** `read_attribute(:id)`, including `record[:id]`, returns the custom primary key when it is not named `id`.
- **After:** it reads the actual `id` attribute. With no `id` column, this case returns nil; `.id` still means the model primary key.
- **Application use:** [Import#receipt:63–68](file:///home/user/workspace/repo/app/models/import.rb#L63-L68) writes `citation[:id]`; [schema:55–62](file:///home/user/workspace/repo/db/schema.rb#L55-L62) defines `citations.doi` as the primary key and no `id` column.
- **What could go wrong — inference:** receipts retain their titles but emit blank DOI fields. The citation relation itself is not lost. Read `.doi` or `.id` deliberately when implementing the upgrade.
- **Evidence:** **Changelog** [7.1 explanation](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md#L219-L225), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L425-L427); **upstream source** [8.1 read implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb) and its custom-primary-key tests. Existing [CSV expectation:43–45](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) would detect this; not run.

### H6. Reminder postponement displays a different wall-clock time across DST

- **Before:** with this application's 7.0 defaults, `TimeWithZone#to_time` retains a fixed UTC offset.
- **After:** Rails 8.1 always retains the receiver's named time zone, so subsequent elapsed-time arithmetic crosses daylight-saving transitions using the new offset. This is not prevented by retaining 7.0 defaults.
- **Application use:** [Note#next_day_reminder_at:40–44](file:///home/user/workspace/repo/app/models/note.rb#L40-L44) adds 86,400 seconds after `to_time`; [reminder preview:17–19](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L17-L19) displays it; [postpone_reminder:71–72](file:///home/user/workspace/repo/app/models/note.rb#L71-L72) persists its epoch.
- **What could go wrong — inference:** October 31, 2026, 09:00 Eastern + 24 elapsed hours used to display November 1, 09:00 −04:00; it now displays 08:00 −05:00. The instant/epoch and the application's “24 elapsed hours” scheduling are unchanged, but the preview's text/offset contract changes. Do not “fix” it to calendar-day arithmetic without a product decision.
- **Evidence:** **Changelog** [8.1 removal](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md#L15-L22); **upstream source** [TimeWithZone#to_time](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb). Existing [DST expectation:13–21](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L13-L21) explicitly expects the old display; not run.

### H7. Expired-export fragments can become non-expiring cache entries

- **Before:** a negative `expires_in` produces an already-expired cache entry.
- **After:** the cache removes the invalid negative TTL. With 7.0 defaults, it reports/logs the error rather than raising; with no store-wide TTL, the resulting entry has no expiration. Adopting 7.1 defaults instead raises `ArgumentError`.
- **Application use:** [export fragment:25–35](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L35) calculates `expires_in: export.expires_at - Time.current`, which is negative for completed but expired exports.
- **What could go wrong — inference:** requests after expiry repeatedly report invalid TTLs and may cache the expired-state fragment indefinitely. This is a silent cache-lifetime change, **not an authorization bypass**: [download controller:5–15](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) independently checks expiry before conditional responses or file delivery. Avoid caching with a nonpositive TTL, or deliberately separate the expired state.
- **Evidence:** **Changelog** [7.1 invalid-expiration configuration](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md#L861-L869); **upstream source** [8.1 cache option normalization](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L908-L947). The deletion of the TTL, not merely the new raise setting, establishes the changed behavior.

### H8. Rich-text plain-text conversion changes exported bytes and snippets

- **Before:** conversion descends into `script`/`style` text, and ordered-list numbering uses the position among **all child nodes**, including intervening whitespace text nodes.
- **After:** script/style contents contribute no text; ordered-list numbering uses element positions. The conversion also becomes iterative to avoid stack overflows.
- **Application use:** [Export#markdown_for:77–81](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) turns the result into stored downloadable Markdown; [notes list:52–53](file:///home/user/workspace/repo/app/views/notes/index.html.erb#L52-L53) and [import preview:56–58](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58) show snippets. [Import:101–106](file:///home/user/workspace/repo/app/models/import.rb#L101-L106) accepts arbitrary body HTML, so these inputs are allowed even if the editor normally emits simpler markup.
- **What could go wrong — inference:** regenerated exports differ for the same body: whitespace-separated ordered lists get different numbers and embedded script/style text disappears. Existing stored export files are not rewritten by upgrading; files generated by old/new workers can differ. Review representative imported bodies and export expectations. These fixes may be desirable, but they change data output.
- **Evidence:** **Upstream source and commit**, not just changelog: [plaintext rewrite PR #55025](https://github.com/rails/rails/pull/55025), [script/style omission commit](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057), [released 8.1 converter](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/plain_text_conversion.rb), compared with 7.0.8.7.

### H9. Attachment filenames are silently sanitized more aggressively

- **Before:** Active Storage filename rendering permits `<`, `>`, `?`, `*`, and `"` while replacing its older unsafe-character set.
- **After:** Rails 8.0 also replaces those five characters with `-` in `Filename#sanitized`, and thus `to_s`.
- **Application use:** [attachment partial:2–11](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb#L2-L11) uses blob filenames for image alt text, names, and download URLs. Notes accept file attachments through [rich-text field:49–51](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L49-L51).
- **What could go wrong — inference:** an existing user upload named `draft?.pdf` displays/downloads as `draft-.pdf`, with no error. Raw stored filename/blob identity is not renamed. Generated Markdown filenames use parameterized notebook slugs and are not the likely exposure. Review whether external filename-sensitive workflows exist; none was established from this repository.
- **Evidence:** **Changelog** [8.0 entry](https://github.com/rails/rails/blob/v8.0.0/activestorage/CHANGELOG.md#L22-L25); **upstream source** [8.1 filename implementation](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/filename.rb), endpoint diff. High under the silent-format rule, with limited apparent application impact.

### H10. HTML content attachments have a different accepted/stored representation — conditional on body content

- **Before:** Action Text recognizes its special `vnd.rubyonrails.horizontal-rule.html` attachment by type/name; the attachment attribute list does not retain arbitrary `content` HTML.
- **After:** content attachments accept HTML types plus nonblank `content`; `content` becomes a retained attachment attribute and is sanitized when attachments are rendered, including the edit representation. A legacy horizontal-rule attachment with no content no longer satisfies that new content-attachment contract.
- **Application use:** the [CSV importer:101–106](file:///home/user/workspace/repo/app/models/import.rb#L101-L106) accepts Action Text/HTML bodies without excluding these attachment forms; the [editor:50](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L50) and [show page:31](file:///home/user/workspace/repo/app/views/notes/show.html.erb#L31) render stored bodies.
- **What could go wrong — inference:** affected imported/legacy bodies can render different attachment content or missing-attachment output, and newly saved content attributes may not round-trip equivalently through old/new servers. **No stored-body inventory was read, and no custom content-attachment producer was found**, so actual exposure is unknown; this is a targeted data-inspection gate, not a claim that every note changes.
- **Evidence:** **Changelog** [7.1 generalized content attachments](https://github.com/rails/rails/blob/v7.1.0/actiontext/CHANGELOG.md#L64-L66), [7.2 edit-view sanitization](https://github.com/rails/rails/blob/v7.2.0/actiontext/CHANGELOG.md#L3-L10); **upstream source** endpoint diffs of [ContentAttachment](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/attachables/content_attachment.rb), [Attachment::ATTRIBUTES](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/attachment.rb), and [Content#render_attachments](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/content.rb).

## 3. Medium-risk changes

### M1. Removed `Rails.application.secrets` breaks citation enrichment

- **Before:** `Rails.application.secrets` reads the application's YAML/environment-backed provider configuration.
- **After:** the API is deprecated in 7.1 and removed in 7.2; 8.1 does not provide it.
- **Application use:** [Citation::Provider#initialize:13–14](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L14), with configuration in [secrets.yml:5–18](file:///home/user/workspace/repo/config/secrets.yml#L5-L18). [Citation#enrich:28–32](file:///home/user/workspace/repo/app/models/citation.rb#L28-L32) constructs the provider without injecting settings.
- **What could go wrong — inference:** enrichment raises `NoMethodError` before making the HTTP request. That is not rescued as a provider-domain error, so Sidekiq retries and the citation may remain pending. Decide where configuration belongs—credentials, explicit ENV-backed configuration, or injected settings—and preserve the intended environment behavior. Renaming this call to `credentials` alone does not migrate the existing YAML settings.
- **Evidence:** **Changelog** [7.1 deprecation](https://github.com/rails/rails/blob/v7.1.0/railties/CHANGELOG.md#L165-L170), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63); **upstream source** application API endpoint diff.

### M2. Resolved JSON 3.1.0 rejects an option passed by Rails 8.1.0's JSON column coder

- **Before:** the local baseline JSON 2.7.2 ignores unknown parser options; Rails 7.0's JSON coder also passes no options to decode.
- **After:** Rails 8.1.0's `ActiveRecord::Coders::JSON` initializes `@options` with `{ escape: false }` and passes that hash to `ActiveSupport::JSON.decode`, which passes it to `JSON.parse`. JSON 3 rejects unknown parser options, and `escape` is not a recognized parser option.
- **Application use:** [Note:12](file:///home/user/workspace/repo/app/models/note.rb#L12) serializes tags through this Rails coder. This remains a problem **after** the separate positional-argument fix to `serialize :tags, coder: JSON`; [schema:99](file:///home/user/workspace/repo/db/schema.rb#L99) contains nonblank JSON text, including the default `[]`.
- **What could go wrong — inference:** loading/deserializing tags is predicted to raise `ArgumentError` for `escape`. This is a source-traced incompatibility, **not runtime-reproduced**. The decision is dependency compatibility: constrain JSON to a compatible 2.x release, select a framework release with a compatible coder, or intentionally replace/adapt the coder after review. Rails-only changelogs would miss the newly resolved JSON major version.
- **A second JSON contract change:** [Citation::Provider:42–52](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) uses plain `JSON.parse`. JSON 3 rejects duplicate object keys and JavaScript comments by default; previously accepted provider responses of those forms now become the app's “not valid JSON” enrichment failure. Invalid escapes are also rejected more strictly than the old baseline. No actual provider response using those forms was established. Decide whether strict rejection is desired rather than globally enabling permissive parsing.
- **Evidence:** **Changelog** [JSON 3.0/3.1 changes](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md); **upstream source** [Rails coder](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/coders/json.rb), [decode pass-through](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb), [JSON parser option validation](https://github.com/ruby/json/blob/v3.1.0/ext/json/ext/parser/parser.c). The [Rails commit introducing the coder options](https://github.com/rails/rails/commit/90616277e3d8fc46c9cf35d6a7470ff1ea0092f7) explains their encoding motivation, but the released load path passes them to parsing too.

### M3. Built-in Sidekiq adapter is deprecated, with removal in Rails 8.2

- **Before:** Rails owns the Sidekiq Active Job adapter used by this application.
- **After:** Rails 8.1 still provides it but deprecates it for removal in 8.2, directing applications to Sidekiq ≥7.3.3, which supplies its own adapter.
