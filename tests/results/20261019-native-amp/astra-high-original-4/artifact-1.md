# Rails 7.0.8.7 → 8.1.0: Margin Notes upgrade assessment

**Recommendation: proceed as a staged compatibility upgrade, not a gem-only bump and not an immediate `load_defaults 8.1` change.** Keep Ruby 3.3.6 and Rails 7.0 defaults initially. This application has confirmed boot failures, request/job failures, a partial-import data-integrity regression, and incompatible queue payloads. No working application files were changed. Diagnostic edits were confined to disposable checkouts.

Reviewed application revision: [ab732f5](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7), with no tracked worktree changes. Assessment/resolution date: 19 October 2026. Exact requested target: **8.1.0**, not the newest Rails release. This is a compatibility assessment, not a security certification of that patch release.

## 1. Evidence and boundaries

- **Executed baseline:** Rails 7.0.8.7, original lockfile, Ruby 3.3.6, PostgreSQL 15.19: **46 tests, 325 assertions, 0 failures/errors/skips**.
- **Executed target resolution:** Rails 8.1.0 resolves with Sidekiq 6.5.12, Redis 4.8.1, Rack 2.2.24, rack-session 1.0.2, rackup 1.0.1, Puma 5.6.9, pg 1.6.0, Pagy 8.6.3, Sprockets 4.4.1 / sprockets-rails 3.5.2. Ruby 3.3.6 satisfies Rails' ≥3.2 requirement. There is **no demonstrated dependency requirement to upgrade Sidekiq, Redis, Puma, or Rack to their next major**.
- **Executed untouched-code target boot:** fails in `config/initializers/action_text.rb:3`: `allowed_tags` is nil; `nil + ...` raises.
- **Diagnostic variant A:** only boot/model compatibility edits in `boot-only.patch`, retaining `load_defaults 7.0`. Eager loading passes. Tests: **46 tests, 44 assertions, 28 failures, 17 errors**. A newly resolved JSON 3.1.0 caused widespread decoding failures; old boolean exception configuration hid request exceptions behind 500 responses.

- **Executed targeted checks:** actual `Import#apply` outside test transactions; import annotations/receipt; reminder DST conversion and scheduling serialization; old/new digest JSON payloads in both directions; real enqueue through Sidekiq into private Redis; JSON versus YAML serialization; negative cache TTL; PostgreSQL date decoding; readonly assignment; rich-text HTML parsing; retry algorithm names. See sections below.
- **Source-based conclusions:** tagged Rails 7.0.8.7 and 8.1.0 implementations, intervening release guidance, and selected 7.1/7.2/8.0 tagged implementations. These are distinguished from execution below. Intermediate Rails application suites were **not** run.
- **Still proposed:** complete fixed-app suite, browser workflows, production-mode smoke/assets checks, actual Sidekiq worker execution/retry under both releases, full job-envelope migration tests, cookie/blob/SGID bidirectional tests, a production data sample audit, and mixed-fleet/rollback rehearsal. No production/shared data or queue contents were inspected.

## 2. Required compatibility work, even with Rails 7.0 defaults

“7.0 preparation” below means the proposed approach works on **7.0.8.7**, not merely that the file parses. Unless explicitly identified as executed, compatibility is based on source/API inspection and still needs the proposed validation.

### R1. Constrain the newly introduced JSON dependency for this exact Rails release

- **Affected:** `Gemfile`, `Gemfile.lock`; JSON session decoding, `Note.tags`, JSONB settings, and framework JSON decoding generally.
- **Condition/evidence:** resolving Rails 8.1.0 today introduces JSON 3.1.0. Active Support 8.1.0 calls `JSON.parse(json, options)`; JSON 3 requires keyword options. The resulting `ArgumentError (given 2, expected 1)` was executed and traced through `ActiveSupport::JSON.decode` and Active Record's JSON coder. Resolving with `json < 3` selected 2.21.2 and removed this blocking error, exposing the actual application incompatibilities.
- **Recommendation:** constrain JSON to a compatible 2.x release and retain the resolved lockfile while targeting exact Rails 8.1.0. Do not monkey-patch JSON or silently change the requested Rails patch version. Separately assess the security/support status of the final locked bundle before deployment.
- **7.0 preparation:** the constraint permits the currently used default JSON 2.7.2; upgrading the baseline to JSON 2.21.2 was not tested. Do not imply that adding a constraint and resolving a new baseline lock is behavior-free.
- **Validation:** fresh install from final lock; sign in and reuse the cookie; read/write pre-existing JSON tags and settings; provider JSON parsing and Active Job JSON round trip.
- **Sources:** [Rails decoder](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb), [JSON 3.1.0 changelog including 3.0 API changes](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md).

### R4. Preserve JSON tags and YAML preferences; do not “prepare” with the new keyword on 7.0

- **Affected:** `app/models/note.rb:12` (`tags`, JSON text, default `[]`); `app/models/notebook.rb:7` (`preferences`, YAML text); corresponding migrations, fixtures and stored rows.
- **Condition/evidence:** positional coder removed in 7.2. **Executed trap:** `serialize :tags, coder: JSON` on 7.0 silently uses YAML: serializing `["alpha", "beta"]` produced `---\n- alpha\n- beta\n`, whereas current Note and target keyword form produced JSON. A syntax-only preparation could corrupt cross-version readability. Notebook's implicit YAML serializer still works on 8.1 with retained 7.0 defaults; `load_defaults 7.1+` removes the implicit default and requires a coder.

- **Validation:** copy representative raw legacy values (JSON arrays, Unicode, empty tags, nil/empty/populated YAML preferences) into an isolated database; read under both versions, write on the new version, read on the old rollback version; compare raw column encodings, not only deserialized values. Audit production samples for unexpected YAML classes/keys before claiming all stored preferences are supported. No bulk rewrite is required for the intended syntax-only change.

## 4. Deployment, persisted data, queues and rollback

### Before any version overlap

1. **Inventory and back up actual state without exposing secrets:** database (especially raw tags/preferences/rich text), Disk blobs/exports, environment/credential secret provenance, active/scheduled/retry/dead Sidekiq jobs, and digest reservations. Confirm actual production PostgreSQL/Redis versions, storage mounts, cache sharing and mailer configuration; repository configuration is not proof of a deployed setup.
2. Preserve `secret_key_base`. For development/test, 7.1 changes `tmp/development_secret.txt` to `tmp/local_secret.txt`: **copy** the old value before first newer boot, retaining the old file for rollback. Otherwise old cookies and persisted attachment signatures may stop working. Do not print keys or deploy the synthetic secret used in these experiments. Production must retain its real secret through ENV/credentials; no production secret was inspected.
3. Deploy the **7.0-compatible** preparation first: explicit import rollback/lookups, enum/accessors, routes/filter/form, provider configuration, Time scheduling, string export concatenation/TTL guard, digest UTC normalization and neutral arguments. Decide DST preview policy. Keep JSON tag syntax, retry symbol and exception setting version-appropriate until 7.1. Re-run baseline tests and real queue boundaries after preparation.
4. Ensure all producers use neutral digest arguments before mixing 7.0 workers with newer producers. Include retries/manual replays, not just HTTP requests. Keep job class names, GlobalID app identity, record primary keys, queue names and reminder IDs stable.

### Upgrade sequence

- Follow [Rails' incremental upgrade guidance](https://guides.rubyonrails.org/v8.1.0/upgrading_ruby_on_rails.html#the-upgrade-process): latest suitable patches in 7.0 → 7.1 → 7.2 → 8.0 → exact requested 8.1.0, resolving/testing each step and recording lockfiles/deprecations. Intermediate patch choices have not been resolved in this assessment. Ruby stays 3.3.6; avoid combining a Ruby 3.4 migration (CSV stops being a default gem) with this task.
- At 7.1 switch the coder keyword, retry symbol and test exception option; keep defaults pinned. Review `app:update` diffs rather than accepting generated defaults wholesale. Preserve Sprockets/importmap, the current auth system, PostgreSQL, Redis and Sidekiq.
- At each step test production-mode eager loading, assets precompile, sign-in/session reuse, owned/foreign CRUD, imports, actual workers, storage, email (captured locally), and all key response paths. Then run the targeted cross-version/data checks above; a green ordinary suite is necessary, not sufficient.
- Adopt optional defaults one at a time only after compatibility is stable. Do not create a single “all defaults on” deployment during a mixed-version window.

### Queue drain and rollback policy

- **Old jobs on new workers:** old digest string/time payloads decoded successfully in the experiment. Existing Sidekiq wrapper class is still present in 8.1. Old scheduled reminders use the outer Sidekiq timestamp; retain their job IDs so replacement checks continue to work. Full worker execution, citation retries and framework purge/analysis jobs must still be rehearsed, not inferred from argument tests.
- **New jobs on old workers:** unmodified new BigDecimal payloads are demonstrably incompatible with Rails 7.0. Neutral time/string producer preparation avoids that for future digest requests. If any typed payloads already exist, rollback must pause producers, drain them on compatible workers or use an audited migration/compatible-reader backport. Simply pausing workers and rolling back is insufficient. Include the scheduled, retry and dead sets, not just the immediate queue; reminders can be scheduled far ahead, so “wait until the queue looks empty” is not a complete policy.
- **Never flush Redis as an upgrade step.** It holds jobs **and** digest reservation sets; removing reservations can allow duplicate digests. Never replace reminder jobs casually with new job IDs without reconciling the persisted current ID. Existing duplicate-mail-on-worker-crash limitations are pre-existing, not solved by this upgrade.
- **Native exports:** IDs/options remain stable. Completed Markdown files do not need regeneration; interrupted working exports may retry from the start and must still respect cancellation. Fix concatenation before new workers take existing export work. Do not purge expired files as part of compatibility work.
- **Rollback data:** preserve JSON tags/YAML preferences; no required schema migration was identified for these fixes. Keep backup copies of raw rich text if new parsing/editor saves rewrite it. Software rollback cannot undo a partially committed import or recover content already overwritten; prevent those writes before rollout, and use a separately reviewed repair if they have occurred.
- **Rollback signatures/caches:** keeping the same secret is necessary but not sufficient after changing message formats. Delay new writers until old readers are retired and the rollback window is closed, or prove bidirectional compatibility and install supported rotations/readers first. Namespace/invalidate only the disposable application cache if its format changes; do not change session signing keys or remove stored blobs to get a passing smoke test.

### Sidekiq upgrade is separate, not silently bundled into Rails

Rails 8.1 still supplies the built-in Sidekiq adapter; it is deprecated for removal in **8.2**, and recommends Sidekiq ≥7.3.3 for the gem-owned adapter. Source inspection and real enqueue show the pinned 6.5.12 path is usable for this evaluation, not that an entire production deployment is certified. If upgrading Sidekiq separately, reassess native `ExportJob`'s symbol-keyed `{ format: "markdown" }` (strict JSON arguments), `User#request_digest`'s `redis.sadd` boolean assumption, `Redis::BaseError` rescue boundaries, Redis protocol/server requirements and wrapper compatibility. Those are not required changes from Rails dependency resolution alone. Keep `concurrent-ruby 1.3.4` during 7.0 preparation; removing that pin is unrelated and could revive the old logger-load issue.
