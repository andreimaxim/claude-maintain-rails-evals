# Margin Notes: Rails 7.0.8.7 → 8.1.0 assessment

## Decision and evidence boundaries

Proceed as a staged compatibility project, not a Gemfile-only update. Keep `config.load_defaults 7.0` during the framework upgrade; defaults adoption is a separate change. Ruby 3.3.6 already satisfies Rails 8.1's Ruby >= 3.2 requirement.

This is a **source-based assessment**, not a successful upgrade rehearsal. Inspected application, lockfile, configuration, tests, and exact Rails v7.0.8.7/v8.1.0 source archives. No application boot, bundle resolution, database operation, worker execution, or browser test was run. No working application files were changed. Target dependency compatibility and actual stored-data contents remain unverified.

Upstream reference: [tagged upgrade guide](https://github.com/rails/rails/blob/v8.1.0/guides/source/upgrading_ruby_on_rails.md), [7.1 release notes](https://github.com/rails/rails/blob/v8.1.0/guides/source/7_1_release_notes.md), [7.2 release notes](https://github.com/rails/rails/blob/v8.1.0/guides/source/7_2_release_notes.md), [8.0 release notes](https://github.com/rails/rails/blob/v8.1.0/guides/source/8_0_release_notes.md), [8.1 release notes](https://github.com/rails/rails/blob/v8.1.0/guides/source/8_1_release_notes.md). The hosted `/v8.1/` guide currently identifies itself as 8.1.4; exact-tag source was used for target-specific conclusions.

## Required compatibility work (even with 7.0 defaults)

Each validation below is **proposed**, not executed.

1. **Action Text initializer will not survive the changed allowlist API.** `config/initializers/action_text.rb` uses `allowed_tags += ...`. In 7.0 it starts as an inherited list; in 8.1 `allowed_tags` starts nil and effective defaults are computed by `sanitizer_allowed_tags`. Build the explicit allowlist from the configured sanitizer's defaults plus `ActionText::Attachment.tag_name`, `figure`, `figcaption`, `details`, and `summary`, at an initialization point where the selected sanitizer is known. Do not merely replace nil with an empty array: that strips normal formatting/attachments. Building from these APIs is possible on 7.0 too. Validate cold boot and render stored links, attachment figures, details/summary, malformed HTML, and script/event-handler input. Recheck under both HTML4 and HTML5 sanitizer settings. Source: [8.1 helper](https://github.com/rails/rails/blob/v8.1.0/actiontext/app/helpers/action_text/content_helper.rb).

2. **Removed Active Record declarations.** `app/models/note.rb` uses keyword-style `enum status: ..., _prefix: true` and positional `serialize :tags, JSON`. Use `enum :status, {...}, prefix: true` (already supported by 7.0 and used by the other models). On 7.1 change serialization to `serialize :tags, coder: JSON`; keep JSON bytes, null/default behavior and array semantics. Do not assume the keyword-coder declaration is a 7.0-compatible preparation: 7.0's implementation selects its coder from the positional argument. `Notebook#preferences` currently defaults to YAML; explicitly use `coder: YAML` on 7.1 before adopting defaults that remove the default serializer. Do not convert existing preferences to JSON incidentally. Validate old raw JSON tags and YAML preferences, nil/empty values, tag edit/reload, heading edit/export, and old-version reads of new writes. Inventory real YAML classes before adding any safe-load permissions; do not enable unsafe YAML globally. Source: [8.1 serialization](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/serialization.rb), 7.2 removal notes; [8.0 enum implementation](https://github.com/rails/rails/blob/v8.0.0/activerecord/lib/active_record/enum.rb).

3. **Highlight aliases target a store accessor, not a column.** `Note` declares `store_accessor :settings, :color` then `alias_attribute :highlight_color, :color`. Rails 7.2 rejects aliases of non-attributes. Replace with explicit getter/setter delegating to `color`/`color=`; this works on 7.0 too. Validate editing `highlight_color` through the note form, persistence in `settings["color"]`, reload/render, and invalid-color rejection without losing other settings keys. Source: 7.1 deprecation and 7.2 removal notes, not merely the guide's custom-attribute-method example.

4. **Provider configuration API removed in 7.2.** `app/models/citation/provider.rb` defaults to `Rails.application.secrets.citation_provider.to_h`; `config/secrets.yml` contains environment-backed settings. Move those settings to an application-owned `config_for` YAML file or explicit environment-backed configuration, preserve development/test defaults and production absence semantics, and update the provider plus fresh-process credential test. Both approaches work on 7.0. Never transplant credentials into source. Validate a fresh process per environment with fake credentials against the loopback provider; assert Basic Auth, configured URL, missing configuration, and no secret logging. Existing tests injecting settings do not cover this default initialization path.

5. **Citation retry option removed in 7.2.** `app/jobs/citation_enrichment_job.rb` uses `wait: :exponentially_longer`. Replace with `:polynomially_longer` at 7.1 (not supported as that symbol in 7.0), or prepare on 7.0 with a numeric wait proc reproducing `(executions**4) + jitter + 2`, including existing 0.15 jitter. Preserve three attempts and terminal failure recording. Exercise actual retry execution with a scripted 503/429 provider, assert retry-delay bounds, maximum six provider requests, terminal failed state, and no unintended extra Sidekiq retry after exhaustion. Existing queued retries remain relevant and must use the same job class.

6. **Failed CSV imports can commit partial data.** `Import#apply` in `app/models/import.rb` saves the import and notes, then `return false` exits the transaction on a failed row. Rails 7.0 rolls back this nonlocal return; 7.2+ commits. Use an explicit `ActiveRecord::Rollback` with an outer result flag, or save! and translate only the intended validation exception outside the transaction while retaining row errors. Compatible preparation on 7.0. Validate a valid first row followed by an invalid second row: no import, notes, citations, or Action Text rows survive, and the response retains row errors. Existing invalid-row request coverage is useful but exercise failure after a successful save, not just preview rejection. Also validate a fully valid batch.

7. **Non-id primary-key receipt lookup loses its alias.** `Import#receipt` uses `citation[:id]`, but `Citation` has `doi` as its database primary key. 7.0 `read_attribute` rewrites `id` to the primary key; 8.1 no longer does. Use `citation.doi` (works on 7.0). Validate exact CSV content with a DOI containing punctuation and a note without a citation. The current receipt assertion should expose this; no schema migration is needed. Source: [7.0 read implementation](https://github.com/rails/rails/blob/v7.0.8.7/activerecord/lib/active_record/attribute_methods/read.rb) versus [8.1](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb).

8. **Preview annotations depend on integer-key stringify behavior.** `Import#annotations` returns a HashWithIndifferentAccess keyed by source-line integers; `app/views/imports/preview.html.erb` calls `stringify_keys` then looks up the integer. 7.0's HWiA implementation simply duplicates the hash; 8.1 uses actual key transformation, turning the line into text. Remove the unnecessary stringify call, or consistently key/look up strings. Either preparation works on 7.0. Validate two distinct annotations, including a quoted multiline CSV row whose source line differs from ordinal position; HTML must display escaped annotations on the correct rows.

9. **Digest queue payload and day semantics change.** `User#request_digest`, `DigestJob`, and `DigestMailer#daily_digest` rely on Active Job 7.0 losing the named time zone and Sidekiq JSON converting BigDecimal to string. 8.1 TimeWithZoneSerializer stores the zone and BigDecimalSerializer writes a named serializer envelope. Thus new jobs can select the reader-local day while Redis still deduplicates the UTC day; old workers cannot deserialize the new BigDecimal serializer. Explicitly normalize the request time to UTC inside DigestMailer before `to_date`/`all_day` (works on 7.0 and handles both old/new payloads). Prepare producers to send completion as a decimal string, e.g. `to_s("F")`, on 7.0. Keep old payload deserialization support until all ready, scheduled, retry, and dead jobs have been handled. Validate JSON-round-tripped jobs in both directions: old producer→new worker and new prepared producer→old worker. Use Eastern 2026-10-04 23:30 (UTC October 5) and notes on opposite sides of UTC midnight; expect October 5 digest content and title in both cases. Test completion 0.6667, not just 0 or 1. The test adapter is not a Redis JSON round trip. Source: [8.1 serializers](https://github.com/rails/rails/tree/v8.1.0/activejob/lib/active_job/serializers), [7.0 serializers](https://github.com/rails/rails/tree/v7.0.8.7/activejob/lib/active_job/serializers).

10. **Postponement preview changes across DST independently of defaults.** `Note#next_day_reminder_at` uses `reminder_at.to_time + 86_400`. In 8.1 `to_time` retains the named zone rather than only a fixed offset; the preview now follows the DST offset. Scheduling still uses the same epoch. Decide whether to adopt the corrected local preview (recommended) and update the documented contract, or explicitly obtain a fixed-offset Time if preserving presentation is essential. A version-independent local preview can be prepared on 7.0 using `reminder_at + 24.hours`. Validate both spring-forward and fall-back: displayed zone/wall time and scheduled instant exactly 86,400 seconds later. Do not mistake this for a changed reminder execution time. Source: [8.1 TimeWithZone#to_time](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb).

## Optional defaults adoption: separate deployment/review

Source of truth: [8.1 load_defaults implementation](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application/configuration.rb).

- **PostgreSQL decoded dates (7.2 defaults):** `Notebook#daily_note_counts` parses `select_rows`' day with `Date.iso8601`; decoded PostgreSQL dates become Date objects. Before enabling `postgresql_adapter_decode_dates`, accept already-decoded Date or parse text; this works on 7.0. Validate raw row types plus actual rendered counts on two UTC dates under both flags. This is not an unconditional 8.1 break with 7.0 defaults.
- **Read-only assignment errors (7.1 defaults):** `NotebooksController#notebook_params` permits `slug`, and the form submits it unchanged. Raising on readonly assignment can reject even the ordinary settings submission. Stop permitting/resubmitting slug on update; retain creation's model-generated slug. Preparation works on 7.0. Validate unchanged and forged slug submissions both preserve persisted slug while allowing name/heading edits.
- **Default YAML coder removal (7.1 defaults):** make Notebook preferences' YAML coder explicit as above. Retaining 7.0 defaults avoids this separate issue but not Note's removed positional signature.
- **HTML5 sanitization (7.1 defaults):** Action Text stores rich HTML and the app customizes rendering. Differentially render old bodies with malformed nesting, tables, links, details/summary and embedded signed attachments; compare safe output and plain-text exports. Editor save may rewrite stored bodies irreversibly. Retain HTML4 initially; do not bulk resave rich text. Test the vendored Trix 1.3.5 with upgraded Action Text JavaScript (loaded from the gem via importmap), direct upload, edit/save/reopen, attachment download and sanitization. Trix 2 adoption is a separate frontend change, not proven necessary by a Rails version bump. Existing details flattening is a documented pre-existing limitation.
- **Cache/message formats (7.1 defaults):** keep cache format 7.0 and old message metadata format during overlap/rollback. Completed export availability fragments are real cache consumers; tests normally disable cache. If new cache format is adopted after old readers are gone, use a new namespace or disposable cold cache on rollback. New signed-message metadata may not be understood by 7.0; validate old/new session cookies, Active Storage signed IDs and Action Text attachment SGIDs in both directions before changing message settings. Existing JSON cookies and SHA256 key derivation are already 7.0 defaults: do not rotate keys merely because Rails changes.
- **Cache expiration validation (7.1 defaults):** `app/views/exports/_export.html.erb` computes `expires_in: expires_at - Time.current`, which is nonpositive for expired exports. New strict validation raises instead of displaying Expired. Only cache availability while future, or use a deliberate positive TTL for the expired representation. Conditional rendering preparation works on 7.0. With caching enabled, test just before, exactly at, and after expiry, both cold/warm; continue enforcing expiry before conditional download responses.
- **Strict HTTP freshness (8.0 defaults):** `ExportDownloadsController#show` uses ETag plus Last-Modified. New behavior gives If-None-Match precedence. Validate conflicting validators (matching ETag/stale date and nonmatching ETag/future date), single validators, and expiry/foreign-user checks before any 304. Adopt deliberately; authorization/expiry is not delegated to the cache.
- **Other generated defaults are not migration requirements:** keep Sidekiq, Sprockets and Disk storage. Solid Queue/Cache/Cable, Propshaft, new authentication generator, deployment scaffolding and YJIT changes do not need adoption. No app-owned AR encryption, custom streaming subclass, alias of a real column with a custom getter, or SQLite use was found. Schema column alphabetization in 8.1 is dump noise, not a data reorder migration.

## Dependencies and enqueue semantics: avoid unsupported assumptions

Gemfile.lock has Sidekiq 6.5.12 (Rack ~> 2.0; Redis < 5), Redis 4.8.1, Puma 5.6.9, Sprockets Rails 3.5.2, pg 1.6.0, Faraday 1.10.4, Pagy 8.6.3. Rails 8.1 actionpack requires Rack >= 2.2.4, not necessarily Rack 3. Do not declare a Sidekiq Rack conflict without resolving: compatible Rack 2 versions can satisfy these constraints, but rackup/rack-session choices also matter. Resolve a minimal target lock in isolation, retain its entire lockfile and resolver output, then boot web and worker processes. Ruby version need not change in this upgrade. Keep the Minitest 5 pin initially; removal is optional. The concurrent-ruby pin can be reconsidered separately after intermediate-version boot checks.

Rails 8.1 still ships its Sidekiq adapter and accepts Sidekiq >= 4.1; it warns that removal is planned for 8.2 and recommends Sidekiq >= 7.3.3. Therefore upgrading Sidekiq is not demonstrated to be required for this target. Prefer keeping it stable for the Rails assessment. A later Sidekiq upgrade is its own Redis-client/strict-arguments migration: `ExportJob.perform_async(..., { format: "markdown" })` uses symbol keys, and `User#request_digest` relies on Redis 4 `sadd` boolean semantics. Validate and prepare string-key options/explicit boolean set APIs before such an upgrade; do not conflate them with Rails 8.1.

`Citation#request_enrichment` and `Note#schedule_reminder` enqueue under row locks and depend on enqueue failure rolling back database state. The 7.2 release notes describe deferral, but **8.1's class default is `enqueue_after_transaction_commit = false`**; do not assume every Rails 8.1 job defers. Keep/explicitly choose false on the target if retaining this contract. That setter is not a 7.0 preparation API. If adopting deferral, redesign failure handling: after-commit Redis failure cannot roll back pending citation/reminder state. Validate Redis refusal and fast worker/transaction overlap for both behaviors. Native ExportJob is outside Active Job and is already enqueued after Export creation commits.

## Delivery and rollback sequence

1. Establish isolated baseline and inventory real stored tag JSON, preference YAML, rich HTML/attachment identifiers and existing Redis job payload types. Do not inspect secrets or log personal data. Record deployed PostgreSQL/Redis versions, cache configuration, shared Disk volume arrangement, secret-key provenance and worker topology; repository config does not establish production reality.
2. Release 7.0-compatible preparations listed above first (including UTC mailer normalization and string digest completion). Keyword serialize and polynomial retry symbol changes belong at 7.1, not prematurely on 7.0. Preserve tables, enum integers, serialized formats, job class names, GlobalIDs, blob keys and key material.
3. Rehearse 7.0 latest patch → 7.1 latest patch → 7.2 latest patch → 8.0 latest patch → exactly 8.1.0, resolving and testing each. Review `app:update` diffs manually; preserve environment/config behavior rather than overwrite files. Keep load_defaults 7.0 throughout. Expose deprecation warnings in rehearsal (production currently disables them). Target 8.1.0 specifically; assess current security patch policy separately before deploying an old initial release.
4. Before mixed web/worker rollout, run payload compatibility checks both directions. Prefer consumers first, then producers; if any new payload is unreadable by rollback consumers, pause producers and drain/segregate queues rather than letting old workers consume it. Include Sidekiq scheduled, retry and dead sets, Active Storage analysis/purge jobs and long-lived reminder jobs—not just the ready queue. Do not indiscriminately flush Redis: digest deduplication reservations live there too. Keep reminder job IDs intact so replacement suppression still works.
5. Back up isolated rehearsal data and production data through the normal approved operational process; no destructive schema change is indicated by these findings. Keep a rollback-compatible release with the preparations. Before rollback, stop incompatible producers, deal with newer payloads and invalidate only disposable incompatible cache entries. Restore key material, not regenerated secrets. In development/test preserve `tmp/development_secret.txt` as `tmp/local_secret.txt` when moving to 7.1 to retain sessions and attachment signatures. Do not rotate production secret_key_base.
6. Adopt defaults individually only after the target framework release is stable and rollback compatibility is explicitly reviewed. Existing data should not need bulk conversion for this plan. Rich-text rewrites and format changes require their own backup/rollback decision.

## Proposed verification and evidence retention

No experiments were run in this assessment, so there is no resolved target lockfile, runtime output, test log or claimed passing check.

For a future rehearsal, a copied checkout is insufficient isolation. Use a fresh PostgreSQL cluster/socket or dedicated database role restricted to variant-specific databases (including Rails parallel-test databases); a dedicated Redis process/port per variant; variant-specific Disk roots, mail directories, tmp/cache, logs and assets. Clear inherited DATABASE_URL/REDIS_URL/service settings and assert resolved database names, Redis endpoint, storage paths and delivery method before any test or job. Use fake citation HTTP service and file/test mail delivery only.

For each variant retain: exact command/environment overrides with secrets redacted; source commit and patch; Ruby/Bundler versions; full Gemfile.lock; effective load_defaults, sanitizer, cache/message format, queue adapter and enqueue policy; database/Redis versions and isolation endpoints; stdout/stderr, exit status, Rails logs and worker logs. Run `bundle check`, `bin/rails zeitwerk:check`, `bin/rails test`, `bin/rails test:system` with an available browser/display, production-mode boot and asset precompile, then real Sidekiq JSON enqueue/execute and the discriminating probes above. Keep each result attributable to its variant; passing the current suite does not establish mixed-version or stored-format safety.

Remaining questions: actual deployment service versions/topology and key provenance; real preference types and queued payload inventory; minimal resolvable 8.1.0 dependency graph; vendored Trix interoperability; actual production cache behavior; desired DST preview presentation. These require rehearsal/operational evidence, not inference from tests.
