# Margin Notes: Rails 7.0.8.7 → 8.1.0 upgrade assessment

**Decision: feasible, but not a Gemfile-only upgrade. Do not deploy the unchanged application on 8.1.0.** Make a compatibility release first, keep `config.load_defaults 7.0` for the framework upgrade, and adopt newer defaults separately. Several changes apply regardless of `load_defaults`.

## Evidence and limits

- Inspected the actual application, configuration, schema, migrations, locked dependencies, and relevant request/model tests at [application revision ab732f5](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7).

Links below are pinned to tags, not moving branches. The public `/v8.1/` guide currently identifies itself as 8.1.4; target-specific conclusions instead use the v8.1.0 tag.
- This is a **source-based assessment**. No application boot, bundle resolution/install, test suite, browser check, database query, Redis operation, or worker experiment was run. Failures described below are predictions grounded in inspected code, not claimed test results. Existing tests cited below were read, not executed.
- Application files and lockfile were not changed. Only this report, a source manifest, and the repository-local `/.amp/in/` ignore rule were added. Existing untracked `.amp/` content was left alone.

## 1. Runtime and dependencies

The application pins Ruby **3.3.6**, Rails **7.0.8.7**, pg **1.6.0**, Sidekiq **6.5.12**, redis-rb **4.8.1**, Puma **5.6.9** via `~> 5.0`, concurrent-ruby **1.3.4**, and Minitest **5.27.0** via `~> 5.25`. Rails 8.1.0 requires Ruby ≥ 3.2: **no Ruby upgrade is required for this target**.

Do not assert that Rails 8.1 requires Rack 3: its Action Pack gemspec permits Rack ≥ 2.2.4; Railties permits rackup ≥ 1.0.0 and Action Pack permits rack-session ≥ 1.0.1. Sidekiq 6.5.12 restricts Rack to 2.x. A Rack-2-compatible resolution is not ruled out by these constraints, but **the complete resolution and runtime compatibility remain unverified**. Keep unrelated pins initially and inspect the candidate lockfile, including rackup/rack-session, rather than forcing a broad dependency update.

The built-in Sidekiq adapter **still exists in 8.1.0**; it warns that it will be removed in 8.2 and recommends Sidekiq ≥ 7.3.3. Moving Sidekiq is a separate, recommended follow-up—not a demonstrated prerequisite for this exact Rails target. Such a move must assess `User#request_digest`'s Redis `sadd` truthiness/error handling, `Notebook#request_export`'s symbol-key options and `Redis::BaseError` rescue, native job JSON strictness, the Redis server version, and old adapter wrapper names in queues. Do not combine that migration silently with Rails.

**Validation gate:** in an isolated copy resolve exactly Rails 8.1.0, record `Gemfile.lock`, Ruby/Bundler versions and `bundle list`, then boot both Puma and a real Sidekiq process. Exercise a native export and each Active Job type, including a scheduled job and retry. `bundle check` alone does not establish this.

### B. CSV import atomicity and representations

**Atomicity — highest data-integrity priority.** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) returns out of a transaction when a later note fails validation. Rails 7.0 rolls that transaction back; 7.2+ commits on a non-local return. The application can report failure while retaining the import, earlier notes, citations and rich-text rows. Keeping 7.0 defaults does not prevent it in 8.1.

Replace the early return with explicit rollback and return a false result outside the transaction. For example, have the transaction end in `true`, raise `ActiveRecord::Rollback` unless every row saves, and convert the transaction's nil rollback result to false. Preserve the failed row's errors for preview rendering. This works on **7.0 and 8.1**. Do not merely prevalidate: save-time failures still need rollback.

**Validation:** existing `imports_controller_test` already has a valid first row followed by an invalid second row and checks all four record counts. Run it with real commits as well as transactional tests; additionally force a late save failure after a valid preview and verify zero persisted batch records. Check the success receipt and unchanged failed-row errors. Any partially committed imports created by an accidental bad deployment require reconciliation; rolling code back does not remove them.

Two more changes affect the same workflow:

- [Import#receipt](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) uses `citation[:id]`, but citations have a string primary key named `doi` and no `id` column. Rails 7.2 removes `read_attribute(:id)`'s custom-primary-key remapping. Use `citation&.doi` (or the semantic `id` reader); `doi` is clearest and works on 7.0. Validate a receipt containing two different DOI values and a row with none. Do not rename the primary key or migrate data.
- [Preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L25-L48) calls `@import.annotations.stringify_keys` then indexes with integer `row.line`. In 8.0, `HashWithIndifferentAccess#stringify_keys` stringifies integer keys too; annotations disappear. Remove the unnecessary `stringify_keys` and keep integer lookups, or render `row.annotation` directly. Both work on 7.0. Validate two distinct annotations with a blank line and quoted multiline body so actual source-line keys differ; retain literal escaping of `<b>` and `&`. Existing import tests cover this distinction.

Sources: [7.0 transaction implementation](https://github.com/rails/rails/blob/v7.0.8.7/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb), [7.2 transaction implementation](https://github.com/rails/rails/blob/v7.2.0/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb), [8.1 attribute reader](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb), [8.0 Active Support changelog](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md).

### E. Reminder scheduling and DST

[Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L56-L68) supplies an integer to `wait_until`. Numeric `scheduled_at` support is removed in 7.2; 8.1 serializes it with `.utc.iso8601`. Use `Time.at(reminder_epoch).utc` at the enqueue boundary. **Works on 7.0** and keeps the database epoch unchanged.

[Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L45) calls `to_time + 86_400`. In 8.1 `TimeWithZone#to_time` unconditionally retains the named zone, not just a fixed offset—even with old defaults. The elapsed instant remains 24 hours later, but the displayed wall time changes across DST. Make the intended behavior explicit:

- Recommended deliberate UX correction: `(reminder_at + 86_400)` retains the reader's zone on both versions. In Eastern Time, Oct 31 2026 09:00 −04:00 becomes Nov 1 08:00 −05:00, not 09:00 −04:00. This changes the currently documented preview and its test; approve it as behavior adoption, not an accidental test adjustment.
- For strict compatibility instead, explicitly construct a fixed-offset Time before addition (`Time.at(reminder_epoch).getlocal(reminder_at.utc_offset) + 86_400`). This also works on 7.0 and preserves the existing preview.

**Validation:** schedule the exact imported epoch (1,793,451,617), assert Redis scheduled score and stored job ID, postpone by exactly 86,400 seconds, verify the superseded job sends nothing and the replacement sends once. Check both fall-back and spring-forward previews, a past-due job, deleted note and enqueue failure preserving prior state. Existing tests exercise fall-back but do not inspect real Sidekiq scheduling or the failure boundary.

Old 7.0 payloads omit the newer `scheduled_at` field; Sidekiq's schedule score still controls delivery. New workers tolerate a missing field in source. Reverse compatibility, including retried/new payloads, must be executed before claiming rollback support; do not rewrite epoch columns or drop scheduled reminders.

Sources: [8.1 job core](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/core.rb), [7.0 job core](https://github.com/rails/rails/blob/v7.0.8.7/activejob/lib/active_job/core.rb), [8.1 TimeWithZone](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb).

### F. Digest arguments: wire format and calendar-day semantics

[User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L56) reserves a **UTC date** in Redis, but passes a reader-zone TimeWithZone and BigDecimal to [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb), then [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L10) chooses `requested_at.to_date` and `requested_at.all_day`.

1. Rails 7.2 preserves a TimeWithZone argument's named zone. New jobs would select the reader's **local day**, while the Redis reservation remains UTC. Old serialized jobs lack the zone field and retain the old fallback. Therefore, unmodified old/new payloads can generate different digest content on the same upgraded worker.
2. BigDecimal gains a tagged Active Job serializer in 7.1 and that representation becomes mandatory in 7.2. Rails 7.0 has no `ActiveJob::Serializers::BigDecimalSerializer`; new payloads cannot simply be fed to old workers. Old Sidekiq JSON payloads instead carry a decimal string. The existing test adapter does not reproduce that JSON conversion.

**Recommended 7.0-compatible preparation:** make UTC semantics explicit in the mailer (`requested_at = requested_at.utc` before both date and range), enqueue UTC Time, and send `reading_completion.to_s("F")`. Keep the same job class and argument count. This fixes the source of the ambiguity rather than teaching business logic about framework versions. The mailer continues to accept old decimal strings and BigDecimals; explicit UTC normalization also handles already-queued zone-bearing payloads on new workers. A conversion in `perform` alone cannot rescue an unknown serializer error that occurs before `perform` on 7.0.

**Validation:** use 2026-10-05 03:30 UTC (Oct 4 23:30 Eastern), notes on both sides of UTC midnight and a nontrivial completion such as 2/3 → 66.67%. Pass actual JSON payloads through old→new and new→old workers; assert subject date, selected notes, percentage, and duplicate-reservation behavior. Include old no-zone TimeWithZone/string-decimal payloads and new zone-bearing/tagged-decimal payloads. The existing digest test catches the local-day change but does not establish wire compatibility.

**Rollout:** stop old producers or deploy the primitive-argument preparation to every producer first. Drain existing digest retries/scheduled work or route incompatible payloads only to new workers; rollback must not let unmodified 7.0 workers consume tagged decimals. Do not delete Redis digest reservations to make migration easier: doing so permits duplicate requests. Preserve their two-day TTL and UTC keys. Real mail delivery is not exactly-once today; the upgrade must not silently amplify duplicates.

Sources: [7.2 Active Job changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [8.1 time-zone serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb), [8.1 decimal serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb), [7.0 time-zone serializer](https://github.com/rails/rails/blob/v7.0.8.7/activejob/lib/active_job/serializers/time_with_zone_serializer.rb).

## 4. Stored content, signing and cache rollout

### Keep keys and wire formats stable first

Sessions store the user ID; Action Text stores signed attachable references; Active Storage serves signed blob URLs. The 7.1 guide changes the development/test key file from `tmp/development_secret.txt` to `tmp/local_secret.txt`. Preserve the old key when continuing a local environment with old attachments/cookies; never print or copy a real key into evidence. Confirm the production `secret_key_base` source and preserve its value across web and workers. Credentials were not decrypted for this assessment.

Keep the 7.0 message writer format/legacy metadata until all readers support new messages. When adopting 7.1 defaults, evaluate `active_support.message_serializer = :json_allow_marshal` and `use_message_serializer_for_metadata = true` separately: newer readers accepting old payloads does **not** establish old readers accepting new payloads. Either retain legacy writers through the rollback window or add proven reader compatibility first. Do not assume JSON session payloads alone prove blob/SGID compatibility. Rails 8.1's new generic Active Record verifier has a legacy compatibility setting, but Blob overrides its verifier with Active Storage's verifier; changing the generic setting alone is not a blanket attachment fix.

**Required two-way validation:** with a fixed synthetic key, create an old session cookie, signed blob/download URL, Disk URL and embedded Action Text SGID; verify on the new version. Create their new counterparts and verify on the rollback version. Test expiration/purpose enforcement too. Keep old assets available during rolling deploys; avoid resaving all Action Text records as a migration. Existing fixtures mint no historical cross-version signing evidence.

### Cache format

Production leaves the Rails default FileStore in place (`tmp/cache`); development uses MemoryStore only when caching is toggled; tests default to NullStore. Redis is for queues/digest reservations, not the configured fragment cache. Rails 8.1 supports cache formats 7.0 and 7.1. Keep **7.0 format** initially; enable 7.1 only after incompatible readers are gone, or use versioned cache namespaces/directories and cold caches. Whether deploys share `tmp/cache` is unverified. Validate real serialized FileStore entries across versions (MemoryStore tests do not prove disk-format compatibility). On rollback, switch back to the old namespace or invalidate only disposable cache entries—never Redis queues/reservations or blob files.

### Editor/assets

The layout explicitly loads vendored **Trix 1.3.5**; upgrading the Rails gem does not replace that script with Trix 2. Rails 8.1 Action Text declares Trix `^2.0.0` in its package metadata, while this app uses no npm build and obtains Action Text JS/CSS from gems. Treat retaining Trix 1.3.5 as an **unverified integration**, not automatically supported or automatically broken. Prefer evaluating the supported Trix 2 pairing in a separate browser-reviewed change; do not load both editors or overwrite layout/importmap blindly with `app:update`.

Validate production asset precompilation and actual create/edit/reopen workflows: persisted links, an image attachment, file attachment, custom details and unrelated tag edits, Turbo navigation and direct upload completion. Trix already flattens details on save today; distinguish that known behavior from a regression. Stored body HTML and blob data need backup/round-trip validation before changing editors. No actual browser workflow tests were found in `test/system`; the system-test base alone is not coverage.

## 5. Enqueue transaction policy: do not change accidentally

[Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L56-L68) and [Citation#request_enrichment](file:///home/user/workspace/repo/app/models/citation.rb#L14-L23) enqueue under row locks. They rely on immediate enqueue failure to roll back reminder/pending state. Rails 7.2 introduced configurable deferred enqueueing, but **8.1's actual base default is false**; its configuration defaults do not automatically force this app to defer. The release-note headline alone is insufficient to conclude otherwise.

Preserve immediate enqueueing for the framework upgrade. If setting it explicitly on 8.1 jobs, use `self.enqueue_after_transaction_commit = false`, not obsolete `:never`/`:always`/`:default` symbols or the removed global config. That setter is not a 7.0 preparatory API. The 7.2 API uses symbols, so treat intermediate-stage configuration separately.

Deferred enqueueing is a separate design decision: Redis can fail after the database commit, leaving a pending citation or reminder pointing at no job, and transactional fixtures may hide the callback. Native `ExportJob.perform_async` is not governed by Active Job's flag. Validate queue failures with committed transactions in separate processes, a fast worker that loads before commit, rollback, and process exit after commit. Do not claim deferred enqueueing solves database/Redis atomicity; a stronger delivery guarantee would need separately scoped design.

Sources: [8.1 enqueuing](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/enqueuing.rb), [8.1 deferred enqueue implementation](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/enqueue_after_transaction_commit.rb), [7.2 deferred enqueue implementation](https://github.com/rails/rails/blob/v7.2.0/activejob/lib/active_job/enqueue_after_transaction_commit.rb).

## 6. Execution sequence and release gates

All steps below are **proposed**, not executed.

1. **Build a disposable baseline.** Copy tracked application files, excluding credentials/keys, storage, logs, cache, bundle configuration and existing temporary data. Provision a unique PostgreSQL database/role or isolated cluster, a dedicated Redis instance (not just a copied checkout), unique Disk roots, FileStore directory, logs, and a local-only mail sink/provider. Override database/Redis URLs for every subprocess, including the citation runner; ensure parallel-test database suffixes remain disposable. Rails 8.1 changes parallel suffixes to `_N`, so reserve both old and new naming schemes. Confirm effective resource paths without revealing credentials before any `db:prepare` or tests.
2. **Run baseline and keep reproducible evidence.** Record command, code diff/commit, Ruby/Bundler versions, exact lockfile, effective defaults, service versions, isolated resource identifiers, stdout/stderr, Rails/worker/provider logs, and exit codes. Use synthetic historical JSON/YAML, rich HTML, attachments and queue payloads. Production data/content distribution has not been inspected.
3. **Deploy a 7.0-compatible preparation only after its validation.** Explicit import rollback; enum/alias/routes fixes; `fragments.join`; receipt and annotation fixes; configuration migration; Time scheduling; explicit digest UTC/string arguments. Prepare readonly form/cache/date handling if desired, but keep behavior changes distinct. Do not prematurely apply `coder:` syntax, `:polynomially_longer`, `show_exceptions = :none`, or new enqueue-policy settings on 7.0.
4. **Use minor-version checkpoints.** Follow the upstream recommendation to resolve/test current-line patches, then 7.1, 7.2, 8.0 and exactly 8.1.0, using selected patch versions at intermediate stages and recording each resolution. On 7.1 change serializer syntax, retry symbol and exception config; fix deprecations before removals. Review `bin/rails app:update` interactively in the disposable copy; do not accept generated replacements wholesale. Keep `load_defaults 7.0`. The downloaded `.0` source tags identify change boundaries, not production patch-version recommendations.
5. **Run the application gates.** `bundle check`; `RAILS_ENV=test bin/rails zeitwerk:check`; full `bin/rails test`; targeted import/export/citation/digest/reminder/report checks described above; production-like eager boot and `assets:precompile` with synthetic secrets; actual Puma/Sidekiq and browser workflows. `bin/rails test:system` with no test cases is not browser evidence. Test schema loading and migrations on fresh disposable databases; Rails 8.0's fresh `db:migrate` can load schema first, so it does not prove historical data migrations replay correctly. Do not reset a shared database. Keep 7.0 migration version tags; 8.1 alphabetizes schema dump columns, which is not a data migration requirement.
6. **Exercise the mixed-version matrix before deployment.** Run old producer→new consumer, new producer→old consumer, old/new web sessions/signatures, old/new database coders and cache formats. Preserve Active Job and native Sidekiq class names, argument counts, GlobalIDs, export IDs, reminder job IDs, scheduled scores and retry counts. Include Active Storage analysis/purge jobs, not only app jobs. Inventory ready, scheduled, retry and dead queues; an empty ready queue is not a drained system.
7. **Stage rollout/rollback.** Deploy compatible readers/preparatory producers first. Keep old wire writers until all relevant readers are upgraded; otherwise quiesce producers and isolate incompatible queues for new workers. Reminders may be scheduled far ahead, so waiting for all queues to empty is not a sufficient plan. Retain a tested rollback build, database/blob backups, stable key material, old asset digests and old cache namespace. Rollback must stop new producers, handle new-format queued work without deleting it, and preserve reservations and job identities. A code rollback cannot undo partial CSV commits or editor rewrites.
8. **Adopt defaults individually after stability.** First resolve YAML, readonly, cache expiry and date-decoding prerequisites; then validate sanitizer, signing/cache formats, HTTP freshness and DST presentation. Only move `load_defaults` once each enabled behavior is understood. Update architecture/testing guidance to describe the delivered contracts rather than suppressing failing assertions.
