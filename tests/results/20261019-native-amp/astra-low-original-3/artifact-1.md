# Margin Notes: Rails 7.0.8.7 → 8.1.0

## Recommendation and evidence boundary

Do not treat this as a Gemfile-only upgrade. First deploy behavior-preserving preparation on 7.0, then validate 7.1 → 7.2 → 8.0 → 8.1, initially retaining `config.load_defaults 7.0`. Adopt newer defaults separately. The requested target is exactly 8.1.0; choosing a newer security patch requires a separate decision.

**Evidence:** read application models/controllers/views/configuration, schema, lockfile, testing guidance and relevant tests; compared upstream 7.0.8.7 and 8.1.0 tagged source plus intervening release notes. No application was booted, no dependency resolution or tests were run, and no database/Redis/cache/storage was accessed. Findings below are source-based predictions, not observed test failures. Runtime compatibility and deployed resource settings remain unverified. Application files were not modified.

Ruby is already 3.3.6; Rails 8.1 requires ≥3.2, so a Ruby upgrade is not required. Keep pg 1.6.0, Sprockets/importmaps/Turbo, Sidekiq and the existing Disk storage unless dependency resolution or verification establishes a reason to change them. Rails 8 defaults for newly generated apps do not require migrating this existing app to Propshaft or Solid Queue/Cache/Cable.

## Queued data and mixed-version rollout

**Digest semantics need deliberate normalization.** `User#request_digest` sends a zoned time and BigDecimal to `DigestJob`; `DigestMailer` uses `requested_at.to_date/all_day` and `BigDecimal(completion)`. Old Active Job loses the named zone on deserialization; target preserves it. A request at 2026-10-04 23:30 New York currently covers October 5 UTC, but new serialization can cover October 4 local time. This change does not depend on `load_defaults`.

Prepare on 7.0 by explicitly normalizing request time to UTC at the mailer/consumer boundary (so old and already-new payloads converge), and send completion as `reading_completion.to_s`. Both work on 7.0. BigDecimal parsing already accepts a BigDecimal as well as its decimal string, so the issue is the **wire format**, not necessarily a mailer crash. Target emits a named `BigDecimalSerializer`; the old release lacks that serializer and cannot consume such new payloads. Explicit decimal-string producers prevent creating incompatible work. They do not repair previously emitted new-format jobs.

Validate all four producer/consumer pairs through a real JSON/Sidekiq boundary with isolated Redis. Use non-UTC near-midnight requests and notes on both sides of UTC/local-day boundaries; verify subject, included notes and percentage. The current Active Job test adapter does not perform Sidekiq's JSON round trip, so its green result is insufficient.

For the cutover, inventory immediate, scheduled, retry and dead work, including long-lived NoteReminderJob, CitationEnrichmentJob, DigestJob, native ExportJob and Active Storage jobs. Quiesce producers and drain or explicitly account for old work before replacing workers; test actual serialized envelopes in both directions. Do not assume draining the immediate queue drains scheduled/retry sets. Keep job class names, GlobalIDs, IDs and export status mappings stable. Re-enqueueing reminders must preserve or atomically replace `reminder_job_id`, otherwise the consumer intentionally discards them. Retries can duplicate digest email; do not blindly replay.

Rails 8.1's built-in Sidekiq adapter still exists but is deprecated for removal in 8.2 (upstream recommends Sidekiq ≥7.3.3). The current Sidekiq 6.5.12/Redis 4.8.1 lock is **not proven compatible or impossible**: Rails 8.1 Action Pack permits Rack ≥2.2.4, not only Rack 3. Do not claim a Rack conflict without resolving the entire graph. Resolve conservatively in the disposable copy and exercise web/worker boot. A separate Sidekiq major upgrade entails Redis API changes, reservation return values, native export argument JSON safety, exception classes and job-wrapper compatibility; avoid folding it silently into this Rails task.

**Transaction enqueue policy:** Citation#request_enrichment and Note#schedule_reminder explicitly rely on queue failure rolling back state under a row lock. Rails 7.2 introduced after-commit enqueue behavior; target 8.1 has per-job boolean `enqueue_after_transaction_commit`, default false. Inspect the chosen intermediate release and adapter, rather than assuming release-note defaults remain unchanged. Preserve immediate enqueue for these jobs during the migration; deferring means failure occurs after DB commit. The boolean API is not present on 7.0; use the version-appropriate setting only after upgrading. Test refused enqueue plus real competing worker execution and DB rollback, not only test-adapter serialization. Native ExportJob is outside Active Job's policy.

## Optional new-default adoption and additional behavior risks

Keep defaults at 7.0 first; this does not prevent the required removals above.

* **Notebook YAML:** 7.1 defaults remove the implicit column serializer, making `Notebook.serialize :preferences` need `coder: YAML`. Stage that syntax on 7.1, not 7.0. Keep existing YAML format; do not switch to JSON without a separately planned data migration. Inventory stored YAML types safely (no unsafe load), including null/empty and export headings. Verify old/new reads and writes on sanitized representative rows.
* **Readonly slug:** 7.1 defaults raise on assignment. `NotebooksController` permits slug and the form resubmits it unchanged, so even ordinary edits can fail. Remove slug from writable parameters/form submission; readonly model protection remains. This preparation works on 7.0. Validate unchanged and forged slug submissions, persisted slug stability and successful name/heading updates.
* **Export caching:** `_export.html.erb` computes a negative TTL after expiration. New cache code rejects/drops invalid TTL; with 7.1 defaults it raises, while non-raising mode can lose the TTL. Render expired availability outside the cache and cache only future-expiring fragments. Works on 7.0. Test caching enabled immediately before, exactly at and after expiration, including an already-warm entry and another reader. Existing null-store tests cannot cover this. The download controller's ownership/expiry checks must still precede conditional responses.
* **PostgreSQL date decoding:** 7.2 defaults enable native Date decoding. `Notebook#daily_note_counts` currently calls `Date.iso8601(day)` on raw select rows and would receive a Date instead of text. Normalize explicitly (`day` if Date, otherwise parse), compatible with 7.0. Test both configurations with UTC-midnight boundary records and stable counts/order.
* **HTTP freshness:** 8.0 defaults enable strict freshness. `ExportDownloadsController#stale?` supplies both ETag and last-modified; when both request headers are present, precedence changes. Test matching ETag + stale date, nonmatching ETag + fresh date, and unauthorized/expired download with matching headers. Adopt intentionally; no preparatory controller replacement required.
* **Sanitization defaults:** 7.1 selects HTML5 where supported. Review malformed stored rich text and attachment rendering under both vendors; fix the allowlist boot issue separately. Existing editor flattening of details/summary is documented current behavior, not evidence of a Rails regression.
* **Cache/message formats:** 7.1 defaults change cache format and signed/encrypted message serializer/metadata. Keep old writer settings until rollback closes or use separate cache namespaces with cold-cache rollout. Session cookies, blob signed IDs and stored Action Text attachment SGIDs require old→new and new→old checks with the same secret. A newer reader accepting old bytes does not establish old-reader compatibility. Retain the production secret-key base; deployment sourcing is unverified. Preserve the development/test secret when changing `tmp/development_secret.txt` to `tmp/local_secret.txt` if existing local signed data matters.

No model uses Active Record `encrypts`; its encryption migration is not currently applicable. Azure storage is commented out; actual configured storage is Disk. Schema-column alphabetization in 8.1 is expected dump churn, not a data migration. Keep historical migration versions; independently test both schema load and migration-from-empty, since historical migrations reference application behavior.

## Execution and release gates

1. Make an isolated copy without real credentials or production data. Use dedicated PostgreSQL databases/role (including all parallel worker databases), a dedicated Redis instance, private cache directory/namespace, Disk storage roots, log/temporary paths, test mail delivery and loopback citation provider. Remove inherited service URLs and verify effective configuration before boot. A copy alone is not isolation.
2. Record each variant's Gemfile/lockfile, Ruby/Bundler versions, defaults and settings, sanitized command/environment, stdout/stderr, Rails logs and resource addresses. Resolve dependencies and run baseline checks there; no experiments have been executed for this report.
3. Apply current-compatible preparation; verify on 7.0. Then resolve and validate each minor step, fixing warnings before removals. Review `app:update` diffs rather than overwriting configuration. Keep new defaults separate.
4. Run `bundle check`, isolated `bin/rails db:prepare`, `bin/rails zeitwerk:check`, `bin/rails test`, `bin/rails test:system` (Chrome/display required), production-like eager boot and `assets:precompile`. Exercise login/session continuity, Trix/direct upload and old attachments, imports/receipts, exports/download/cache expiry, worker retries/reminders/digests and citation subprocess credentials. Retain commands and results per variant; investigate failures rather than relaxing tests to fit changed behavior.
5. Before rollout, back up DB and storage and inventory queued work/cache topology/secret sourcing. Close the producer-consumer matrix before mixed deployment. Keep old/new assets during overlap. Rollback means restoring compatible writers and consumers, not merely reverting Gemfile; isolate or drain incompatible new jobs, invalidate versioned cache as planned, and retain old secrets and DB formats. No mandatory persisted-data conversion has been established by this source review.

Open gates: actual resolved target dependencies and Rack/Puma/Sidekiq startup; deployed PostgreSQL/Redis versions and service topology; representative stored YAML/rich-text/signed data; complete queue-envelope compatibility; all runtime and browser validation above.
