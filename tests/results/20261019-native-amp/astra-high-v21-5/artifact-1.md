## 2. High-risk changes

### H1. A rejected import can now commit a partial batch

- **Before — Code:** Rails 7.0 rolls back a written transaction exited by a non-local `return`. `Import#apply` saves the import, saves rows in order, and executes `return false` when a row fails validation ([import.rb:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60)).
- **After — History + Code:** The rollback-on-return behavior was removed in 7.2; 8.1 commits a normal `return`/`break`/`throw` exit. Keeping 7.0 defaults does **not** restore it. [Changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L371-L377); [target transaction implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L649-L676).
- **Inference:** A valid first row followed by an invalid row can leave the import, earlier notes, rich text and citations committed while the response reports failure. Retrying can duplicate earlier rows. Use an explicit rollback/error strategy that preserves the intended validation response. The existing [invalid-batch test](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L73) names precisely this case; it was not run.

### H2. Import receipts silently lose their DOI values

- **Before — Code:** `citation[:id]` resolves to the model’s custom primary key, `doi`.
- **After — History + Code:** Since 7.2, `read_attribute(:id)`/`[:id]` reads the actual `id` attribute, not a differently named primary key. Here that yields `nil`; it does not raise a missing-column error. [Removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L421-L427); [read implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb#L29-L35).
- **Use / consequence — Code + Inference:** [Import#receipt:63–68](file:///home/user/workspace/repo/app/models/import.rb#L63-L68) produces successful CSV downloads with blank DOI fields. Read `citation.id` or explicitly `citation.doi`; the [receipt assertion](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) checks this contract.

### H3. Import previews silently omit annotations

- **Before — Code:** `HashWithIndifferentAccess#stringify_keys` effectively duplicated this hash, leaving integer keys unchanged.
- **After — History + Code:** Rails 8.0 stringifies all keys, including integers. Indifferent access equates strings with symbols, **not integers**. [Changelog/example](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md#L30-L49).
- **Use / consequence — Code + Inference:** [Import#annotations](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) writes integer line keys; [preview:22,42–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) stringifies them and still looks up an integer. Annotations disappear from the preview without an exception, although they remain in submitted CSV and saved notes. Keep key normalization consistent; include multiline-row source numbers when reviewing.

### H4. Digest jobs change their calendar-day interpretation

- **Before — Code:** The time argument records an offset, but Rails 7.0 deserializes it in the worker/job time zone, UTC here.
- **After — History + Code:** The serializer carries the named time zone and restores it. Old payloads without that field retain the fallback behavior. [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L47-L49) (also backported to 7.1); [serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb).
- **Use / consequence — Code + Inference:** [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) reserves a **UTC date** but passes the reader’s local time. [DigestMailer:7–12](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L12) uses that time’s `to_date` and `all_day`. A request at 2026-10-05 03:30 UTC / October 4 23:30 Eastern now covers October 4’s **Eastern** day, not October 5’s UTC day. This changes both the subject and selected notes, and can disagree with the reservation. Decide the intended day explicitly and normalize at the mailer boundary for old and new payloads. [Existing boundary test](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37).

### H5. BigDecimal job arguments are incompatible with old workers

- **Before — History + Code:** Active Job passes BigDecimal as a primitive; Sidekiq’s JSON storage turns it into a string.
- **After — History + Code:** A tagged `ActiveJob::Serializers::BigDecimalSerializer` payload preserves the decimal type. The transitional opt-in introduced in 7.1 is no longer optional in 8.1. Rails 7.0 workers do not have that serializer. [Introduction and rolling-deploy warning](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L157); [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L63-L65); [target implementation](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).
- **Use / consequence — Code + Inference:** [User:41,54–56](file:///home/user/workspace/repo/app/models/user.rb#L41-L56) sends the completion ratio to [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L4-L7). An old worker receiving a new payload fails deserialization; new workers can still receive old string arguments. The mailer’s `BigDecimal(...)` conversion itself accommodates strings and BigDecimals. Plan queue/worker compatibility and rollback, not merely web deployment order.
- **Additional transitive watchpoint — History + Inference:** The resolver also moves the decimal implementation from Ruby’s 3.1.5 to 4.1.3. Division precision/rounding changed ([history](https://github.com/ruby/bigdecimal/blob/v4.1.3/CHANGES.md), [division PR](https://github.com/ruby/bigdecimal/pull/329), [rounding fix](https://github.com/ruby/bigdecimal/pull/330)), and this application divides counts then rounds to four places. No changed four-place result was established for this app; review non-terminating ratios and rounding boundaries rather than assuming either a regression or exact numerical equivalence. The definite high risk here is the queue format.

### H6. Reminder postponement previews change across daylight saving

- **Before — Code:** Under 7.0 defaults, `TimeWithZone#to_time` preserves a fixed UTC offset. Adding 86,400 seconds keeps that offset.
- **After — History + Code:** Rails 8.1 always preserves the named time zone; retaining the old configuration no longer selects fixed-offset conversion. [Changelog](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md#L15-L20); [implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb#L494-L499).
- **Use / consequence — Code + Inference:** [Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L44) feeds the [preview](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20) and postponement epoch. October 31, 2026 09:00 Eastern +86,400 seconds changes its representation from November 1 **09:00 −04:00** to **08:00 −05:00**. The instant stays the same: this is not a one-hour scheduling shift. The preview becomes zone-correct but contradicts the old documented/tested display contract ([test:20–21](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L20-L21)). Confirm elapsed-hours versus same-local-clock requirements.

### H7. Rich-text parsing and plaintext exports change independently of defaults

- **Before — Code:** Action Text parses HTML with Nokogiri HTML4; plaintext conversion includes script/style text and counts whitespace nodes when numbering ordered-list items.
- **After — Code + History:** Its internal document/fragment parser uses HTML5 whenever available, even with 7.0 defaults. This is separate from the **sanitizer vendor**, which remains HTML4 here. Plaintext conversion drops script/style contents and numbers list elements without counting interleaved whitespace. Sources: [HTML5 commit](https://github.com/rails/rails/commit/55bca6b8e85cbe719e748f4cd6acd2a8c2accb14), [script/style commit](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057), [iterative conversion/list fix](https://github.com/rails/rails/pull/55025). The endpoint diff, not just release headings, exposed these changes.
- **Use / consequence — Code + Inference:** [CSV rows accept HTML](file:///home/user/workspace/repo/app/models/import.rb#L100-L106); [export generation converts it to plain text](file:///home/user/workspace/repo/app/models/export.rb#L77-L81); [preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58) does too. Malformed/nested imported HTML can be repaired into a different tree, and saving it can persist different markup. New exports can differ from already-created files: newline-separated `<li>` elements no longer get gaps in their numbering, and script/style text disappears. No database corpus was inspected, so existing affected records are unknown. Review representative imported HTML and editor round trips, not only simple paragraphs.
- **Code + History:** Content attachments also gain generalized HTML support and sanitization of the `content` attribute when rendered for editing ([7.1 change](https://github.com/rails/rails/blob/v7.1.0/actiontext/CHANGELOG.md#L64-L66), [7.2 changes](https://github.com/rails/rails/blob/v7.2.0/actiontext/CHANGELOG.md#L3-L10)). Imported HTML can reach this path; custom attachment markup may render differently. This does not imply ordinary file attachments are newly broken or that unsafe content should be preserved.

### H8. Negative fragment TTLs no longer mean an already-expired entry

- **Before — Code:** A negative `expires_in` produces an immediately expired entry.
- **After — History + Code:** Rails removes a negative `expires_in`; with the retained defaults it reports/logs the error and continues without that per-call expiry. With 7.1+ defaults it raises instead. [Changelog](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md#L861-L869); [target validation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L909-L944).
- **Use / consequence — Code + Inference:** [exports/_export:25–35](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L35) passes `export.expires_at - Time.current` for every completed export, including expired ones. Expired-status fragments can now remain without a TTL and generate warnings, instead of immediately expiring. Do not describe this as an authorization bypass: [downloads check ownership and expiry first](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15). Decide how expired indicators should be cached; separately review raising behavior before changing defaults.

### H9. Local secret-key selection can invalidate sessions and stored attachment signatures

- **Before — Code:** Development/test generate their key in `tmp/development_secret.txt`.
- **After — History + Code:** Rails uses `tmp/local_secret.txt`, and the target also prefers `SECRET_KEY_BASE`/credentials when present locally. [Upgrade guide](https://guides.rubyonrails.org/v8.1/upgrading_ruby_on_rails.html#development-and-test-environments-secret-key-base-file-changed); [8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/railties/CHANGELOG.md#L156-L163).
- **Use / consequence — Code + Inference:** The old filename exists in this workspace; its contents were not read. [Sessions](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L17), [rich text](file:///home/user/workspace/repo/app/models/note.rb#L8), and [Active Storage blobs](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb) depend on derived signatures. Without preserving the effective key, local logins can be lost and existing attachment references can fail verification. Merely copying the file is insufficient if a different ENV/credentials key takes precedence. This is a **local-environment** finding; no production key change was established.

### H10. Test requests stop propagating exceptions under the existing boolean setting

- **Before — Code:** `config.action_dispatch.show_exceptions = false` makes request errors propagate to tests.
- **After — History + Code:** Boolean support was removed in 7.2. In 8.1 only `:none` selects that behavior; `false` falls through to rendering exceptions. [Removal](https://github.com/rails/rails/blob/v7.2.0/actionpack/CHANGELOG.md#L100-L102); [target case statement](https://github.com/rails/rails/blob/v8.1.0/actionpack/lib/action_dispatch/middleware/exception_wrapper.rb#L185-L197).
- **Use / consequence — Code + Inference:** [test.rb:30–31](file:///home/user/workspace/repo/config/environments/test.rb#L30-L31) still sets `false`; authorization tests rely on exceptions, e.g. [imports:98–107](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L98-L107). Those assertions fail, and other unexpected errors may become rendered responses rather than propagate. **High under the silent-behavior rubric, but test-only and mechanically repairable:** use `:none` to preserve the current contract; choose `:rescuable` only if deliberately changing it.

## 3. Medium-risk changes

### M1. Citation-provider settings lose the `Rails.application.secrets` API

- **Before — Code:** [Provider#initialize](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L14) reads the `citation_provider` hash from `config/secrets.yml` via Rails’ secrets loader.
- **After — History + Code:** Deprecated in 7.1, `Rails.application.secrets` was removed in 7.2 ([changelog](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63)).
- **Inference:** Enrichment fails before the HTTP request; the resulting missing-method error is not the provider’s handled `Error`/`Unavailable`, so jobs can retry while the citation stays pending. Decide whether these environment-backed settings belong in `config_for`, direct ENV-backed configuration, or credentials; preserve each environment’s behavior. [Tests also access/mutate the removed API](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L105-L122).

### M2. The built-in Sidekiq adapter is deprecated for removal in Rails 8.2

- **Before — Code:** Rails provides the adapter used by `config.active_job.queue_adapter = :sidekiq`.
- **After — History + Code:** It still exists in 8.1, but warns that it will be removed in 8.2 and directs users to Sidekiq ≥7.3.3 ([changelog](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md#L19-L23), [adapter warning](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb#L33-L38)).
- **Use / consequence — Code + Inference:** [Application config](file:///home/user/workspace/repo/config/application.rb#L22-L24) and [Sidekiq/Redis pins](file:///home/user/workspace/repo/Gemfile#L34-L36) make this an upcoming migration decision, **not an 8.1 resolver conflict**. Upgrading Sidekiq is separate work involving the native export job and direct Redis calls. The locked Sidekiq 6.5.12 source already handles Rails’ new BroadcastLogger API, so that commonly cited logger incompatibility was not found here.

### M3. Newly resolved JSON 3 rejects previously accepted provider responses

- **Before — Code + History:** Ruby’s JSON 2.7.2 accepts duplicate object keys (last wins) and comments. The provider calls `JSON.parse(body)` without options.
- **After — History + Code:** Resolved JSON **3.1.0** rejects duplicate keys and comments by default, rejects additional malformed escape/surrogate cases, and rejects non-ASCII binary strings during generation. [JSON history](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md); parser option handling and defaults were also read in the unpacked release.
- **Use / consequence — Code + Inference:** [Provider:42–52](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) converts parser errors into enrichment failure. A response with two `title` keys previously selected the last one; now it is refused. Decide whether to require strict provider JSON or deliberately permit specific legacy syntax. Actual provider traffic was not inspected, so this is a boundary risk, not a demonstrated production failure. JSON also backs tags/jsonb and Sidekiq payloads, but no app-generated duplicate-key payload was found; do not claim all stored tags or queues become unreadable.
