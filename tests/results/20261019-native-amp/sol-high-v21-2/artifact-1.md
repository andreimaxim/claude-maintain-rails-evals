## High-risk changes

### H1. Returning from the import transaction now commits partial imports

**Before → after — Code + History:** Rails 7.0.8.7 rolls back a written transaction exited by a nonlocal `return`. Rails 7.1 introduced a choice; 7.2 removed the rollback behavior, and 8.0 removed the compatibility setting. Rails 8.1 commits on normal nonlocal exit. See [removal commit](https://github.com/rails/rails/commit/eccc6061f4) and [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L371-L377).

**Application — Code:** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import, saves each note, and executes `return false unless row.note.save` **inside** the transaction. [ImportsController#create](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L9-L19) treats false as failure.

**What could go wrong — Inference:** A valid first row followed by an invalid row leaves the import, earlier notes, rich text, and newly created citations committed while showing a failure page. The [existing invalid-batch test](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L72) targets this exact boundary. Use an explicit rollback/failure contract rather than relying on `return`; retaining 7.0 defaults does not restore rollback.

### H2. CSV receipts silently lose their DOI values

**Before → after — Code + History:** `read_attribute(:id)` and therefore `record[:id]` used to map to a custom primary key. In 7.2 that fallback was removed; it reads the physical `id` attribute, which is absent here. The `record.id` method still represents the primary key. See [removal and upstream nil expectation](https://github.com/rails/rails/commit/39997a0f049dfb3d94b28d1cb131b9136a1b7b0a).

**Application — Code:** [Import#receipt](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) writes `citation[:id]` to its DOI column, but [citations use `doi`](file:///home/user/workspace/repo/db/schema.rb#L55-L62).

**What could go wrong — Inference:** A successful import's downloaded receipt contains blank DOI cells without reporting an error. The [CSV assertion](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) should catch it. Read `citation.id` or the explicit `citation.doi` instead.

### H3. Import previews silently omit annotations

**Before → after — Code + History:** `HashWithIndifferentAccess#stringify_keys` used to just duplicate the hash, leaving integer keys intact. Rails 8.0 fixes it to stringify **all** keys. Integer lookup does not gain string/symbol indifference. See [fix and before/after example](https://github.com/rails/rails/commit/e8574542f88695329e7324f864b9048b0ba0da1b).

**Application — Code:** [Import#annotations](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) keys annotations by integer source line. The [preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys`, then looks up the integer `row.line`.

**What could go wrong — Inference:** Keys become `"2"`, `"4"`, etc., so the conditional is false and annotations disappear from the preview. Import persistence still uses the original row and keeps annotations: this is a misleading review screen, not proven database loss. Use consistent key types. The [multi-line CSV preview case](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L8-L25) already distinguishes the behavior.

### H4. Digest email switches from the reservation's UTC day to the reader's local day

**Before → after — Code + History:** Active Job 7.0 serializes TimeWithZone with its offset but deserializes into the job's current zone. Since 7.2, it also stores the zone identifier and restores that zone. See [implementation](https://github.com/rails/rails/commit/18098ccc4c) and [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L47-L49).

**Application — Code:** [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) reserves `requested_at.utc.to_date`, but sends `requested_at` in the reader's zone. [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L12) uses that argument's `to_date` and `all_day` for the subject and query.

**What could go wrong — Inference:** The existing case at **2026-10-05 03:30 UTC / October 4 23:30 Eastern** changes from an October 5 UTC digest to an October 4 local-day digest. That disagrees with the UTC reservation and can select a different set of notes. Already queued 7.0 payloads lack `time_zone` and retain the old fallback, so old and new payloads can produce different semantics on the same new worker. See [existing expectation](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37). Decide explicitly whether digests follow UTC or the reader's calendar.

### H5. BigDecimal job arguments change wire format during deployment

**Before → after — Code + History:** In 7.0, JSON-backed job arguments turn a BigDecimal into a decimal string. 7.1 added `BigDecimalSerializer` behind a rollout switch; 7.2 removed primitive serialization and 8.0 removed the switch. Rails 8.1 writes a tagged serializer object and restores a BigDecimal. See [serializer introduction](https://github.com/rails/rails/commit/bc1f323338), [7.1 rollout warning](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L157), and [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L59-L65).

**Application — Code:** [User#reading_completion and enqueue](file:///home/user/workspace/repo/app/models/user.rb#L34-L56) put this exact type through DigestJob/Sidekiq. [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L10) normalizes with `BigDecimal(...)`, which can accept the old string or new decimal; the consumer's conversion is not the main hazard.

**What could go wrong — Inference:** A 7.0 worker cannot resolve the new `ActiveJob::Serializers::BigDecimalSerializer` and fails deserialization of newly produced digest jobs. New workers can still consume the old strings. This is asymmetric compatibility, not “all queued jobs break.” Plan worker/producer cutover or an intermediate serializer-compatible release; 7.0 configuration defaults cannot disable the target format.

### H6. Reminder preview changes across daylight-saving transitions

**Before → after — Code + History:** In 7.0 with this app's defaults, `TimeWithZone#to_time` preserves a **fixed UTC offset**. Rails 8.0 added zone-preserving mode; 8.1 makes `to_time` always preserve the **zone object**, regardless of the old compatibility setting. See [8.1 removal commit](https://github.com/rails/rails/commit/c79dc282d687cff1c5dc81e19d27257dca5e6a80). Reading only the earlier default-change entry would miss the unconditional 8.1 behavior.

**Application — Code:** [Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L45) adds 86,400 seconds to `reminder_at.to_time`; [postponing](file:///home/user/workspace/repo/app/models/note.rb#L71-L73) stores its epoch; [the page](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20) displays it.

**What could go wrong — Inference:** October 31 2026, 09:00 Eastern plus 24 elapsed hours displays **November 1 08:00 −05:00**, rather than the old fixed-offset **09:00 −04:00**. The epoch is the same: this does **not** change the 24-hour delay or silently turn it into “same local time tomorrow.” It does change the visible offset/wall time and contradicts the [existing test expectation](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L6-L21). Confirm the intended user-facing promise.

### H7. Expired export fragments lose their negative TTL

**Before → after — Code + History:** 7.0 permits a negative expiration, making a cache entry immediately expired. New cache option validation removes negative `expires_in`; with retained 7.0 defaults it reports/logs the invalid value instead of raising. Without a store-level default TTL, the resulting entry has no expiration. See [validation change](https://github.com/rails/rails/commit/0ae0ab7e3f) and [target implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L906-L945).

**Application — Code:** [Export partial](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) passes `export.expires_at - Time.current` for **every completed export**, including expired ones. This is used with real caching in production.

**What could go wrong — Inference:** Expired indicators can be cached indefinitely until eviction, deletion, or a version/key change, and expired rows generate warnings. This changes cache policy silently; the currently rendered “Expired” text is not itself incorrect. [The download controller](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L4-L16) still authorizes and checks the deadline before conditional responses, so this is **not** an inferred access-control bypass. If 7.1+ defaults are later adopted, the same negative value raises instead. Avoid caching an already-expired indicator with a negative TTL.

### H8. Rich-text plain-text output changes, including stored Markdown exports

**Before → after — Code + History:** Target `to_plain_text` drops script/style contents that 7.0 included. Ordered-list numbering now counts element siblings instead of all sibling nodes, so formatting whitespace no longer creates skipped numbers. Neither requires changing sanitizer defaults. See [script/style fix](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057) and [iterative conversion change](https://github.com/rails/rails/commit/0a5faeaf71745b05d937b579a4da5bd90e0b6b58).

**Application — Code:** [Imports accept body HTML](file:///home/user/workspace/repo/app/models/import.rb#L101-L108), [previews convert it](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58), and [Export#markdown_for](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) converts saved bodies before [uploading the generated file](file:///home/user/workspace/repo/app/models/export.rb#L64-L72).

**What could go wrong — Inference:** Re-exporting identical notes can produce different stored bytes: text inside script/style disappears, and a newline-separated list previously numbered 2, 4 becomes 1, 2. This is likely desirable, but it is a data-format change, not merely a stack-overflow fix. Actual affected stored HTML was not inspected; review representative imported HTML and exports. Existing downloaded export blobs are not rewritten by the upgrade.

### H9. Blob metadata updates now change owning records' timestamps

**Before → after — Code + History:** 7.0 blob updates did not touch attached owners. Since 7.1, a blob's `after_update` touches its attachments and their records; the touch setting defaults true. ActionText::RichText in turn belongs to its note with `touch: true`. See [7.1 changelog explanation](https://github.com/rails/rails/blob/v7.1.0/activestorage/CHANGELOG.md#L147-L154), [target blob callback](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/blob.rb#L25-L46), and [attachment](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/attachment.rb#L20-L37).

**Application — Code:** [Notes have rich-text attachments](file:///home/user/workspace/repo/app/models/note.rb#L8-L8); [digests select by notes.updated_at](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L9). [Exports also own a blob](file:///home/user/workspace/repo/app/models/export.rb#L7-L8).

**What could go wrong — Inference:** Analysis/reanalysis or another metadata update can make an otherwise unedited note count as updated that day, changing digest membership, and can invalidate export fragments through updated owner versions. No image processor does **not** eliminate this path: the null analyzer also writes `analyzed` metadata. The chance of crossing a digest-day boundary depends on when analysis runs; no live data/jobs were examined.

### H10. Attachment filenames gain new substitutions

**Before → after — Code + History:** Active Storage now additionally replaces `"`, `<`, `>`, `?`, and `*` with `-` in `Filename#sanitized` / `to_s`. See [change](https://github.com/rails/rails/commit/0d5bbb65a1).

**Application — Code:** [The blob partial](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb#L2-L12) uses filenames in image alt text and links; rich-text uploads accept reader-selected filenames.

**What could go wrong — Inference:** An existing attachment named `chapter?.pdf` is displayed/served as `chapter-.pdf`. Stored blob keys and file bytes are not renamed, but externally visible filenames change without an exception. Generated exports use a parameterized slug and are unlikely to contain these characters. This is a bounded format-compatibility concern, not evidence of lost files.

### H11. Local secret-key selection changes can invalidate saved attachment signatures

**Before → after — Code + History:** 7.0 development/test generates `tmp/development_secret.txt`; 7.1 moved the local file to `tmp/local_secret.txt`; 8.1 first honors ENV/credentials even locally. See [upgrade guidance](https://github.com/rails/rails/blob/v8.1.0/guides/source/upgrading_ruby_on_rails.md#development-and-test-environments-secret_key_base-file-changed), [8.1 entry](https://github.com/rails/rails/blob/v8.1.0/railties/CHANGELOG.md#L156-L163), and [target selection](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application/configuration.rb#L526-L546).

**Application — Code:** [Sign-in uses encrypted sessions](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L17); [rich-text validation resolves signed blob attachables](file:///home/user/workspace/repo/app/models/note.rb#L95-L97); [blob URLs are rendered](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb#L2-L12). GlobalID's unchanged railtie derives its signed-ID verifier from the app key generator. In this workspace the old temporary secret file exists, the new one does not, and no SECRET_KEY_BASE ENV variable is set; values were not read.

**What could go wrong — Inference:** If the effective key changes, existing sessions, signed URLs, and SGIDs embedded in saved local rich text stop verifying. Login expiry alone is minor; missing embedded attachments make this a stored-data compatibility risk. Preserve the effective key before moving local data. Production is a separate conditional concern: retain its existing effective key; there is no `secret_key_base` entry in this repository's `secrets.yml`, so I did not infer production currently depends on that removed fallback.

### H12. Resolved BigDecimal changes arithmetic precision/rounding internals — review risk, not a demonstrated wrong percentage

**Before → after — Resolution + Code + History:** The current Ruby default is BigDecimal 3.1.5; the new lock selects 4.1.3. The `/` implementation routes through changed division/precision logic; intervening releases fix division precision and rounding, and 4.1 changes division algorithms. See [version history](https://github.com/ruby/bigdecimal/blob/v4.1.3/CHANGES.md), [rounding PR](https://github.com/ruby/bigdecimal/pull/330), and [released-source comparison](https://github.com/ruby/bigdecimal/compare/v3.1.5...v4.1.3).

**Application — Code:** [User#reading_completion](file:///home/user/workspace/repo/app/models/user.rb#L53-L56) divides a BigDecimal ready-note count by total notes, then rounds to four decimal places. That value is serialized into the digest job.

**What could go wrong — Inference / uncertainty:** This is a silent numeric-result review surface under the requested risk rubric. **I have not established an input count for which this app's final four-decimal result differs**; the upstream rounding example is not automatically an app regression. Verify uneven ratios and four-decimal rounding boundaries when evaluating the upgrade, or separately control this dependency. Do not confuse this arithmetic risk with the definite wire-format incompatibility in H5.

## Medium-risk changes

### M1. Rails.application.secrets is removed; provider configuration needs a migration choice

**Before → after — Code + History:** 7.0 reads `config/secrets.yml` through `Rails.application.secrets`; 7.1 deprecates it and 7.2 removes it. See [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63).

**Application — Code:** [Citation::Provider#initialize](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L15) uses that API by default, and [the tests](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L40-L57) use it as well. [The YAML](file:///home/user/workspace/repo/config/secrets.yml#L5-L18) deliberately JSON-quotes ENV values to preserve credentials such as a leading-zero username and punctuation-bearing password.

**What could go wrong — Inference:** Enrichment jobs raise NoMethodError before making HTTP requests; this is not equivalent to the existing “No citation provider is configured” domain failure. Choose ENV/config_for/custom config versus credentials and preserve the current string/nil contract. This is configuration migration, not an automatic move to encrypted credentials. The existing end-to-end credential test is a useful acceptance case.

### M2. Built-in Sidekiq adapter deprecated in 8.1, removed in 8.2

**Before → after — Code + History:** Rails 7.0 provides its Sidekiq adapter. 8.1 still provides it but warns to upgrade to **Sidekiq >= 7.3.3** for the adapter maintained there; the source explicitly says removal in Rails 8.2. See [8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md#L19-L23) and [adapter warning](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb#L33-L37).

**Application — Code:** [The explicit :sidekiq adapter](file:///home/user/workspace/repo/config/application.rb#L22-L24) and [Sidekiq 6.5.12 pin](file:///home/user/workspace/repo/Gemfile#L34-L36) use the deprecated implementation.

**What could go wrong — Inference:** It is **not removed in 8.1.0**, and dependency resolution succeeds. However, the next release requires a deliberate Sidekiq/Redis/Rack compatibility plan, not just a Rails setting rename. Tests use `:test`, and [production suppresses deprecation reporting](file:///home/user/workspace/repo/config/environments/production.rb#L75-L76), so the warning can be missed. A Sidekiq upgrade is not included in the resolved dependency delta.

### M3. Newly resolved JSON 3.1.0 rejects input that JSON 2.7.2 accepted

**Before → after — Resolution + Code + History:** JSON 3 defaults reject duplicate object keys and JavaScript comments; intermediate releases tighten invalid escape/surrogate handling. See [3.0 release](https://github.com/ruby/json/releases/tag/v3.0.0), [complete intervening history](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), and [source comparison](https://github.com/ruby/json/compare/v2.7.2...v3.1.0). JSON 3.1 also rejects non-ASCII BINARY strings during generation; the relevant app-generated strings appear UTF-8, so no specific such failure was established.

**Application — Code:** [Citation::Provider#metadata_from](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) directly uses `JSON.parse` with default options, rescues ParserError, and turns it into a provider failure. JSON also decodes persisted tags/settings and Sidekiq payloads; app-produced tag arrays and job hashes do not intentionally contain duplicate keys/comments.

**What could go wrong — Inference / conditional:** A provider response such as an object containing two `title` keys previously used the last value; now enrichment fails with “response was not valid JSON.” Actual provider responses were not inspected. Decide whether to enforce valid JSON, explicitly permit known legacy input at that boundary, or stage the JSON dependency separately. This is not evidence that ordinary JSON, all stored tags, or all Sidekiq jobs fail.

## Low-risk changes — mechanical fixes

- **Code + History:** `enum status: ..., _prefix: true` in [Note](file:///home/user/workspace/repo/app/models/note.rb#L10-L10) is removed in Rails 8; use `enum :status, { draft: 0, ready: 1 }, prefix: true`. Other app enums already use positional declarations. [Removal](https://github.com/rails/rails/blob/v8.0.0/activerecord/CHANGELOG.md#L64-L66); model load/tests catch it.

## Evidence boundary and suggested review order

**Code + History:** Read release changelogs for 7.1, 7.2, 8.0, 8.1 across all companion frameworks; compared the released Rails trees [7.0.8.7 → 8.1.0](https://github.com/rails/rails/compare/v7.0.8.7...v8.1.0), then inspected the relevant source changes and history. **Inference / recommendation:** First address model/initializer/route-load mechanical blockers, then protect import atomicity, choose digest-day semantics and a queue cutover, and preserve signing keys. Review preview/receipt content and export/cache semantics before separately adopting newer framework defaults. A successful dependency solve is not evidence of boot or runtime compatibility.

**Validation boundary:** No application boot, tests, migrations, asset builds, workers, HTTP requests to the app/provider, or new-version installation were performed. Findings are source-based, not reproduced runtime failures. Application and tracked configuration files were left unchanged; only this report and dependency-resolution evidence were saved as local review artifacts. This is a focused risk assessment, not an exhaustive framework/security certification or approval to upgrade/deploy.
