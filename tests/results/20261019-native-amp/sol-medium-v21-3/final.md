# Rails 7.0.8.7 → 8.1.0: application-specific upgrade risk

## Application facts the ratings depend on

**Code read:** This assessment is for Margin Notes as checked out, not for a newly generated Rails 8.1 application.

- Ruby is **3.3.6**; Rails is pinned to **7.0.8.7** ([Gemfile](file:///home/user/workspace/repo/Gemfile#L4-L8)). Ruby already satisfies Rails 8.1's ≥ 3.2 requirement ([upstream gemspec](https://github.com/rails/rails/blob/v8.1.0/rails.gemspec)).

Actual production PostgreSQL/libpq versions and deployment overrides were not inspected.

## High-risk changes

### H1. An import that returns early can now commit a partial batch

**History:** Rails 7.1 introduced committing on non-local returns behind a setting; Rails 7.2 removed the old rollback behavior. It remains changed with 7.0 defaults. See [7.2 Active Record changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md) and [removal commit](https://github.com/rails/rails/commit/eccc6061f4).

**Before → now, code read:** 7.0's transaction manager rolls back a written transaction exited by `return`; 8.1 commits a normal non-exception exit. [`Import#apply`](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import and preceding notes, then uses `return false unless row.note.save` inside the transaction. The controller interprets false as failure and renders a preview ([controller](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L9-L20)).

**Application consequence — inference:** An invalid later row can leave the import and earlier rows persisted while the UI reports failure. A retry can duplicate the successful prefix. Unlike a raised exception, a validation failure returning false does not roll back anymore. The existing [invalid-row test](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L65) begins with a valid row followed by an invalid one and is directly relevant. Inspect the all-or-nothing contract and use an explicit rollback/exception design before upgrading.

### H2. CSV receipts silently lose citation DOIs

**History:** Rails 7.2 removed `read_attribute(:id)`'s custom-primary-key fallback: [commit, including regression test](https://github.com/rails/rails/commit/39997a0f04).

**Before → now, code read:** `record[:id]` calls `read_attribute`. On a Citation, it used to read the `doi` primary key; it now reads the literal `id` attribute, which is absent and returns nil. The table has a string `doi` primary key ([schema](file:///home/user/workspace/repo/db/schema.rb#L55-L62)), but [`Import#receipt`](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) writes `citation[:id]` to the DOI CSV column. HTML receipts use `citation.doi` and are unaffected ([view](file:///home/user/workspace/repo/app/views/imports/show.html.erb#L14-L19)).

**Application consequence — inference:** Downloaded receipts have blank DOI cells without an exception; a reader can see a correct HTML receipt but get an incomplete CSV. Use the actual DOI or the primary-key `id` method, not attribute indexing. The [existing CSV assertion](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) checks this contract.

### H3. Import preview annotations disappear after `stringify_keys`

**History:** Rails 8.0 fixes `HashWithIndifferentAccess#stringify_keys` to stringify **all** keys, not just symbols: [changelog](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md), [commit](https://github.com/rails/rails/commit/e8574542f8).

**Before → now, code read:** [`Import#annotations`](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) builds an indifferent-access hash keyed by integer source-line numbers. The [preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys`, then still indexes by `row.line`, an integer. In 7.0 integer keys survived; now line 2 becomes key `"2"`, and indifferent access does not equate integer `2` with string `"2"`.

**Application consequence — inference:** Preview annotations silently vanish even though they are still persisted by the import. This breaks the reader's opportunity to review the data, not the stored annotation itself. Decide on consistent key types; the [existing preview assertions](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L20-L24) should detect it.

### H4. Digest contents change from UTC days to reader-local days

**History:** Rails 7.2 preserves serialized TimeWithZone zones: [changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [implementation commit](https://github.com/rails/rails/commit/18098ccc4c).

**Before → now, code read:** In 7.0, the timestamp's offset is serialized, but deserialization calls `in_time_zone` in the worker's zone. In 8.1, a `time_zone` field is serialized and restored; older payloads without it retain the fallback behavior. [`User#request_digest`](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) deliberately passes a reader-zoned time, while reserving the UTC date. [`DigestMailer`](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L10) uses `requested_at.to_date` and `requested_at.all_day` without converting to UTC.

**Application consequence — inference:** At 2026-10-05 03:30 UTC, an Eastern reader's timestamp is October 4 at 23:30. The old worker sends the October 5 UTC digest; the new worker dates it October 4 and selects that local day's notes. The UTC reservation key is unchanged. During rollout, old payloads/new payloads and old/new workers can produce different content days. Choose UTC-day versus reader-day semantics explicitly and account for already queued jobs. The [existing near-midnight test](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37) is particularly valuable.

### H5. BigDecimal job payloads are not readable by old Rails workers

**History:** Rails 7.1 introduced an opt-in BigDecimal serializer specifically to avoid rolling-upgrade breakage; 7.2 removed the primitive path and 8.0 removed its compatibility configuration. See [7.1 explanation](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), and [8.1 serializer source](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

**Before → now, code read:** 7.0 leaves a BigDecimal primitive for Sidekiq's JSON encoding, which becomes a decimal string. 8.1 writes a tagged `ActiveJob::Serializers::BigDecimalSerializer` object and restores a BigDecimal. [`User#reading_completion`](file:///home/user/workspace/repo/app/models/user.rb#L53-L56) supplies that type to [`DigestJob`](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L4-L7). The [mailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L10) converts it with `BigDecimal(...)`; receiving a BigDecimal is itself compatible with that conversion.

**Application consequence — inference:** A 7.0 worker cannot resolve the serializer used by an 8.1 producer. New workers can still consume the old string argument. Plan producer/worker sequencing, queue isolation/draining, and rollback compatibility; retaining `load_defaults 7.0` does not preserve the old encoding. This is high because Redis jobs survive deployment and mixed-version operation is affected, not because every new-version digest is broken.

### H6. Reminder previews start following DST after `to_time`

**History:** Rails 8.0 introduced zone-preserving `to_time`; 8.1 removes the old conversion behavior: [8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md), [removal commit](https://github.com/rails/rails/commit/c79dc282d6), [final implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb).

**Before → now, code read:** Under the current defaults, 7.0 converts a TimeWithZone to a Time with a **fixed offset**. In 8.1 it converts with the actual time-zone object, so Time arithmetic follows offset transitions. [`Note#next_day_reminder_at`](file:///home/user/workspace/repo/app/models/note.rb#L35-L45) uses `reminder_at.to_time + 86_400`; the [reminder partial](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20) displays its offset and local time.

**Application consequence — inference:** Across a spring-forward transition, March 7 at 09:00 −05:00 plus 24 elapsed hours displays as March 8 at **10:00 −04:00**, rather than **09:00 −05:00**. The epoch used by [`postpone_reminder`](file:///home/user/workspace/repo/app/models/note.rb#L71-L72) is unchanged: this fixes the preview's obsolete offset, not a change from elapsed-day to calendar-day scheduling. Review user-visible time expectations and DST assertions; this unconditional change is not held back by 7.0 defaults.

### H7. Negative fragment TTLs are discarded instead of producing already-expired entries

**History/code:** Rails 7.1 added invalid-expiration handling: [changelog](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md), [final `merged_options` / `handle_invalid_expires_in`](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb).

**Before → now, code read:** The [completed-export fragment](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) always computes `expires_in: export.expires_at - Time.current`, including after expiry. 7.0 accepts a negative TTL as an already-expired entry. 8.1 removes the negative TTL and reports/logs an error when `raise_on_invalid_cache_expiration_time` is false, as with these 7.0 defaults. With no store-wide TTL configured, the resulting fragment has no expiry. With 7.1+ defaults it instead raises.

**Application consequence — inference:** Expired indicators can be retained indefinitely in the production FileStore, or until MemoryStore eviction in development; this changes cache retention and may accumulate entries. It does **not** grant expired downloads: [the download controller](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) independently checks ownership and `downloadable?` before conditional responses. Decide how expired states should be cached, and check immediately before/after the deadline with caching enabled, not only the normal NullStore test configuration.

### H8. Action Text conversion changes the exported text and accepted content attachments

**History:** The 7.1 [Action Text changelog](https://github.com/rails/rails/blob/v7.1.0/actiontext/CHANGELOG.md) generalizes ContentAttachment beyond named horizontal rules. Rails 7.2 [sanitizes content attachments when rendering for Trix](https://github.com/rails/rails/commit/e215bf3360). Later commits [omit script/style contents from plain text](https://github.com/rails/rails/commit/bd0729ce37) and [replace recursive conversion, including ordered-list indexing](https://github.com/rails/rails/commit/0a5faeaf71). These differences are present in the endpoint source diff, even where the release changelog is sparse.

**Before → now, code read:** 7.0 recognizes a named `vnd.rubyonrails.horizontal-rule.html` attachment even without a `content` attribute. 8.1 requires HTML content, and sanitizes that content during attachment rendering. Plain-text conversion formerly traversed script/style text; it now omits it, and counts ordered-list element positions rather than all sibling-node positions. See [old attachment source](https://github.com/rails/rails/blob/v7.0.8.7/actiontext/lib/action_text/attachables/content_attachment.rb), [new source](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/attachables/content_attachment.rb), and the commits above.

**Application use, code read:** CSV imports accept `body_html` ([Import](file:///home/user/workspace/repo/app/models/import.rb#L100-L106)); editor forms load saved bodies ([form](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L48-L51)); import previews and Markdown exports call `to_plain_text` ([preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58), [export](file:///home/user/workspace/repo/app/models/export.rb#L77-L81)).

**Application consequence — inference:** Existing HTML can render/export differently without a model error: script/style text disappears from exports; pretty-printed ordered lists can have corrected numbering; old contentless horizontal-rule attachments may become missing-attachment placeholders. Editing/resaving can persist the newly sanitized representation. These are largely beneficial correctness/security changes, but still high under a data-format/security-default rubric. Existing stored bodies were not inspected, so the number of affected notes is unknown. Review representative imported HTML, horizontal rules, nested lists, attachments and edit/save round trips.

### H9. Trix assets become a mixed-version combination (high review candidate, not a confirmed failure)

**History/code:** Rails 8.1 [moves Trix into `action_text-trix`](https://github.com/rails/rails/blob/v8.1.0/actiontext/CHANGELOG.md); the resolved gem provides Trix **2.1.19** ([gem source](https://github.com/basecamp/trix/releases/tag/v2.1.19)). The app deliberately keeps **vendored Trix 1.3.5 JS** in the [layout](file:///home/user/workspace/repo/app/views/layouts/application.html.erb#L9-L14), while [actiontext.css](file:///home/user/workspace/repo/app/assets/stylesheets/actiontext.css#L1-L7) requires the gem-provided `trix` stylesheet. [`@rails/actiontext`](file:///home/user/workspace/repo/app/javascript/application.js#L4) also changes with Rails, including its upload integration ([8.1 JS](https://github.com/rails/rails/blob/v8.1.0/actiontext/app/javascript/actiontext/index.js)).

**Before → now:** The previously mixed 1.3.5 JS / Rails-bundled CSS (whose source header reports 1.3.2) combination becomes 1.3.5 JS / 2.1.19 CSS plus the new Action Text upload code. Merely resolving the new gem does **not** replace the layout's JS with Trix 2. For example, the CSS changes toolbar media queries from device width to viewport width. Trix 2.1.19's DOMPurify update is in the unselected JS, so its editor-side security improvements are not automatically obtained.

**Application consequence — inference, unverified:** Toolbar, attachment and edit/save compatibility deserve direct review before entrusting persisted rich text to this combination. A specific loss/corruption case has not been demonstrated; the high rating is precautionary because editor round trips write stored bodies. Choose whether to retain a coherent 1.x asset set or deliberately upgrade the editor; do not count the dependency update as an automatic editor migration.

### H10. BigDecimal arithmetic changes with the newly locked dependency (high review candidate)

**History:** The resolved BigDecimal **4.1.3**, versus this Ruby's available 3.1.5, includes division precision/rounding fixes in 3.2 and replacement division algorithms in 4.1: [changelog](https://github.com/ruby/bigdecimal/blob/v4.1.3/CHANGES.md), [division-rounding PR](https://github.com/ruby/bigdecimal/pull/330), [precision-growth PR](https://github.com/ruby/bigdecimal/pull/329).

**Before → now, code/history:** This application computes `(BigDecimal(ready_count) / total).round(4)` in [`User#reading_completion`](file:///home/user/workspace/repo/app/models/user.rb#L53-L56), then displays it in digest mail ([template](file:///home/user/workspace/repo/app/views/digest_mailer/daily_digest.text.erb)). BigDecimal's internal quotient precision/rounding implementation changes in the selected dependency.

**Application consequence — inference, unverified:** Arithmetic fixes are behavior changes, but no differing result for this application's nonnegative integer counts rounded to four decimal places has been established. Treat this as a narrower numerical review candidate, not a claimed percentage bug. Check recurring ratios and values around four-decimal rounding boundaries. BigDecimal 4's `divmod` return-type change, removed `precs`, and BigMath additions are not used here.

## Medium-risk changes

### M1. Citation provider configuration can no longer use `Rails.application.secrets`

**History:** Deprecated in [Rails 7.1](https://github.com/rails/rails/blob/v7.1.0/railties/CHANGELOG.md), removed in [Rails 7.2](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md).

**Before → now, code read:** [`Citation::Provider#initialize`](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L15) reads `Rails.application.secrets.citation_provider.to_h` by default. Rails 8.1 no longer provides that API, so instantiating the default provider raises instead of obtaining the configured URL/credentials. [`Citation#enrich`](file:///home/user/workspace/repo/app/models/citation.rb#L28-L33) does not handle that missing API as a provider-domain error.

**Consequence/decision — inference:** Enrichment jobs fail before their HTTP call, can follow Sidekiq retries rather than the intended provider-error handling, and leave pending status. Decide whether to retain environment-based configuration directly, move it into application configuration, or migrate to encrypted credentials. This is a configuration/security-ownership decision, not simply renaming a method; retain environment-specific behavior and verify both web and workers receive the replacement settings. No secret values were inspected or copied into this report.

### M2. Rails' bundled Sidekiq adapter is deprecated and scheduled for removal in 8.2

**History/code:** [Rails 8.1 Active Job changelog](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md) and [adapter warning](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb) specify Sidekiq **7.3.3+** for the adapter provided by Sidekiq itself.

**Before → now:** The [configured `:sidekiq` adapter](file:///home/user/workspace/repo/config/application.rb#L22-L24) still exists in 8.1 and the bundle retains Sidekiq 6.5.12, but it is now a deprecated integration with a stated next-release removal. This is **not** a present dependency-resolution blocker. Production also disables deprecation reporting ([configuration](file:///home/user/workspace/repo/config/environments/production.rb#L76-L77)).

**Consequence/decision — inference:** Decide whether 8.1 is an interim destination and separately budget a Sidekiq migration or replacement backend. Do not silently fold a Sidekiq 7 upgrade into this Rails-only assessment: its Redis/client and native-job contracts need their own review. The medium rating follows the stated rule for deprecations removed in the next release.

### M3. Newly resolved JSON 3 rejects provider payloads previously accepted (conditional)

**History:** JSON **3.1.0** is newly required/resolved, whereas the original lockfile did not pin JSON and this Ruby provides 2.7.2. JSON 3 defaults reject duplicate object keys and JavaScript comments; intervening releases also reject invalid string escapes and fix invalid surrogate handling. See [JSON changelog](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md).

**Before → now, code read:** [`Citation::Provider#metadata_from`](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) uses `JSON.parse(body)` without compatibility options, and maps `JSON::ParserError` to a permanent provider error. A formerly accepted response with repeated `title` keys or a comment can now fail validation instead of yielding metadata. JSON also backs serialized note tags ([Note](file:///home/user/workspace/repo/app/models/note.rb#L12)) and Sidekiq payloads; the app's own tag writer produces ordinary string arrays, not duplicate-key objects.

**Consequence/decision — inference, conditional:** If the real provider emits these nonconforming documents, enrichment will now be marked failed. Decide whether to require conforming JSON, change the provider, or explicitly allow selected legacy syntax. No such provider response was observed, so this is a contract-boundary risk rather than a confirmed broken request. JSON 3 also removes `create_additions`, `fast_generate` and mutable default options, but those APIs are not used by the application or the read Sidekiq JSON load/dump methods.

## Low-risk changes — mechanical fixes / localized compatibility checks

- **L1 — enum syntax removal:** [`Note`, line 10](file:///home/user/workspace/repo/app/models/note.rb#L10) uses the removed keyword definition; preserve the mapping/prefix with `enum :status, { draft: 0, ready: 1 }, prefix: true`. Other app enums already use positional syntax. **History + code:** [8.0 Active Record changelog](https://github.com/rails/rails/blob/v8.0.0/activerecord/CHANGELOG.md). Model loading catches this.
- **L2 — positional serializer removed:** [`serialize :tags, JSON`](file:///home/user/workspace/repo/app/models/note.rb#L12) must become `serialize :tags, coder: JSON`, preserving the existing stored JSON, not switching formats. **History + code:** [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md). Model loading catches this.
- **L3 — aliases must target actual attributes:** [`alias_attribute :highlight_color, :color`](file:///home/user/workspace/repo/app/models/note.rb#L13-L14) points at a JSONB store accessor, not a column; 7.2 rejects it during attribute-method generation. Use ordinary reader/writer method aliases or equivalent delegation to the existing accessor. **History + code:** [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md), [attribute-method implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods.rb).
- **L4 — Action Text allowlist now defaults to nil:** [`allowed_tags += ...`](file:///home/user/workspace/repo/config/initializers/action_text.rb#L1-L3) now raises on nil during initialization; base the assignment on `sanitizer_allowed_tags + %w[details summary]`, retaining the framework's attachment/default tags. **History + code:** [7.1 Action Text changelog](https://github.com/rails/rails/blob/v7.1.0/actiontext/CHANGELOG.md). This accessor change applies even though HTML5 sanitization is not enabled.
- **L5 — numeric `wait_until` no longer supported:** [`Note#schedule_reminder`](file:///home/user/workspace/repo/app/models/note.rb#L56-L62) passes an integer epoch; new job serialization calls `scheduled_at.utc.iso8601`, so use `Time.at(reminder_epoch)` for the same instant. **History + code:** [7.1/7.2 Active Job changelogs](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [8.1 core](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/core.rb).
