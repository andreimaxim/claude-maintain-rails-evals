# Rails 7.0.8.7 → 8.1.0: Margin Notes upgrade plan

**Recommendation: proceed as a staged compatibility upgrade, not a Gemfile-only bump. Keep `config.load_defaults 7.0` for the initial target release.** Ruby 3.3.6 already satisfies Rails 8.1's Ruby ≥3.2 requirement. The existing Sidekiq 6.5.12 / Redis 4.8.1 / Puma 5.6.9 / Sprockets stack resolves with Rails 8.1.0 and Rack 2.2.24; none must be replaced merely because new Rails applications use different defaults.

This is an assessment, not an implemented upgrade. All application execution and experimental edits were confined to disposable copies with isolated PostgreSQL, Redis, cache, and storage resources. The working application's tracked files and index are unchanged. No deployment, production-data inspection, or migration occurred.

## Evidence and its limits

Application starting point: [examined revision](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7), with a clean tracked worktree. Read the application's models, controllers, jobs, mailers, routes, environment configuration, schema/migrations, views, tests, and development/architecture guidance. Production infrastructure and historical data contents are unknown.

Upstream conclusions below are based on **versioned** Rails guides and tagged sources, not the latest unversioned API. In particular, the 7.2 release notes' enqueue-after-commit description must not be applied blindly to 8.1.0: the actual target class default is `false`.

- With identical synthetic verifier key/digest, old signatures are accepted by the new reader; a new-default metadata-bearing signature is not readable by Rails 7.0. This is a verifier-format experiment, not a browser-cookie or real attachment integration test.

### Required dependency constraint for the exact requested target

The initial `bundle update rails` resolved **JSON 3.1.0**. Rails 8.1.0 passes a positional options hash to `JSON.parse`, while JSON 3 takes keywords. This broke this application's session reads and Active Storage metadata decoding. Pin **`gem 'json', '< 3'`** for an exact 8.1.0 target; the experiment resolved **2.21.2** and the same paths then worked. This constraint is compatible with the current Ruby/Rails, although adding it to the original bundle was not separately tested. [S12]

Rails **8.1.4** contains the upstream JSON compatibility fix. Consider a separately agreed later patch target rather than treating 8.1.0 as the latest release; this assessment did not substitute another Rails version. Do not remove the constraint while still targeting 8.1.0 merely because Bundler resolves successfully.

## 2. Mixed-version rollout and rollback requirements

### A. BigDecimal job payloads — resolve before new producers run

`User#reading_completion` returns a BigDecimal. Rails 7.0 treats it as primitive: its test adapter preserves the object, whereas Sidekiq JSON turns it into a string. Rails 7.2+ always emits `ActiveJob::Serializers::BigDecimalSerializer`. Old Rails 7.0 workers cannot deserialize that class. Retaining 7.0 framework defaults does **not** retain the old argument encoding. [S9,S11]

**Recommended current-compatible prep:** enqueue `reading_completion.to_s('F')` and retain `BigDecimal(params[:completion])` at consumption. Deployed before upgrading, it keeps percentage precision and avoids a new serializer across both rollout and rollback. Tested through the real Redis path on both versions. The prepared payloads contain a decimal **string**, and mail still reports 67% for two ready notes out of three. Old primitive-string payloads remain readable by the new worker. A new zone field is ignored by the old time serializer; consumer UTC normalization keeps both behaviors aligned.

Before deploying new producers, inspect queue/retry/scheduled/dead sets for this application's job classes and argument formats in the real deployment (read-only inventory first). Do not purge arbitrary queues or delete reservation keys as a deployment shortcut. If new BigDecimal payloads have already been written, rollback to unprepared 7.0 is unsafe: let capable workers finish/retry them, isolate them for capable workers, or perform a separately reviewed payload conversion preserving IDs, retry state, schedule, and reservations. Stopping producers without accounting for retries is not a drain.

### B. Enqueue-after-commit — do not silently reverse the failure contract

`Citation#request_enrichment` and `Note#schedule_reminder` intentionally enqueue under row locks so a queue exception rolls back state. The jobs lock/reload before acting. In 7.2, **adopting 7.2 defaults** selects adapter-based post-commit enqueueing; the built-in Sidekiq adapter inherits the default of deferral. A Redis failure can then occur after pending/reminder state has committed. Tests using transactional fixtures may never run those commit callbacks. [S13]

The **actual 8.1.0 target** defaults `ApplicationJob.enqueue_after_transaction_commit` to **false**, both with 7.0 and 8.1 load defaults, as source and probes show. Do not copy the 7.2 documentation's global setting or symbolic values into 8.1: `:never/:always/:default` and the global config have been removed. If preserving the immediate-enqueue contract explicitly during a 7.2-defaults bridge, use its supported per-job `:never`; use per-job `false` on 8.1 if an explicit setting is needed. This is **not** a current-7.0 configuration API.

Validate on a real commit boundary with independent database connections and isolated Redis: a rejected enqueue leaves the prior state intact; a committed request can be loaded by the worker; a rollback does not leave actionable work. Check successful post-commit publication failure separately if deliberately adopting it. Native `ExportJob.perform_async` is outside Active Job and is not made transaction-aware by these settings.

### C. Stored signatures, local keys, and cache formats

- **Keep the signing root stable.** The 7.1 local secret file changes from `tmp/development_secret.txt` to `tmp/local_secret.txt`. Preserve/rename the old file rather than generating a new key, or development/test sessions and existing attachment signatures break. Do not print the secret. Production uses ENV/credentials and is unaffected by that filename change, but key continuity across all web/worker instances still matters. [S1]
- **Defer new message writers while rollback to 7.0 is possible.** 7.1 defaults introduce `message_serializer = :json_allow_marshal` and `use_message_serializer_for_metadata = true`. The name means new readers can accept old Marshal data; it does **not** mean old Rails 7.0 can read newly emitted metadata-bearing messages. Keep old writing settings through the rollback window, then change them as a separate release after compatible readers are everywhere. This affects signed blob URLs, attachable signed GlobalIDs stored in rich-text HTML, and other signed/encrypted messages; do not assume a new cookie login repairs stored rich-text signatures. [S14]
- **Validate real attachment lifecycle in both directions.** Seed an old-version blob and rich-text attachment in an isolated shared rollout database/storage, render/open/edit on the new version, then roll the reader back. Test a newly attached blob too, plus a previously issued blob URL. The generic verifier probe establishes a format hazard, not every one of these application paths. Existing tests generate fresh blobs/signatures in one version and cannot establish stored-data compatibility.
- **Treat cache separately from durable records.** New 7.1 cache format is optional default adoption. Production has no explicit application cache override; development uses MemoryStore only when toggled on, tests use NullStore. Redis here is a queue/reservation store, not `Rails.cache`. Keep cache format 7.0 during mixed readers, or use a cold/versioned cache namespace; do not flush the Sidekiq/reservation Redis to clear fragments. There is no application use of serialized Active Record objects in the inspected cache code, so the newer AR Marshal format is not a demonstrated durable-data migration. [S1,S15]

## 4. Ordered implementation and release plan

1. **Prepare on 7.0.8.7.** Land the current-compatible changes above: complete Action Text allowlist, split routes, positional enum, method aliases, singular association filter, omitted nil form model, explicit import rollback, primary-key access, integer-key preview preservation, string join, owned citation config, Time-valued scheduling, explicit DST representation, consumer UTC normalization, and decimal-string digest arguments. Preserve stored formats and current defaults. Existing compatible-preparation experiment passes; no new framework-only settings belong in this release.
2. **Use a 7.1 bridge**, preferably the maintained/final patch appropriate to that series for upgrade feedback. Change tags to keyword JSON coder, make notebook YAML explicit, switch exception config to `:none`, and rename the retry strategy. Keep defaults 7.0 initially. Confirm raw stored JSON/YAML reads and writes with both the current deployed reader and bridge; resolve deprecations before proceeding. No 7.1 runtime was executed in this assessment.
3. **Verify 7.2, then 8.0, then exact 8.1.0** in isolated CI/staging, retaining defaults 7.0 and the existing queue/assets adapters. Review `app:update` output rather than overwriting environment, storage, provider, auth, or queue configuration. Keep versioned migrations and the existing schema; Rails 8.1 alphabetizes schema dumps, which is not evidence of a database change. New databases in Rails 8 may load the schema before pending migrations, so test fresh setup separately from upgrading an existing database. Never use `db:migrate:reset` against data to keep. [S1–S4]
4. **For the exact 8.1.0 bundle, constrain JSON <3** and retain the tested dependency lock. Run full suite, eager load, production-like asset build/boot, and the discriminating validations not covered by ordinary tests: real queue scheduling/retries, dual-version persisted attachment and settings reads, browser rich-text round trips, real commit/queue-failure boundaries, UTC/DST cases, and cache enabled at expiry. Existing tests are necessary, not the acceptance gate alone.
5. **Roll out prepared compatible readers/workers and producers deliberately.** Inventory queue formats and delayed work first; keep old-format writers while 7.0 rollback is supported. Preserve the signing key, storage service names/files, job classes/IDs, Sidekiq queue names, citation DOI identity, and digest reservation keys/UTC semantics. Monitor pending citations, orphan/stuck reminders, failed exports, duplicate/missing digests, deserialization failures, and attachment verification errors. SMTP/deployment hosts and private-blob policies are baseline deployment gaps, not automatically fixed by upgrading.
6. **Rollback rehearsal before production.** Roll the prepared app code and dependency lock back together without reverting compatible data. Old tags must still be JSON and preferences YAML. Confirm all waiting/retrying/scheduled work remains consumable and that newly created attachments still resolve. If new-only payloads/signatures were written, do not promise a blind old-version rollback: retain capable readers/workers or execute an explicitly reviewed migration/recovery plan. Do not undo partially committed imports by guessing which records to delete; prevent that behavior before deploying.
7. **Adopt defaults gradually afterward.** First fix/test readonly, date, cache-expiry, and explicit YAML behavior, then evaluate sanitization/freshness and format writers. Retain old format settings through the rollback window, or deliberately end compatibility and document that decision. Only then raise `load_defaults`, removing temporary pins/settings as supported. Update ARCHITECTURE/TESTING and provider/Trix/serialization comments to reflect the chosen runtime and behavior, not merely the generated Rails template.

## 5. Remaining questions / proposed checks

- What exact production cache, signing-key source, local storage sharing, proxy, provider endpoint, worker topology, and mail delivery settings are deployed? Repository defaults are not proof of deployment configuration.
- Are there historical preferences other than simple string-keyed YAML hashes, tags not encoded as JSON arrays, or stored rich-text SGIDs created with other keys? Inventory read-only; do not bulk rewrite unseen data.
- How far out are reminder schedules, and which retry/dead jobs must remain runnable across rollback? No real/shared Redis was inspected.
- Is the documented fixed-offset reminder preview intentionally retained, or should it display the reader's effective zone? The assessment preserves behavior; changing that is a separate decision.
- Does the old Trix/new Action Text combination remain functional in supported browsers? No browser/system suite was run; repository has a system-test base but no implemented system test cases in the inspected checkout.
- Production-style boot, full worker-daemon lifecycle, real scheduler/retry timings, and shared stored attachment cross-version browser tests remain proposed. Passing disposable request tests does not resolve those questions.
