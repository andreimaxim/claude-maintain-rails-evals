## High-risk changes

### H1. A failed CSV import can now commit its successful prefix

**Before → after [changelog + framework source]:** Rails 7.0 rolls back a written transaction when `return`, `break` or `throw` leaves the block. 7.1 introduced an opt-in return-to-commit behavior; 7.2 removed rollback-on-nonlocal-exit, and 8.1 commits such exits. Retaining 7.0 defaults does **not** restore rollback in 8.1. Sources: [original PR and rationale #48600](https://github.com/rails/rails/pull/48600), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L371-L377), [target transaction implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L643-L675).

**Application use [code]:** [Import#apply:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the Import, saves rows individually, then `return false unless row.note.save` from inside the outer transaction. Application feedback promises that nothing was saved: [preview:15–19](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L15-L19).

**What could go wrong [inference]:** With a valid first row and invalid later row, Rails 8.1 can retain the Import and first note while the controller renders failure. Repeating the corrected import can duplicate the successful prefix. The transaction must be exited with an explicit rollback/exception while preserving the method's failure result. Review a late-failing batch, not only an invalid first row.

### H2. Import annotations silently disappear from previews

**Before → after [changelog + commit]:** `HashWithIndifferentAccess#stringify_keys` used to preserve integer keys; Rails 8.0 converts them to strings. Indifferent access only normalizes symbols, not integers. Upstream intentionally did not backport this long-standing behavior change: [commit and examples](https://github.com/rails/rails/commit/e8574542f88695329e7324f864b9048b0ba0da1b).

**Application use [code]:** [Import#annotations:37–41](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) keys an indifferent hash by integer source-line numbers. [preview:22,42–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys`, then still looks up `annotations[row.line]` with an integer.

**What could go wrong [inference]:** Nonempty annotations stop displaying with no error. They are still assigned to the note by the import, so the preview ceases to describe the data being saved. Keep the lookup and transformed key type consistent; include a multiline CSV row when reviewing source-line behavior.

### H3. CSV receipts silently lose citation DOIs

**Before → after [changelog + source]:** `read_attribute(:id)` previously redirected to a custom primary key. Since 7.2 it reads the actual `id` attribute; `record[:id]` uses this path. `record.id` remains the primary-key accessor. Sources: [7.1 deprecation](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md#L219-L225), [target read implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb#L29-L35).

**Application use [code]:** Citations have a string `doi` primary key and no `id` column: [schema:55–62](file:///home/user/workspace/repo/db/schema.rb#L55-L62). [Import#receipt:63–69](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) writes `citation[:id]` into the CSV DOI field.

**What could go wrong [inference]:** CSV DOI cells become blank, although the HTML receipt still shows `citation.doi`. This is an externally consumed data-format regression, not just an accessor rename. Use the declared DOI/primary-key accessor and compare HTML and CSV receipts.

### H4. Digest jobs change from UTC-day content to reader-local-day content

**Before → after [changelog + PR + source]:** The old Active Job TimeWithZone serializer writes an offset but deserializes in the worker's current zone. The target writes the named zone too and restores it. Legacy payloads without `time_zone` fall back to `Time.zone`; old readers ignore the added field. Sources: [PR #50240 and compatibility discussion](https://github.com/rails/rails/pull/50240), [target serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb). This is not gated by `load_defaults`.

**Application use [code]:** [User#request_digest:34–41](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) reserves a **UTC date** in Redis but passes a time in the user's zone. [DigestMailer:6–12](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L12) uses that argument's `to_date` and `all_day` for subject/content selection.

**What could go wrong [inference]:** For a Los Angeles reader requesting at 00:30 UTC, a new payload describes the previous local date and filters a local-day window, while the reservation remains attached to the new UTC day. Old queued payloads still select the UTC window; new payloads consumed by old workers also behave differently. This changes digest membership and titles even if all records and instants remain identical. Decide whether reservation and content are UTC or local, then make that explicit before a mixed-version rollout.

### H5. New digest BigDecimal payloads cannot be read by Rails 7.0 workers

**Before → after [changelog + commit + source]:** 7.0 treats BigDecimal as a primitive; a JSON queue turns it into a string. 7.1 added `BigDecimalSerializer` with a migration switch. The legacy primitive mode was removed in 7.2 and its configuration removed in 8.0, so 8.1 emits a tagged serializer payload even with 7.0 defaults. Sources: [introducing commit and deployment warning](https://github.com/rails/rails/commit/bc1f3233384601fa8720ee164bced84ffbf3acf2), [7.2 removals](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L59-L65), [target serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

**Application use [code]:** [User:41,53–56](file:///home/user/workspace/repo/app/models/user.rb#L41-L56) passes a BigDecimal completion ratio to DigestJob; [DigestJob:6–7](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L6-L7) forwards it to [DigestMailer:10](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L10).

**What could go wrong [inference]:** An old worker consuming a newly serialized job cannot resolve the new serializer. New workers can still accept old string arguments; `BigDecimal(params[:completion])` also accepts an already-decimal value, so that mailer conversion is not itself a demonstrated blocker. The risk is queued-data compatibility. Use a staged reader-before-writer upgrade or a coordinated producer/worker cutover; a gem-only rolling deployment is unsafe for these jobs.

### H6. Reminder postponement display changes at daylight-saving boundaries

**Before → after [changelog + source]:** Rails 7.0 `TimeWithZone#to_time` preserves a fixed UTC offset under these defaults. 8.1 unconditionally returns a Ruby Time with the full zone object; arithmetic can therefore recalculate its offset across DST. The old compatibility setting is deprecated, not a way to recover the old implementation. Sources: [8.1 removals](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md#L3-L22), [target `to_time`](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb#L494-L500).

**Application use [code]:** [Note#next_day_reminder_at:35–44](file:///home/user/workspace/repo/app/models/note.rb#L35-L44) calls `reminder_at.to_time + 86_400`; [postpone_reminder:71–72](file:///home/user/workspace/repo/app/models/note.rb#L71-L72) schedules its epoch, and [reminder partial:16–19](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L19) displays it.

**What could go wrong [inference]:** The scheduled instant remains 86,400 elapsed seconds later, but the preview's offset and wall-clock time can change. For New York, noon on 2026-10-31 plus 24 elapsed hours becomes 11:00 −05:00 on November 1 rather than the old fixed-offset display of noon −04:00. This fixes the preview's zone consistency but changes a user-visible time contract; do not inadvertently turn elapsed-hour postponement into calendar-day postponement while adapting it.

### H7. Negative fragment TTLs are discarded instead of creating expired entries

**Before → after [changelog + source]:** 7.0 accepted negative `expires_in`, making the entry already expired. The target removes a negative expiration and reports an invalid-expiration error. With this app's retained defaults it reports rather than raises, then proceeds without that per-call TTL; with 7.1+ defaults it raises. Sources: [7.1 configuration change](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md#L861-L869), [target option processing](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L908-L946).

**Application use [code]:** [export partial:25–36](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) caches all completed exports, including expired ones, with `expires_in: export.expires_at - Time.current`. Cache use is enabled in production.

**What could go wrong [inference]:** Rendering an expired export can write an availability fragment with no time-based expiration rather than an already-expired fragment. A hit whose recorded deadline has passed takes this path on regeneration too. It can survive until key invalidation/eviction/deletion; adopting newer defaults instead makes the exports page raise. The download action separately rechecks ownership and expiry ([downloads:5–15](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15)), so this is **not evidence of an expired-file authorization bypass**. Decide how expired indicators should be cached rather than submitting negative TTLs.

### H8. Action Text plain-text output changes, including persisted Markdown exports

**Before → after [commit + release-source diff]:** The target omits script/style contents from plain text, whereas 7.0 included their text. Its iterative traversal also counts ordered-list items by element position, avoiding whitespace text nodes inflating list numbers. These are not all called out in the release changelog. Sources: [script/style filtering commit](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057), [traversal/list-numbering commit and tests](https://github.com/rails/rails/commit/0a5faeaf71745b05d937b579a4da5bd90e0b6b58).

**Application use [code]:** Imported `body_html` goes into Action Text at [Import:101–108](file:///home/user/workspace/repo/app/models/import.rb#L101-L108); snippets use `to_plain_text` in [note index:53](file:///home/user/workspace/repo/app/views/notes/index.html.erb#L53) and [import preview:56–58](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58). [Export#markdown_for:77–81](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) writes the conversion into an uploaded Markdown file.

**What could go wrong [inference]:** The same stored body can generate different snippets and export bytes, without a migration or error. Existing completed export files are not rewritten; regenerated exports can differ. Review indented ordered lists and imported script/style markup. No claim is made that such markup exists in production.

### H9. Development/test signing keys can change, invalidating sessions and attachment references

**Before → after [upgrade history + source]:** The local key file changed from `tmp/development_secret.txt` to `tmp/local_secret.txt`. The target also prefers a configured `SECRET_KEY_BASE`/credentials secret locally rather than always relying on a generated local key (unless dummy-key mode is requested). Sources: [Rails upgrade history](https://guides.rubyonrails.org/v8.1/upgrading_ruby_on_rails.html#development-and-test-environments-secret-key-base-file-changed), [target secret selection](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application/configuration.rb#L519-L544), [8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/railties/CHANGELOG.md#L156-L163).

**Application use [code]:** [ApplicationController:7–18](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L18) uses signed/encrypted sessions; [Note:8](file:///home/user/workspace/repo/app/models/note.rb#L8) and [note editor:48–50](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L48-L50) persist signed attachment references in rich text.

**What could go wrong [inference, local environments]:** A changed key logs readers out and can invalidate attachment signatures in an existing development database. Merely copying the old file is insufficient if a different ENV/credentials key now takes precedence. Inspect the effective source without disclosing the key. I did not read decrypted credentials or assert which branch this environment takes. This does not by itself establish production key rotation.

## Medium-risk changes

### M1. `Rails.application.secrets` is removed: citation enrichment needs a configuration migration

**Before → after [changelog + source]:** Rails read `config/secrets.yml` via `Rails.application.secrets`. 7.1 deprecated that API and 7.2 removed it: [7.1 notice](https://github.com/rails/rails/blob/v7.1.0/railties/CHANGELOG.md#L165-L170), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63).

**Application use [code]:** [Citation::Provider#initialize:13–15](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L15) reads the URL and basic-auth settings through this API. [Citation#enrich:28–32](file:///home/user/workspace/repo/app/models/citation.rb#L28-L32) constructs it in the job. Tests also use the removed API ([enrichment test:117–122](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L117-L122)).

**What could go wrong [inference]:** Enrichment raises before making its HTTP request; this error is not the provider's explicitly handled Error/Unavailable outcome, so the citation can remain pending during backend retries. Choose credentials versus environment-backed application configuration, preserve the key shape and missing-provider behavior, and migrate test setup too. This is a configuration/security-management decision, not a sufficient one-token rename.

### M2. Built-in Sidekiq adapter is deprecated and scheduled for removal in Rails 8.2

**Before → after [changelog + source]:** Rails 8.1 still includes the adapter usable by Sidekiq 6, but warns that Rails 8.2 removes it and recommends Sidekiq >= 7.3.3's own adapter: [8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md#L19-L23), [target adapter](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb#L39-L45).

**Application use [code]:** [application.rb:24](file:///home/user/workspace/repo/config/application.rb#L24) selects `:sidekiq`, while [Gemfile:35–36](file:///home/user/workspace/repo/Gemfile#L35-L36) pins Sidekiq 6.5.12 and redis-rb 4.8.1.

**What could go wrong [inference]:** The pin does not prevent resolving Rails 8.1, and this is not an asserted immediate adapter removal. It does leave a mandatory backend migration before the next Rails minor. A Sidekiq major upgrade would require a separate Redis/client/queue-format review; it was neither performed nor included in this resolver run.

### M3. The resolved JSON 3 upgrade rejects formerly accepted provider responses

**Before → after [dependency changelog + source]:** On this Ruby, the copied lockfile moves runtime JSON 2.7.2 to 3.1.0. JSON 3 rejects duplicate object keys and JavaScript comments by default and removes permissive/additions APIs; 3.1 also rejects non-ASCII binary strings on generation. Sources: [JSON 3.1.0 history, including 3.0 changes](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), [target parser](https://github.com/ruby/json/blob/v3.1.0/lib/json/common.rb).

**Application use [code]:** [Citation::Provider:42–52](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) uses unqualified `JSON.parse(body)` and rescues `JSON::ParserError`. Sidekiq 6 also uses plain JSON parse/generate for its payloads; application tags use a JSON coder at [Note:12](file:///home/user/workspace/repo/app/models/note.rb#L12).

**What could go wrong [inference]:** A provider object containing duplicate `title`/`url` keys, or comments, changes from accepted content to the permanent "not valid JSON" enrichment failure; it does not enter the transient retry path. Choose whether to enforce strict provider JSON, request an upstream fix, or deliberately opt into specific allowances. Ordinary valid JSON is not shown to fail. The application does not use removed JSON convenience APIs; no unconditional Sidekiq JSON-API failure was identified. This finding depends on today's resolution and this machine's previous default gem, not solely on the two Rails versions.
