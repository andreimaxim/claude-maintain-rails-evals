# Margin Notes: Rails 7.0.8.7 → 8.1.0 assessment

## Conclusion and evidence boundary

This is not a Gemfile-only upgrade. Preserve Rails 7.0 defaults initially, fix the required compatibility issues below, and validate sequentially through 7.1, 7.2, 8.0, and exactly 8.1.0 before separately adopting defaults. Several changes affect persisted content, transaction outcomes, and queued jobs regardless of `load_defaults`.

This assessment is **source-based**, not a successful upgrade trial. Inspected the application's models, controllers, jobs, mailers, views, initializers, schema, dependency lock, architecture, and relevant tests; compared them against exact upstream tags. No application boot, dependency resolution, tests, database operations, Redis operations, or upgrade experiments were executed. The application is unchanged. There is no experimental target lockfile or test log to report. All validation below is proposed. Production versions, deployment topology, stored rows and queued payloads remain unverified.

Ruby is pinned to 3.3.6, satisfying Rails 8.1's >=3.2 requirement. Existing dependencies include pg 1.6.0, Puma 5.6.9, Sidekiq 6.5.12, Redis 4.8.1, Pagy 8.6.3, Faraday 1.10.4, Sprockets Rails 3.5.2 and Turbo Rails 2.0.12. Do not gratuitously upgrade these together. Rails 8.1 Action Pack requires Rack >=2.2.4, not Rack 3 exclusively; Sidekiq's Rack ~>2 constraint is not by itself a conflict. Actual resolution including rack-session/rackup and server boot is still required. Rails 8.1 retains its built-in Sidekiq adapter (deprecated for removal in 8.2); moving to Sidekiq >=7.3.3 is a separate integration project, not established as mandatory here.

Each validation must be performed on an isolated copy, and on both current and target versions where applicable.

## Optional defaults adoption and additional conditional findings

1. **Notebook YAML preferences:** `serialize :preferences` continues to have a YAML default with old defaults, but 7.1 defaults set `default_column_serializer = nil`. Before adopting those defaults, explicitly use `serialize :preferences, coder: YAML` on 7.1+. Keyword coder is not a safe 7.0 preparatory change. Preserve YAML rather than converting the column to JSON. Inventory legacy YAML values/classes; validate null, empty hash and populated `export_heading` across writes/reads on both versions. Do not introduce a Hash type restriction without checking existing rows.
2. **Readonly slug:** 7.1 defaults enable `raise_on_assign_to_attr_readonly`. `NotebooksController` permits slug and its edit form always submits it, even unchanged; this can raise on persisted records. Stop permitting/submitting slug for updates before adopting the default (works on 7.0). Retain create-time slug generation. Validate unchanged and tampered slug submissions both preserve slug and still update name/heading. Existing tests cover these requests.
3. **PostgreSQL date decoding:** 7.2 defaults enable `postgresql_adapter_decode_dates`. `Notebook#daily_note_counts` passes each raw `select_rows` date to `Date.iso8601`; that breaks when the value is already Date. Retain false initially, or explicitly select `DATE(notes.created_at)::text AS day` to preserve the public query result contract (also works on 7.0). Validate notes just before/after UTC midnight with a non-UTC reader, chronological ordering across month boundaries and exact counts. Do not change to reader-local reporting by accident.
4. **Expired fragment TTL:** `app/views/exports/_export.html.erb` computes negative `expires_in` for expired exports. 7.1 defaults raise for negative expiration; with old defaults target can instead report and drop the bad TTL, risking an unintended non-expiring cache entry. Avoid caching the expired indicator and only cache live availability with a deadline/positive lifetime; this approach works on 7.0. Ensure passage of time between check and write cannot generate a negative TTL. Validate warm and cold cache immediately before, at, and after expiry with caching truly enabled. Existing export cache test is useful, but ordinary tests use NullStore and caching off.
5. **Conditional download responses:** 8.0 defaults enable `action_dispatch.strict_freshness`. For `ExportDownloadsController#show`, If-None-Match takes precedence over If-Modified-Since rather than requiring both validators to be fresh. Keep old default initially or intentionally adopt HTTP semantics; no application rewrite is necessarily required. Test matching ETag with stale date, mismatched ETag with fresh date, then expired/foreign exports with both validators. Authorization/expiry must still precede 304. Current test sends only ETag while valid and both only after expiry, so it does not discriminate these cases.
6. **HTML5 sanitizers and editor:** 7.1 defaults choose HTML5 sanitizer where supported; review malformed/nested legacy HTML alongside custom allowlist and attachments. HTML rendering and plain-text Markdown may change. No bulk rewrite is required merely to enable rendering. Trix 1.3.5 is deliberately vendored in the layout while Action Text JS comes from Rails via importmap: do not blindly apply generated asset/editor configuration. Verify loading/editing/saving old links, attachments, captions and uploaded files in a browser. `details/summary` flattening on editor save is already documented behavior, not a new Rails bug. A Trix update is a separate deliberate decision after compatibility/security review, not presumed mandatory by source evidence here.
7. **Transaction-aware enqueue:** Do not blindly copy 7.2 release-note defaults into ApplicationJob. Actual 8.1 `enqueue_after_transaction_commit` default is false; only booleans are supported. The app's `Citation#request_enrichment` and `Note#schedule_reminder` rely on Redis enqueue failure rolling back the state change inside `with_lock`. Opting into deferred enqueue breaks that guarantee because Redis failure happens after commit. Keep immediate enqueue unless redesigning failure recovery. Explicit boolean setting is not available on 7.0; no preparation needed there. Validate using a real worker, separate DB connections and Redis failure, outside test transactions. Native `ExportJob.perform_async` is not controlled by Active Job's option.

Do not automatically adopt Solid Queue, Solid Cache, Solid Cable, Propshaft, new authentication generators or deployment templates. They are not necessary to upgrade this existing application. No custom encryption columns, SQLite, custom ActiveStorage streaming subclasses or custom autoload-path requires were found in the inspected application paths. Their unrelated upgrade guidance does not justify app changes. Retain historical migration versions; review generated schema sorting separately from actual schema changes.

## Stored data, mixed versions, rollout and rollback

- **Prepare on 7.0 first:** deploy compatible enum/delegation/transaction/receipt/annotation/export/configuration/reminder-time fixes and UTC/string digest boundary normalization. Do not deploy keyword serializers, the new retry symbol or symbolic exception configuration to 7.0. Run the baseline again after preparation.
- **Advance one minor at a time:** use a supported patch of each bridge line, record the exact selected versions, and review `app:update` rather than overwriting app configuration. On 7.1 adopt keyword serialization, renamed retry strategy and exception symbols. Keep `load_defaults 7.0` initially through the target. Only then adopt defaults individually.
- **Queues:** inventory default, scheduled, retry and dead sets, including ActiveStorage analysis/purge jobs, not only currently runnable jobs. Capture representative redacted payloads and preserve job IDs/execution counts. New BigDecimal serializer payloads cannot be assumed consumable by 7.0; the preparatory string producer avoids generating them, but any already produced need draining or explicit conversion under an approved procedure. New zoned-time payloads are readable with different semantics by old consumers unless UTC normalization is deployed first. Check Sidekiq wrapper class names and metadata in both directions. Do not delete long-future reminders or reset IDs to solve compatibility.
- **Cutover:** prefer coordinated web/worker cutover after stopping producers and letting in-flight work finish, unless the bidirectional payload matrix has passed. Retain scheduled jobs and reservations. A queue drain alone does not empty retry/dead/scheduled sets. Native exports and retries can resume work; verify cancellation and idempotency before restarting workers. Mail delivery is not transactional and duplicates are an existing possibility.
- **Rollback:** first stop target producers/workers, determine which formats they wrote, then choose old code only if it can read those formats. Validate old scheduled and new retry payloads before returning workers to service. Do not assume restoring a database snapshot safely reconciles Redis, emails, blob files and newly accepted user edits. Preserve coherent backups of DB/blob storage and queue inventories; use a forward fix where rollback would lose accepted data.
- **Database and blobs:** retain enum numbers, JSON tags, YAML preferences, JSONB settings, DOI primary key, rich-text bodies and existing attachment/blob IDs. No broad data-format migration is proposed. Check engine migration differences in the disposable environment. If a schema change becomes necessary, make it additive/backward-compatible through the rollback window. Verify real-shaped old blob signed IDs, Action Text SGIDs and disk-service files before/after. Historical jobs reference GlobalIDs, including string DOI IDs.
- **Sessions and signatures:** keep production secret_key_base and cookie JSON format stable. 7.1 changes development/test secret file from `tmp/development_secret.txt` to `tmp/local_secret.txt`; securely copy the value if preserving local signatures matters, without logging it. New message serializer/metadata defaults can make new tokens unreadable by old deployments; delay adoption until rollback compatibility is proven. Test old→new and new→old sessions, attachment SGIDs, blob URLs, and expired/tampered tokens. Invalidating permanent stored attachment references is not solved by asking users to log in again.
- **Caches:** keep 7.0 cache format during mixed versions; 7.1 can read old entries, the reverse is not guaranteed. Test actual configured production store (not established by this repository). If adopting a new format, use a new namespace/cold cache and ensure rollback isolates incompatible entries. Redis here stores queues/reservations, not configured Rails cache; never flush it as a cache-reset shortcut.
- **Sidekiq modernization:** defer to a separate plan or a separately tested bridge. Sidekiq 7 changes Redis client contracts and strict argument checks: the native export producer currently sends symbol-keyed `{ format: 'markdown' }`, and `User#request_digest` relies on boolean single-member `sadd`. Do not assume both survive a client upgrade. Retaining the current stack for 8.1 still needs live integration checks and an operational support/security decision.

## Proposed validation execution and evidence retention

Create disposable variants from a fixed application revision: (A) unchanged 7.0 baseline, (B) prepared 7.0, (C) bridge versions with old defaults, (D) exact 8.1.0 with old defaults, (E) one-default-at-a-time variants. A copied checkout alone is insufficient isolation.

Before any boot, give each experiment an isolated PostgreSQL cluster or explicit disposable databases (including parallel test suffixes), a dedicated Redis instance, private disk-service roots, private cache/temporary paths, and fake provider/mail delivery. Explicitly override DATABASE_URL, REDIS_URL, cable URL, storage services, file-cache path and mail delivery; remove inherited production service credentials. Check effective configuration without exposing secrets. Limit test workers or provision their resources. A fresh development Rails server is not needed for source review; browser runs must use the isolated variant only.

For every experiment retain: exact command and exit status, timestamp, app revision/diff, Ruby/Bundler versions, Gemfile/Gemfile.lock and `bundle list`, effective nonsecret settings, isolated resource identities, fixture/payload hashes, stdout/stderr, Rails log, Sidekiq log, provider log and browser captures. Label each variant's evidence separately. Suggested commands after isolation and resolution: `bundle check`, `bin/rails zeitwerk:check`, `bin/rails db:prepare`, `bin/rails test`, `bin/rails test:system`, and production-mode `bin/rails assets:precompile`; preserve deprecation output. Run actual Redis-backed enqueue/worker smoke flows separately from in-memory tests. Check whether there are runnable system tests rather than interpreting zero tests as browser coverage.

Release gates: every required behavior above passes; old/new DB values and queue payloads pass bidirectionally or cutover excludes overlap; signatures preserve existing content; cached expiry and conditional downloads pass; application and worker boot under deployment-like configuration; production database/Redis versions and Puma/Rack stack are verified. Production email delivery and host are currently unconfigured, so test with a capture transport and do not claim production mail delivery verified.
