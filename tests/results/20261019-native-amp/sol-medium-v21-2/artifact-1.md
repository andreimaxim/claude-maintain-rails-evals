## 2. High-risk changes

### H1. Returning from a transaction now commits a partially applied CSV import

**Before — Code:** Rails 7.0 rolls back a written transaction on a non-local `return`. **Now — History + Code:** Rails 7.1 introduced an opt-in commit behavior; 7.2 removed rollback-on-return, and 8.1 commits unless an exception/abort requires rollback. Retaining 7.0 defaults does **not** retain rollback-on-return.

**Application:** [`Import#apply`, import.rb:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import, then returns `false` from inside the transaction when any row's `note.save` fails. Import-level validation checks CSV structure, not all note validations ([import.rb:111–128](file:///home/user/workspace/repo/app/models/import.rb#L111-L128)).

**Inference / consequence:** A structurally valid file with a valid first note and a blank-title second note can now leave the import and first note committed while the controller displays a failure. Reapplying can duplicate the successful rows. Decide how to express an explicit rollback while preserving the method's false/error contract; this is not fixed by changing framework defaults. The existing invalid-row request test is a useful later check, not a check run here.

**Sources:** [7.1 transaction history](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md#L304-L335), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md), [old transaction implementation](https://github.com/rails/rails/blob/v7.0.8.7/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L316-L351), [8.1 implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb#L644-L681).

### H2. CSV receipts silently lose DOI values when reading `citation[:id]`

**Before — History + Code:** `read_attribute(:id)`, also used by `record[:id]`, redirected to a custom primary key. **Now:** Since 7.2 it reads the actual `id` attribute, not the custom key.

**Application:** [`Import#receipt`, import.rb:63–69](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) emits `citation && citation[:id]`; citations have only the primary key `doi` ([schema.rb:55–62](file:///home/user/workspace/repo/db/schema.rb#L55-L62)).

**Code + inference / consequence:** The 8.1 attribute reader no longer rewrites `id`; an absent attribute uses `Attribute::Null`, whose value is nil. This path therefore produces **blank DOI cells**, rather than a useful exception. Use the semantic `citation.doi` or primary-key accessor `citation.id` when upgrading. Ordinary numeric-ID models are unaffected.

**Sources:** [7.1 announcement](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md#L219-L225), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L421-L427), [8.1 reader](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb#L29-L34), [null attribute](https://github.com/rails/rails/blob/v8.1.0/activemodel/lib/active_model/attribute.rb#L229-L239).

### H3. Import preview annotations disappear after `stringify_keys`

**Before — Code:** `HashWithIndifferentAccess#stringify_keys` returned a duplicate, preserving integer keys. **Now — History + Code:** It inherits the actual key-stringifying behavior, converting integer keys too.

**Application:** [`Import#annotations`, import.rb:37–41](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) keys the indifferent hash by integer source line. The preview calls `.stringify_keys` and still looks up `annotations[row.line]` with an integer ([preview.html.erb:22–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44)). Indifferent access interchanges symbols and strings, **not integers and strings**.

**Inference / consequence:** Key `2` becomes `"2"`, and the lookup returns nil: annotations vanish from preview without an error, although import persistence still reads `row.annotation`. Quoted multiline CSV makes source-line keys especially important. Preserve one key type consistently rather than treating this as an escaping bug.

**Sources:** [8.0 changelog, “stringify all keys”](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md), [old overrides](https://github.com/rails/rails/blob/v7.0.8.7/activesupport/lib/active_support/hash_with_indifferent_access.rb), [8.1 key conversion](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/hash_with_indifferent_access.rb#L408-L410), [inherited stringify implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/core_ext/hash/keys.rb#L9-L19).

### H4. Negative fragment TTLs are discarded instead of representing already-expired entries

**Before — Code:** A negative `expires_in` produced an immediately expired entry. **Now — History + Code:** Cache options delete a negative TTL, report an error, and either continue without that TTL or raise if `raise_on_invalid_cache_expiration_time` is enabled. The application keeps the **false** setting with 7.0 defaults.

**Application:** The completed export partial always calls `cache ... expires_in: export.expires_at - Time.current`, including after the deadline ([exports/_export.html.erb:25–36](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36)).

**Inference / consequence:** Rendering an already-expired export on a cold cache can write its “Expired” fragment **without an expiration** (subject to store eviction/clearing and cache-key changes). This is not evidence of unauthorized downloads: [`ExportDownloadsController#show`:5–15](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) still checks ownership and `downloadable?` before conditional HTTP handling. Raising newer defaults instead would turn the same expired-page path into an exception. Choose an explicit expired-fragment policy.

**Sources:** [7.1 expiration-validation entry](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md), [old expiry calculation](https://github.com/rails/rails/blob/v7.0.8.7/activesupport/lib/active_support/cache.rb#L927-L946), [8.1 validation and error policy](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L905-L946), [default gate](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application/configuration.rb#L305-L311).

### H5. Digest jobs retain the reader's zone instead of becoming UTC in the worker

**Before — Code:** The TimeWithZone serializer stored the instant/offset, but deserialized it into `Time.zone` (UTC here). **Now — History + Code:** Payloads include the named `time_zone`; new workers deserialize into that zone. This is unconditional, not gated by `load_defaults`.

**Application:** [`User#request_digest`:35–41](file:///home/user/workspace/repo/app/models/user.rb#L35-L41) reserves a **UTC** day but sends the reader-zoned `requested_at`; [`DigestMailer#daily_digest`:7–12](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L12) derives its subject date and query window from `to_date` / `all_day` on that argument.

**Inference / consequence:** At 2026-10-05 03:30 UTC, the Eastern request time is October 4 at 23:30. A new payload now selects the **October 4 Eastern day**, not October 5 UTC, while the Redis reservation remains for October 5 UTC. Subject and note membership change silently. Old payloads without a zone still fall back to the worker zone; old workers ignore the new zone field. A mixed queue can therefore deliver different digest content for equivalent request times. Decide whether the contract is UTC days or reader-local days and align reservation and mailer boundaries. The existing [digest test:7–37](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L7-L37) explicitly expects the old UTC behavior.

**Sources:** [7.2 changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L47-L49), [old serializer](https://github.com/rails/rails/blob/v7.0.8.7/activejob/lib/active_job/serializers/time_with_zone_serializer.rb), [new serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb). The fix also appears in later 7.1 patch history; it is absent from the actual 7.0.8.7 baseline.

### H6. BigDecimal job arguments acquire a new wire format and Ruby type

**Before — History + Code:** Active Job 7.0 let BigDecimal pass through as a primitive; Sidekiq's JSON storage converted it to a string. **Now:** BigDecimal uses an `_aj_serialized` envelope naming `ActiveJob::Serializers::BigDecimalSerializer`; 7.1 offered a rollout flag, 7.2 removed the primitive fallback and 8.0 removed the flag.

**Application:** [`User#reading_completion` and `request_digest`:41,53–56](file:///home/user/workspace/repo/app/models/user.rb#L34-L56), [`DigestJob`:4–7](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L4-L7), [`DigestMailer`:10](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L12).

**Inference / consequence:** New workers receive BigDecimal instead of String for new payloads. The mailer's `BigDecimal(...)` conversion is not by itself evidence of failure: it can accept a BigDecimal. **Old Rails 7.0 workers cannot resolve the new serializer**, however, so new-producer/old-worker overlap and rollback after new jobs are queued can fail deserialization. New workers still accept old plain strings. Drain/segregate queues or use an intermediate compatibility rollout before allowing new-format producers; do not assume 7.0 defaults preserve the old format in 8.1.

**Sources:** [7.1 history explicitly describes deployment compatibility](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L155), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L59-L65), [8.0 removal](https://github.com/rails/rails/blob/v8.0.0/activejob/CHANGELOG.md), [8.1 serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

### H7. `TimeWithZone#to_time` now retains a named zone, changing DST previews

**Before — Code:** With the current defaults, `to_time` returned a Ruby Time at the current fixed UTC offset. **Now — History + Code:** Rails 8.1's implementation always uses `getlocal(time_zone)`, retaining the named zone. The old setting no longer restores the fixed-offset behavior.

**Application:** [`Note#next_day_reminder_at`:40–44](file:///home/user/workspace/repo/app/models/note.rb#L40-L44) does `reminder_at.to_time + 86_400`; the note page displays this preview ([reminder partial:16–20](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20)).

**Inference / consequence:** Across an Eastern fall-back transition, a Saturday 09:00 EDT reminder plus 24 elapsed hours now displays Sunday **08:00 EST**, rather than **09:00 at the old -04:00 offset**. The epoch instant remains the same, so this is a wall-clock/offset presentation change, **not** evidence that postponement changes from 24 hours to one calendar day. Confirm the intended display and update its documented assumptions.

**Sources:** [8.0 introduction of named-zone mode](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md), [8.1 removals](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md#L15-L22), [old implementation](https://github.com/rails/rails/blob/v7.0.8.7/activesupport/lib/active_support/time_with_zone.rb#L492-L501), [new implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb#L493-L499).

### H8. Blob analysis/metadata updates touch owning records and can affect digest inclusion

**Before — Code:** The baseline Blob has no general `after_update :touch_attachments`. **Now — History + Code:** Updating a blob touches attachments and their owning records, by default. For embedded note files the owner is the Action Text rich-text record, which itself touches its note.

**Application:** Notes have rich text ([note.rb:8](file:///home/user/workspace/repo/app/models/note.rb#L8)); exports attach files ([export.rb:8,67–71](file:///home/user/workspace/repo/app/models/export.rb#L66-L74)). Digest membership depends on **note `updated_at`** ([digest_mailer.rb:9](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L10)); fragment keys also include export versions.

**Inference / consequence:** Analysis/re-analysis of an attached blob can update the note's timestamp and bring it into a later digest without a reader editing the note; export caches can invalidate earlier than before. This is a cache-consistency fix, but timestamps are application data here. No image processor is installed, so real image-metadata analysis may be limited; the source path also runs for other blob updates. Actual job backlog/analysis timing was not inspected.

**Sources:** [7.1 changelog](https://github.com/rails/rails/blob/v7.1.0/activestorage/CHANGELOG.md#L147-L153), [Blob callback](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/blob.rb#L44), [touch propagation](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/blob.rb#L363-L373), [Attachment owner](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/attachment.rb#L25), [RichText owner](https://github.com/rails/rails/blob/v8.1.0/actiontext/app/models/action_text/rich_text.rb#L50-L61).

### H9. Action Text sanitizes nested content attachments on more paths

**Before — Code:** Baseline `Content#render_attachments` passed nodes through without sanitizing their `content` attribute there. **Now — History + Code:** Rendering first sanitizes nonempty `content` HTML and removes an empty content attribute. This affects editor conversion and attachment rendering, including paths used by plain-text conversion. Do not assume every security fix listed in an intermediate changelog is new: some other Action Text fixes are already backported into 7.0.8.7.

**Application:** Arbitrary CSV body HTML becomes Action Text ([import.rb:101–106](file:///home/user/workspace/repo/app/models/import.rb#L101-L106)); the note editor renders saved HTML ([form:48–50](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L48-L50)); export generation calls `to_plain_text` ([export.rb:77–80](file:///home/user/workspace/repo/app/models/export.rb#L77-L80)).

**Inference / consequence:** Existing/imported nested HTML attachments with disallowed markup can render or export differently, and saving through the editor can persist the sanitized representation. This is a security improvement, not a reason to disable sanitization. Ordinary text and blob attachments without `content` are not evidence of affected content. Inspect representative saved attachments; no stored HTML was read here.

**Sources:** [7.2 changelog and CVE-2024-32464 entry](https://github.com/rails/rails/blob/v7.2.0/actiontext/CHANGELOG.md), [8.0 empty-content fix](https://github.com/rails/rails/blob/v8.0.0/actiontext/CHANGELOG.md), [sanitizing commit](https://github.com/rails/rails/commit/e215bf3360e6dfe1497c1503a495e384ed6b0995), [8.1 rendering implementation](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/content.rb#L97-L110).

### H10. Newly resolved BigDecimal also changes arithmetic implementation — conditional numeric risk

**Before — Code/environment metadata:** Ruby's unlocked BigDecimal 3.1.5 supplies the division used for reading completion. **Now — Resolution + History:** The lock adds **4.1.3**, crossing division precision/rounding fixes in 3.2 and further division algorithm/fix work in 4.1. This is separate from Active Job's wire-format change.

**Application:** [`User#reading_completion`:53–56](file:///home/user/workspace/repo/app/models/user.rb#L53-L56) divides ready-note count by total and rounds to four places; the [digest template:14](file:///home/user/workspace/repo/app/views/digest_mailer/daily_digest.text.erb#L14) renders its percentage.

**Inference / consequence:** A changed numeric result would silently alter a queued completion value. **No concrete note-count pair with a different four-decimal result was established**, so this is a high-consequence candidate, not a confirmed regression. Investigate recurring ratios and rounding boundaries independently before treating it as a blocker. Removed `precs`, changed `divmod`, BigMath and Float-construction APIs have no application callers.

**Sources:** [BigDecimal release history, including 3.2.0/3.2.1/4.1.0/4.1.3](https://github.com/ruby/bigdecimal/blob/v4.1.3/CHANGES.md), [released division source](https://github.com/ruby/bigdecimal/blob/v4.1.3/ext/bigdecimal/bigdecimal.c). Native code was read, not installed, compiled or executed.

### H11. Existing attachment filenames acquire different sanitized output

**Before — Code:** Active Storage's filename sanitizer did not replace `<>?*"`. **Now — History + Code:** It replaces those characters with dashes and corrects filename JSON encoding. This is an output change, not a rename of the stored blob key.

**Application:** User-uploaded attachment filenames appear as labels and in blob routes ([blob partial:8–12](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb#L8-L12)); the export download also uses `blob.filename.to_s` ([download controller:12](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L12)).

**Inference / consequence:** Previously stored names containing these characters can display/download differently without an error. Normal filenames and the application's generated `<slug>.md` export names are not affected. High under the silent-output/data-format rule, but narrow in practical scope; no affected stored filename was observed. Do not infer that blob bytes are renamed or lost.

**Sources:** [8.0 storage history](https://github.com/rails/rails/blob/v8.0.0/activestorage/CHANGELOG.md), [7.2 filename JSON fix](https://github.com/rails/rails/blob/v7.2.0/activestorage/CHANGELOG.md), [8.1 filename source](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/filename.rb#L59-L74).

## 3. Medium-risk changes


### M1. `Rails.application.secrets` is removed

**Before — Code:** Provider construction reads `Rails.application.secrets.citation_provider`. **Now — History:** Deprecated in 7.1, removed in 7.2; `config/secrets.yml` is no longer loaded through that API.

**Application:** [`Citation::Provider#initialize`:13–14](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L14), backed by [secrets.yml:5–18](file:///home/user/workspace/repo/config/secrets.yml#L5-L18).

**Inference / consequence:** Citation enrichment fails when it constructs the provider. Choose the new configuration source (credentials, explicit environment configuration, or an explicitly loaded config file) and its missing-configuration behavior; do not merely delete the file or assume existing environment values are picked up automatically. This is medium because moving secret/configuration ownership needs a decision.

**Sources:** [7.1 deprecation](https://github.com/rails/rails/blob/v7.1.0/railties/CHANGELOG.md), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md), [8.1 application source](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application.rb).

### M3. Resolved JSON 3.1 is source-incompatible with Rails 8.1.0 decoding

**Before — Code/environment metadata:** JSON 2.7.2 accepted a positional options hash and ignored unknown parser options. **Now — Resolution + History + Code:** `ActiveSupport::JSON.decode` in Rails 8.1.0 calls `JSON.parse(json, options)` with a positional second argument, but newly resolved **JSON 3.1.0** defines `parse(source, ...keyword options...)`. In addition, Rails' serialized-JSON coder supplies `{ escape: false }`, which is not an accepted JSON 3 parser option. Merely changing the forwarding to keywords would not resolve that second incompatibility.

**Application:** [`Note#tags` / `tag_list`:12,86–91](file:///home/user/workspace/repo/app/models/note.rb#L12-L91) uses the serialized JSON coder, and its `settings` jsonb column also goes through Active Support JSON decoding. Both remain affected after mechanically repairing `serialize` and `alias_attribute` syntax.

**Code-derived inference / consequence:** Decoding otherwise valid stored tags/settings is expected to raise **ArgumentError for the positional argument count**; after fixing that, the serialized coder's `escape` option would still be rejected. Fixing only model syntax is therefore insufficient with this resolved dependency set. Choose a compatible JSON bound or framework version/fix; a successful dependency solve did not prove source compatibility. This finding was traced through both released sources, **not executed**.

**Additional History + inference:** JSON 3 also rejects duplicate keys and comments by default, invalid escapes/surrogates more strictly, and non-ASCII binary strings on generation. Provider metadata uses plain `JSON.parse` and handles `JSON::ParserError` as enrichment failure ([provider.rb:42–58](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L58)); formerly tolerated nonstandard responses can now fail. No actual provider response or stored malformed JSON was inspected.

**Sources:** [Rails JSON-coder change](https://github.com/rails/rails/commit/90616277e3d8fc46c9cf35d6a7470ff1ea0092f7), [8.1 JSON coder](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/coders/json.rb), [decode forwarding](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb#L23-L24), [JSON 3.1 release history](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), [JSON 3.1 parse signature](https://github.com/ruby/json/blob/v3.1.0/lib/json/common.rb#L291-L299), [JSON parser option validation](https://github.com/ruby/json/blob/v3.1.0/ext/json/ext/parser/parser.c#L2009-L2090).
