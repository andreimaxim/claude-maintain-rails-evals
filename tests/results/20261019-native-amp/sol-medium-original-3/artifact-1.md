# Rails 7.0.8.7 → 8.1.0: Margin Notes upgrade plan

## Recommendation

Proceed as a staged compatibility upgrade, **not** a Gemfile-only bump or an immediate switch to `load_defaults 8.1`. Keep Ruby 3.3.6 and Rails 7.0 defaults initially. Ruby already satisfies Rails 8.1's ≥3.2 requirement. Work through patched 7.1, 7.2, 8.0, then the requested exact 8.1.0, resolving deprecations at each boundary. Review the security/support suitability of deploying the exact older 8.1.0 release separately; this evaluation does not substitute a newer requested target.

No working application files were changed. All application experiments used a disposable checkout, a dedicated PostgreSQL database, a separate Redis server, and copy-local storage/cache/log paths. The only workspace additions are this ignored report/evidence and a repository-local `/.amp/in/` exclude rule. No commit, push, deployment, or production-data inspection occurred.

The passing candidate is experimental evidence, **not** a finished upgrade. Its test changes only redirect the citation tests' configuration access from removed `secrets` to the proposed configuration owner. Browser/system tests, production boot/server smoke tests, actual worker execution, intermediate-version suites, and deployment/rollback rehearsal were **not run**.

### Time behavior: required explicit decisions, not silent default adoption

1. **Digest UTC-day contract changes even with 7.0 defaults.** `User#request_digest` reserves a Redis key by UTC day but sends a reader-zone `TimeWithZone`. New Active Job serialization preserves the named zone; old serialization restores UTC. `DigestMailer#daily_digest` uses `requested_at.to_date` and `all_day`, so an Eastern request at 2026-10-04 23:30 switches from October 5 UTC content to October 4 local content. The current existing test caught the changed subject; not every zone/day boundary is covered.
   - **Recommendation:** Normalize `requested_at = requested_at.utc` in the mailer before deriving date/range. This preserves the documented UTC contract for **old queued and new jobs**, and works on 7.0. Alternatively, intentionally redesign reservation keys and digest content together as a separate feature; changing only the mailer expectation is insufficient.
   - **Validate:** October 4 23:30 Eastern (October 5 UTC) with ready notes on both sides of both midnights; assert reservation date, subject, inclusion/exclusion, and duplicate requests, through JSON-backed queue deserialization.
2. **DST postponement preview changes even with 7.0 defaults.** `Note#next_day_reminder_at` does `reminder_at.to_time + 86_400`. Target `to_time` preserves the zone object, not just a fixed UTC offset. The same elapsed instant now displays November 1 08:00 −05:00 instead of November 1 09:00 −04:00. Scheduling epoch is unchanged.
   - **Recommendation:** Decide whether to retain the documented fixed-offset preview. The preservation candidate uses `reminder_at.to_time.getlocal(reminder_at.utc_offset) + 86_400`, compatible with 7.0. If adopting the arguably clearer reader-zone display, keep the code, update the existing assertion/documentation explicitly, and make spring-forward and fall-back expectations visible. Do not change 24 elapsed hours to a calendar day by accident.
   - **Validate:** Both DST transitions; assert rendered preview offset/wall time **and** postponed epoch, not just “24 hours” text.

## Queued work, persisted formats, rollout and rollback

### BigDecimal jobs need a bridge before mixed versions

`User#request_digest` enqueues `reading_completion` as BigDecimal. Old Sidekiq JSON round trips yield a decimal string; Rails 8.1 writes `ActiveJob::Serializers::BigDecimalSerializer` and reconstructs BigDecimal. This is **not gated by load_defaults** on the target.

Executed cross-read results:

- 8.1 reads old time as UTC and old completion as String.
- 8.1 reads new time in America/New_York and new completion as BigDecimal.
- **7.0 cannot read the new BigDecimal payload** (“Serializer ... is not known”). Keeping 7.0 framework defaults does not solve this.

**Preferred preparation:** enqueue completion as `reading_completion.to_s("F")` on 7.0. The existing mailer parses the decimal string, so the wire contract is explicit and precision is preserved. Deploy this to *all* producers before newer consumers/producers, and normalize the mailer to UTC on both versions. Alternatively backport a compatible deserializer to every rollback worker, but that adds more moving parts than sending a string. Validate the bridge through actual queue JSON and mail output; it was proposed, not executed as a full producer/worker bridge here.

Do not change job class names/argument shapes or discard Redis contents to make deployment easier. Inventory immediate queues, retry/dead sets, and scheduled work. Reminders can be far in the future, and obsolete reminder jobs are intentionally retained and ignored using job IDs. Waiting for the immediate queue to become empty is not enough. Preserve scheduled job IDs and their database associations. Newer payloads left in retry/dead sets still matter on rollback.

### Sidekiq is compatible here, but is a separate future upgrade

The actual conservative resolution kept **Sidekiq 6.5.12, Redis gem 4.8.1, Rack 2.2.24, rack-session 1.0.2, rackup 1.0.1, Puma 5.6.9**, and existing Sprockets. Rails 8.1.0 permits Rack 2; there is no demonstrated Rails-8.1 requirement to upgrade all of them. Real adapter enqueue succeeded. The built-in adapter is deprecated for removal in Rails 8.2, recommending Sidekiq ≥7.3.3.

If upgrading Sidekiq as an optional second project:

- `Notebook#request_export` passes `{ format: "markdown" }` to native Sidekiq; convert to string keys (works on the current version) before strict JSON argument validation becomes enforced.
- Explicit decimal string arguments also avoid strict-JSON rejection in older Active Job payloads.
- `User#request_digest` currently depends on Redis 4 `sadd` returning Boolean. With integer 0 on a newer client, Ruby truthiness would incorrectly enqueue duplicates. Use an available Boolean `sadd?` or explicitly compare the supported client's response, verified against the chosen Redis API; do not simply update the gem pin.
- Recheck `Redis::BaseError`/`CannotConnectError` rescue behavior against the selected client, and adapter wrapper class compatibility for jobs already queued. Verify Redis server requirements, Sidekiq web/Rack compatibility, workers, and provider's Puma-based test fake separately. These newer dependency variants were not resolved or tested here.

### Deployment sequence

1. **Before any upgrade:** back up database and blob files together; inventory real YAML/JSON/rich-text data, production secret source, queue ages, scheduled/retry jobs, session signing, cache topology, and web/worker versions. Production is not a verified deployment in this sample: mail delivery/link host, private file access and upload abuse controls are existing concerns, not new Rails regressions.
2. **Preparatory 7.0 release:** safe changes above (routes, enum, virtual accessor alias, singular association query, unbound form, string join, explicit DOI, annotation keys, explicit import rollback, provider config ownership, Time scheduling); explicit UTC digest semantics, decimal-string producer bridge, and optional safe readonly/cache/date preparations. Exercise the existing and new discriminating checks on 7.0. Do **not** prematurely replace the JSON coder call, retry symbol, or Boolean show_exceptions with APIs 7.0 doesn't implement correctly.
3. **Intermediate 7.1:** convert serialize/retry/exception settings; retain 7.0 defaults and old message/cache writers. Review `app:update` diffs, not wholesale overwrite. In development/test preserve the existing `tmp/development_secret.txt` as `tmp/local_secret.txt` if retaining local sessions and signed attachment IDs matters; contents were not read or copied in this experiment. Production key source must remain stable too.
4. **7.2 → 8.0 → exact 8.1.0:** at each step run application suites, inspect deprecations, boot production-like processes, exercise real queue JSON and assets. Lock JSON <3 for the tested exact target and retain resolved lockfile. Upgrade workers/readers before introducing any new writer format; use a non-mixed cutover if two-way compatibility cannot be demonstrated.
5. **Defaults later:** apply and validate individual changes above, only after every reader understands the new formats and the rollback window is decided. Keep release-separated switches for message/cache writers; a cache namespace can be discarded, but stored attachment signatures cannot simply be flushed.
6. **Rollback rehearsal:** restore the prior application/lockfile without changing tag JSON, preference YAML, integer enum values, DOI keys, blob keys or attachment rows. Ensure prior workers can deserialize every retained payload. Preserve Redis reservations/queues (do not flush), the session secret and signature settings, and old assets during overlap. If newer stored signatures/payloads have been emitted without old-reader support, rollback is not safe merely because database schema did not change; use a compatibility reader release or drain/transform the affected work with an audited plan first.

## Browser and data validations still required

- The layout hardcodes **vendored Trix 1.3.5**, while `@rails/actiontext` comes from the upgraded gem; the target bundle resolved **action_text-trix 2.1.19** through Rails' 2.1.x dependency. The old script does not automatically update. Do not load two Trix versions. Choose one supported editor/Action Text pairing, precompile and inspect the actual JS/CSS, then test links, direct upload, existing signed attachments, over-limit rejection and resave. New Trix APIs/content formats must also be readable by the rollback editor. Retaining the old pin is a temporary compatibility choice, **not verified browser compatibility**. A change to Trix 2 is not verified against current Action Text 7.0.
- Existing details/summary content is already flattened on a Trix edit/save (documented before this upgrade). Do not call this a new regression or silently rewrite stored content to “fix” the upgrade. Use copies of stored examples in browser comparisons.
- Test actual worker execution for citations, delayed/superseded reminders, exports/cancellation, digest JSON arguments, retry exhaustion and Redis refusal under production-like adapters. The test adapter/fake native jobs do not establish these process-boundary contracts.
- Production-like asset boot and HTTP download behavior, schema replay, two-way sessions/signatures/cache, stored YAML permitted types, and disk-sharing/deployment topology remain unverified. No claim is made about production-data prevalence or the absence of third-party library runtime incompatibilities.
