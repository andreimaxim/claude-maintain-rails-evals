# Margin Notes: Rails 7.0.8.7 → 8.1.0 assessment

## Recommendation and evidence status

**Proceed as a staged compatibility migration, not a version-only edit.** Keep `config.load_defaults 7.0` for the initial framework upgrade. This does not retain APIs removed by newer Rails. Use 7.1 → 7.2 → 8.0 → exactly 8.1.0 as isolated verification checkpoints; adopt newer defaults separately. No application changes were made.

This is a **source-based assessment**, not a successful upgrade rehearsal. Inspected Gemfile/lockfile, configuration, models, controllers, views, jobs, schema, tests and repository guidance. Fetched upstream release notes and implementation files at immutable version tags with `curl -fsSL https://raw.githubusercontent.com/rails/rails/<tag>/<path>`. No bundle resolution, Rails boot, tests, database queries, queue operations, or browser experiments were executed. Therefore there is no experimental dependency resolution or runtime log to report. All validation below remains proposed. Existing stored data and production deployment settings have not been inspected. The guide URL initially read currently serves 8.1.4 documentation; conclusions below were checked against **v8.1.0** sources rather than assuming that page exactly describes 8.1.0.

Current baseline: Ruby 3.3.6; Rails 7.0 defaults; pg 1.6.0; Sidekiq 6.5.12; redis 4.8.1; Puma 5.6.9; Sprockets; importmap; vendored Trix 1.3.5. PostgreSQL stores application data, Redis stores jobs and daily digest reservations, and Disk Active Storage stores attachments/exports. Test mode replaces Active Job with its test adapter and native Sidekiq with fake mode, but digest reservations still use Redis.

### Digest serialization: mandatory behavior and rollout preparation

Affected chain: `User#request_digest` → `DigestJob` → `DigestMailer#daily_digest`.

1. **Time zones change in Rails 7.2, regardless of load_defaults.** Old serializer retains an offset in JSON but deserializes in the job's zone (UTC here). New serializer adds the argument's IANA time-zone name and restores it. The mailer uses `requested_at.to_date` and `requested_at.all_day`, while reservation keys use UTC dates. Thus an Eastern request at 2026-10-05 03:30 UTC starts selecting October 4 locally instead of October 5 UTC. Existing digest tests already exercise this and should not be “fixed” by changing expected dates.
2. **BigDecimal becomes a tagged Active Job serializer.** 7.0 pushes a decimal through JSON as a string; newer Rails emits `ActiveJob::Serializers::BigDecimalSerializer`. A 7.0 worker cannot resolve that serializer. New workers can consume old decimal strings. TestAdapter does not recreate the old real-JSON boundary, so passing unit/request tests cannot establish mixed-version compatibility.
3. **Recommended preparation on 7.0:** make the mailer's UTC-day selection explicit (`requested_at = requested_at.utc` before choosing day/range), and enqueue completion as a decimal string (`reading_completion.to_s('F')`). Both work on current Rails and preserve this app's documented UTC contract. Keep mailer accepting existing strings and decimals. The producer may retain its zoned time for context; explicit consumer normalization removes dependence on producer format.
4. Deploy consumer preparation everywhere before newer producers. Exercise old-producer/new-worker and new-producer/prepared-old-worker JSON payloads. Freeze near midnight in zones on both sides of UTC; include notes on opposing UTC/local dates, 1/3 completion and a zero-note reader. Verify selected notes, subject date, percentage, and one reservation per UTC day.
5. If tagged decimal payloads have already been emitted, reverting code alone is unsafe: process them with compatible workers or perform a separately reviewed payload conversion. Inspect ready, scheduled, retry and dead queues, not just current queue length. Do not blanket-clear Redis: reservations prevent duplicate digests and queues contain reminders and exports.

### Reminder display behavior: mandatory decision, not necessarily a code fix

`Note#next_day_reminder_at` uses `reminder_at.to_time + 86_400`. Rails 7.0 converts a TimeWithZone to a fixed-offset Time; 8.1 retains the named zone. The epoch still advances by 86,400 seconds, but the preview's offset/wall-clock time can change across DST. Current documentation explicitly describes the old fixed-offset preview. Existing reminder tests check epoch arithmetic, not the DST preview.

Recommendation: deliberately adopt a zone-correct preview by using `reminder_at + 86_400` (supported on 7.0), and update its documented behavior. If exact old display is required instead, explicitly convert to the current fixed offset before addition. Do not use `1.day` to mean 24 elapsed hours. Validate spring-forward and fall-back: epoch difference is 86,400; displayed offset and local clock agree with the chosen contract. Existing bigint reminders need no rewrite.

These are **not blockers to retaining 7.0 defaults**. They become blockers before enabling the corresponding newer defaults.

Do not switch persisted preferences to JSON as incidental cleanup. | Read real/sanitized old YAML samples, nil/empty values and export headings; new writes must remain readable by old code. Cookie serializer is already JSON and key-generator digest already SHA256: do not apply an unrelated 6.1→7.0 rotation. | Cross-version session cookies, CSRF, signed blob URLs and attachment SGIDs, including previously saved rich text. Production cache is the framework's default FileStore (`tmp/cache`), development uses MemoryStore/NullStore and tests normally NullStore. A shared cache rollout issue applies only if deployments share this directory or override the store; inspect actual topology. A new-format cache can be discarded/namespaced during rollback, unlike durable preferences or rich text. New message metadata/serializer writers can produce tokens old nodes cannot read even though new nodes accept old tokens; retain compatible writing until rollback is no longer needed.

In development/test, Rails 7.1 changes the local secret filename from `tmp/development_secret.txt` to `tmp/local_secret.txt`. Preserve the old value securely if keeping existing sessions and stored attachment signatures. Never copy a real secret into experiment logs. Confirm production's actual secret source remains unchanged; config/secrets.yml here contains citation settings, not an inspected production secret_key_base.

## Queue timing, dependencies, and scope

### Transaction timing is version-sensitive

`Citation#request_enrichment` and `Note#schedule_reminder` enqueue under a row lock and rely on an enqueue exception rolling back changes. Rails 7.2's default adapter policy defers until after commit, so an enqueue failure can occur after the pending/reminder state has committed. This risk exists at the 7.2 checkpoint even if the final 8.1 default differs. Rails 8.1's job class default is **false**; do not claim every 8.1 app defers automatically based on prose alone.

At 7.2 explicitly preserve immediate enqueue with the supported `:never` policy on the affected jobs; for 8.1 use boolean `false` (symbol policies removed). These setters are not 7.0 preparation. Alternatively redesign failure recovery as a separate change, not an accidental default adoption. Exercise real transactions without transactional test wrapping: refused enqueue must retain previous reminder, clear no valid state, and not leave a citation falsely pending. Race an immediate worker against commit to verify existing row-lock protection. `ExportJob` is native Sidekiq and is not affected by Active Job's transaction setting.

### Dependency conclusions, not a solved lockfile

- Ruby 3.3.6 exceeds Rails 8.1's Ruby 3.2 minimum. pg 1.6.0 satisfies the tagged PostgreSQL adapter's `~> 1.1` requirement. Verify the actual PostgreSQL server version against the adapter minimum before rehearsal.
- **Do not assert Rails 8.1 requires Rack 3.** Its tagged Action Pack gemspec requires Rack >= 2.2.4. Sidekiq 6.5.12 constrains Rack ~> 2.0; compatible rack-session/rackup versions must be resolved. A concrete lockfile and Puma HTTP startup still need testing. Preserve pinned dependencies first and update only proven blockers.
- The built-in Sidekiq adapter still exists in 8.1 and accepts Sidekiq >= 4.1; it warns that removal is coming in 8.2 and recommends Sidekiq >= 7.3.3 for the gem-owned adapter. Sidekiq 6.5 implements the lifecycle hook the 8.1 adapter calls. This is source evidence, **not proof that the complete old stack runs on 8.1**.
- Treat a Sidekiq/Redis upgrade as a separate workstream if desired/needed. Inspect `User#request_digest` single-member `sadd` truthiness and Redis exception classes used in `Notebook#request_export`, plus native export JSON arguments, before changing clients. Redis-client protocol/reply changes must not turn “already reserved” into a new digest enqueue.
- Retain Sprockets/importmap, Sidekiq and Disk storage. Propshaft, Solid Queue/Cache/Cable, authentication generators and params.expect are not required migrations for this app. Keep Faraday and Pagy unchanged unless resolution/runtime evidence requires otherwise. Current Minitest 5 pin may remain during the migration.
- Vendored Trix 1.3.5 is intentionally used with current Action Text; upgrading the gem does not update that script. Do not assume the new Action Text JS and old editor interoperate. Inspect the target asset version and browser-test edit/upload/reload before choosing to keep it or replace it with the target-supported Trix. Precompile and serve assets with production-like settings.
- No `encrypts` attributes, custom ActiveStorage::BaseController subclass, SQLite configuration, or custom broadcasts were found in this application's inspected paths. Therefore encryption SHA1 data migration, streaming-concern inclusion, SQLite strict strings and broadcast logger rewrites are not currently motivated. Existing private-file/security limitations and missing production mail delivery are deployment concerns, not caused by this upgrade.

## Rehearsal, delivery and rollback sequence

1. Create a disposable copy **and isolate resources before any boot**: dedicated PostgreSQL database(s), including parallel-test suffixes; dedicated Redis instance/port (preferred) for both jobs/reservations and Cable; independent Disk storage roots, cache directory and secret; local fake citation server; test/file-only mail delivery. Scrub inherited DATABASE_URL/REDIS_URL and credentials. A checkout copy with the existing defaults is not safe isolation. Do not use production snapshots containing secrets or reader data without an approved sanitization process.
2. Capture baseline 7.0.8.7 lockfile, Ruby/Bundler versions, exact commands, nonsecret effective configuration, stdout/stderr, exit codes and Rails/worker logs under a variant-labelled evidence directory. Run `bundle check`, `bin/rails zeitwerk:check`, `bin/rails test`, asset precompile and `bin/rails test:system` with the required browser/display. The repository does not currently have substantive system-test scenarios; add temporary browser validation for rich text and reminders rather than treating that command alone as workflow coverage.
3. Apply only 7.0-compatible preparation in that disposable rehearsal first; repeat checks. Then resolve each checkpoint, retain Gemfile.lock per variant and review `app:update` diffs instead of overwriting app configuration. Apply version-specific serializer/retry/exception/queue settings at their valid checkpoint. Maintain load_defaults 7.0. Enable deprecation visibility during rehearsal (production currently suppresses it).
4. At each stage run the table's boundary checks and real Sidekiq enqueue/consume tests, not only TestAdapter. Retain fixtures of actual JSON envelopes from both versions for immediate, scheduled, retry and dead work, including GlobalIDs, job_id, executions and scheduled_at. Verify new workers consume old reminder jobs and retries and old rollback workers can consume permitted new payloads. Storage analyzer/purge jobs also require inclusion in this inventory.
5. Deploy compatible consumers before new-format producers, or stop producers and drain/segregate incompatible queues. Scheduled reminders can be far in the future; “drain now” is not sufficient. Preserve job IDs because reminder suppression depends on them. Do not blindly replay completed email jobs or clear reservations. Validate reservation TTL and restart/retry behavior.
6. Verify 8.1.0 with old defaults before adopting optional defaults one at a time. Preserve database/storage backups and secret continuity. API fixes here do not inherently require a schema/data rewrite. Rails 8.1 alphabetical schema dumps are expected formatting changes, not a reason to rebuild production tables; test fresh-schema and historical-migration paths separately in scratch databases.
7. Roll back to the **prepared** prior release, not the untouched original. Preserve JSON tags and YAML preferences, rollback-readable job payloads and legacy token writers. Keep newer workers available for any incompatible payloads already produced. Revert/discard incompatible caches independently; never discard durable blobs or queued reminders. Practice rollback by writing records/jobs/tokens on the target then reading/processing on the rollback variant.

Remaining release gates: an actual resolved target lockfile, real DB/server version, production topology and mail configuration, stored YAML/rich-text sample inventory, complete scheduled/retry/dead queue inventory, old/new token interoperability, Trix compatibility, and executed baseline/target/rollback checks. Exact 8.1.0 security suitability was not audited; this assessment does not imply it is the preferred production patch release.
