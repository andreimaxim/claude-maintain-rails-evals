# Rails 7.0.8.7 → 8.1.0: application-specific upgrade risk

Assessment date: 19 October 2026. This is a source-based assessment, not a tested upgrade.

## 1. Application facts the ratings depend on

**Evidence labels:** **App** means application code/configuration read; **Source** means released upstream source/diff or commit read; **Changelog** means upstream release notes; **Resolution** means the dependency-only Bundler operation actually completed; **Inference** means the predicted application consequence or risk rating, not an observed runtime result. Findings assume the mechanical blockers below are corrected; an earlier boot error can otherwise mask later problems.

### What the dependency-only resolution actually changes

**Resolution:** Copied `Gemfile` and `Gemfile.lock` to a temporary directory, replaced only `gem "rails", "7.0.8.7"` with `gem "rails", "8.1.0"`, and ran `bundle lock --update rails` against the copy, using Ruby 3.3.6 / Bundler 2.5.22. **It succeeded.** This establishes satisfiable declared constraints, not runtime compatibility. The result reflects gems available on the assessment date, not just those available when Rails 8.1.0 was released.

- Rails and all its version-coupled components move to **8.1.0**: Active Support, Model, Record, Job, Storage; Action Pack, View, Mailer, Mailbox, Cable, Text; Railties.
- Newly locked: `action_text-trix 2.1.19`, `bigdecimal 4.1.3`, `drb 2.2.3`, `json 3.1.0`, `rack-session 1.0.2`, `rackup 1.0.1`, `securerandom 0.4.1`, `uri 1.1.2`, `useragent 0.16.11`, `webrick 1.9.2`.
- `net-imap` moves **0.6.7 → 0.6.8**; `method_source 1.1.0` leaves the lockfile.
- Crucially, **Rack stays 2.2.24, Sidekiq stays 6.5.12, Redis stays 4.8.1, Puma stays 5.6.9, and pg stays 1.6.0**. The existing frontend gems, Faraday, Mail and net-smtp also remain locked. There is no forced Rack 3 or Sidekiq 7 upgrade in this result.
- **Source:** Some newly explicit dependencies replace Ruby default gems. Installed baseline metadata is JSON 2.7.2, BigDecimal 3.1.5, DRb 2.2.0, SecureRandom 0.3.1 and URI 0.13.1. “New to lockfile” does not mean previously unused.

## 2. High-risk changes

### H1. Returning from an import transaction commits a partial import

**Before — Source:** Rails 7.0 rolls back a written transaction when its block exits through a nonlocal `return`. **After — Changelog / Source:** Rails 7.2 removes that rollback behavior; Rails 8.1 commits a normal non-exception exit. Keeping 7.0 defaults does not retain the removed behavior. See the [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L371-L373) and [implementation change](https://github.com/rails/rails/commit/eccc6061f4f3abdfdeb9a363987a898418d9498f).

**App:** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import, then saves rows one by one, executing `return false` on the first invalid note. The controller subsequently renders a failed preview ([controller](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L8-L20)).

**Inference — High:** A file with a valid first row and invalid second row leaves the import and first note persisted while presenting failure. Retrying can duplicate already-saved rows. This violates the all-or-nothing contract, not just an exception expectation. Review an explicit rollback strategy rather than relying on `return`. The existing [invalid-second-row test](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L72) already names the relevant boundary; it was not run.

### H2. Integer annotation keys are stringified, so import previews lose annotations

**Before — Changelog / Source:** `HashWithIndifferentAccess#stringify_keys` effectively duplicated the hash, retaining integer keys. **After:** Rails 8.0 fixes it to stringify every key. See [release entry](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md#L30-L45) and [PR #53125](https://github.com/rails/rails/pull/53125).

**App:** [Import#annotations](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) stores annotations by integer source line. The preview calls [`.stringify_keys`](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22), then still looks up [integer `row.line`](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L42-L44).

**Inference — High:** Annotation sections silently disappear from previews, including invalid-row previews, although the annotation is still persisted on successfully imported notes. Normalize keys and lookups together or avoid unnecessary stringification. This is a deliberately non-backported bug fix, not a new setting.

### H3. `citation[:id]` no longer returns the DOI primary key

**Before — Source:** `read_attribute("id")`, used by `[]`, redirected to a custom primary key. **After — Changelog / Source:** Rails 7.2 removes that fallback; reading a nonexistent `id` attribute returns nil here. See [release entry](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md#L425-L427) and the [target reader](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb#L29-L35).

**App:** [Import#receipt](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) writes `citation[:id]` into the DOI CSV field; the [citations schema](file:///home/user/workspace/repo/db/schema.rb#L55-L62) has only `doi` as its primary key.

**Inference — High:** Downloaded receipts silently contain blank DOI cells. The DOI remains stored; the export is wrong. Use the explicit DOI accessor or primary-key method `.id`, not bracket access to a nonexistent column. The existing [receipt assertion](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) covers the observable contract.

### H4. Digest jobs now preserve the reader's zone, changing the selected day

**Before — Source:** The TimeWithZone serializer stored the offset but deserialized into `Time.zone`, UTC in this app. **After — Changelog / Source:** Rails 7.2 includes the named zone in new payloads and restores it. Old payloads without the zone retain the fallback. See [release entry](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L47-L49) and [serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb).

**App:** [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) reserves a **UTC-date** Redis key but passes a user-zone time. [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L12) uses that received time's `to_date` and `all_day` directly; the [UI promises UTC](file:///home/user/workspace/repo/app/views/notes/index.html.erb#L10).

**Inference — High:** New jobs select a local-day window, not the promised UTC-day window, so notes can be omitted or included on a different day. For example, the existing test's request at **5 October 2026 03:30 UTC** is **4 October 23:30 in New York**: the old path selects 5 October UTC, the new path selects 4 October in New York. Even away from midnight, the UTC boundaries of `all_day` change. Old/new queued payloads can produce different contents on the same new worker. Decide the digest's intended day explicitly; retaining the UTC reservation alone does not preserve it. See the [existing boundary test](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37).

### H5. New BigDecimal job arguments cannot be read by Rails 7.0 workers

**Before — Changelog / Source:** Active Job treated BigDecimal as a primitive; Sidekiq's JSON round-trip delivered a string. Rails 7.1 introduced an opt-in tagged serializer specifically to support staged deployments. **After:** Rails 7.2 removes the primitive serializer; the old opt-out configuration is also removed by 8.0. See [7.1 explanation of mixed-version failure](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L157), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md#L59-L65), and [target serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

**App:** [User](file:///home/user/workspace/repo/app/models/user.rb#L41-L56) enqueues the BigDecimal reading-completion ratio; [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L6-L7) forwards it to [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L10). Sidekiq remains at 6.5.12, so this is a Rails payload change, not a Sidekiq dependency upgrade.

**Inference — High, deployment-dependent:** An old worker receiving a new payload lacks `ActiveJob::Serializers::BigDecimalSerializer` and cannot deserialize the digest. Rollback has the same issue if new jobs remain queued. New workers can still read old string arguments and the mailer coerces either representation. Coordinate producers/consumers, drain or isolate queues, or bridge payload compatibility before overlap. A clean-start test suite does not establish this rolling-deployment contract.

### H6. `TimeWithZone#to_time` now keeps full timezone rules, not a fixed offset

**Before — Source:** With 7.0 defaults, `to_time` preserved the current numeric UTC offset. **After — Changelog / Source:** Rails 8.1 always retains the receiver's timezone object, including DST transitions. This removal is not undone by `load_defaults 7.0`. See [commit and tests](https://github.com/rails/rails/commit/c79dc282d687cff1c5dc81e19d27257dca5e6a80).

**App:** [Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L44) calculates `reminder_at.to_time + 86_400`; the [reminder partial](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20) displays the result.

**Inference — High under the timezone-behavior criterion:** Across New York's autumn transition, the existing example's **31 October 2026 09:00 −04:00 + 24 hours** was displayed as **1 November 09:00 −04:00**; the new result is **1 November 08:00 −05:00**. They are the **same instant**. The job is not moved by an hour: postponement still stores the result's epoch ([Note](file:///home/user/workspace/repo/app/models/note.rb#L71-L72)). The visible wall time/offset and the existing [preview expectation](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L19-L21) change. Decide whether to adopt the corrected local-zone preview or explicitly retain the fixed-offset presentation; do not accidentally change 24 elapsed hours to one calendar day.

### H7. Negative cache TTLs are discarded, rather than creating expired entries

**Before — Source:** A negative `expires_in` produced an already-expired cache entry. **After — Source:** Rails 7.1+ removes that TTL and reports an invalid-expiration error; with the retained old defaults it does not raise. With 7.1 defaults it raises instead. See [PR #45892](https://github.com/rails/rails/pull/45892), the [follow-up commit](https://github.com/rails/rails/commit/f4aa7ad9a61bc4cbd1bb585cb965109b1f707e96), and [target implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L910-L944). The endpoint source, not the PR's preliminary discussion, determines this assessment.

**App:** The [export availability fragment](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) passes `export.expires_at - Time.current` even after expiry. Production caching is enabled.

**Inference — High for changed caching semantics, limited security impact here:** Rendering an expired export now reports an error and can cache the **Expired** fragment without a time-based expiry, until key/version invalidation or eviction. It does **not** by itself persist a valid download link or bypass expiry: [the download action](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) independently rechecks ownership and [downloadability](file:///home/user/workspace/repo/app/models/export.rb#L45-L48). Separate expired rendering from positive-TTL caching, and test the deadline on both sides. Adopting newer defaults without fixing this turns the same input into an exception.

### H8. Blob metadata updates now touch attachment owners and affect digest membership

**Before — Source:** Updating/analyzing an existing blob did not perform the added attachment-owner touch. **After — Changelog / Source:** Rails 7.1 adds it to invalidate stale metadata-dependent caches. The target's `Blob#touch_attachments` touches attachments, whose `record` association normally touches the owner; Action Text rich text in turn touches its note. See [introducing commit](https://github.com/rails/rails/commit/294c2710620871a691e4ca5fefb5e5ace279195d), [attachment association](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/attachment.rb#L25), and [rich-text association](https://github.com/rails/rails/blob/v8.1.0/actiontext/app/models/action_text/rich_text.rb#L46).

**App:** Notes [have rich-text bodies](file:///home/user/workspace/repo/app/models/note.rb#L8) with blob attachments; [digests select by `notes.updated_at`](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L8-L9). Exports also [attach a generated blob](file:///home/user/workspace/repo/app/models/export.rb#L67-L71).

**Inference — High, input/timing-dependent:** When background analysis or another blob metadata update occurs after attachment, it can move an otherwise unedited note's `updated_at`, change digest inclusion/order and invalidate owner-versioned cache entries. No production frequency was established. Review whether “updated today” should include attachment analysis, especially analysis completing across a day boundary. This is a persisted timestamp change, including beneficial cache invalidation, not merely a performance optimization.

### H9. Rich-text plain-text conversion changes stored Markdown exports

**Before — Source:** Plain-text conversion could include script/style node text; ordered-list numbering used child-node positions, including whitespace nodes. **After — Source:** Script/style content is excluded and numbering counts element siblings. These are source-diff findings, not a claim that every change had a changelog entry. See [script/style fix](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057) and [iterative conversion/list-numbering commit](https://github.com/rails/rails/commit/0a5faeaf71745b05d937b579a4da5bd90e0b6b58).

**App:** CSV imports accept [body HTML](file:///home/user/workspace/repo/app/models/import.rb#L101-L106); plain text is shown in [import previews](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58) and the [notes list](file:///home/user/workspace/repo/app/views/notes/index.html.erb#L52-L53). [Export#markdown_for](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) uses `to_plain_text`; generated output is [uploaded as a stored file](file:///home/user/workspace/repo/app/models/export.rb#L67-L71).

**Inference — High, content-dependent:** The same saved HTML can generate different preview text and different Markdown bytes without a database body change. Formatted ordered lists separated by newlines distinguish the paths; script/style text matters only if such nodes exist in stored/imported HTML. Existing export files are not rewritten automatically, so old/new workers can produce different files. Compare representative imported bodies and list exports; retain the fixes unless the application intentionally relies on the old output. No stored-content inventory was performed.

## 3. Medium-risk changes

### M1. `Rails.application.secrets` is removed; choose the replacement configuration source

**Before — App / Source:** The provider default argument reads `config/secrets.yml` through `Rails.application.secrets`. **After — Changelog / Source:** Rails 7.2 removes that API. See [release entry](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63).

**App:** [Citation::Provider#initialize](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L14) invokes it before making an HTTP request. The [citation integration tests](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L117-L122) also mutate that configuration.

**Inference — Medium:** Default provider construction raises instead of enriching citations; the error is not a provider HTTP refusal. Choose credentials, explicit ENV-backed application configuration, or `config_for`, preserving the environment/key conventions and test overrides. This is not safely solved by mechanically renaming `secrets` to `credentials`: their storage and deployment requirements differ.

### M2. The built-in Sidekiq adapter is deprecated and scheduled for removal in 8.2

**Before — Source:** Rails supplied the adapter used by the pinned Sidekiq 6.5.12. **After — Changelog / Source:** Rails 8.1 retains it but warns of removal in **8.2**, recommending Sidekiq **7.3.3 or newer** for Sidekiq's own adapter. See [release entry](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md#L19-L23) and [adapter warning](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb#L33-L39).

**App:** [Application configuration](file:///home/user/workspace/repo/config/application.rb#L22-L24) selects `:sidekiq`, while [Gemfile](file:///home/user/workspace/repo/Gemfile#L34-L36) pins Sidekiq 6.5.12 and Redis 4.8.1. Native [export enqueueing](file:///home/user/workspace/repo/app/models/notebook.rb#L24-L26) also uses a symbol-key options hash, relevant to any later Sidekiq strict-arguments migration.

**Inference — Medium:** The declared dependencies resolve for 8.1.0; this is **not** evidence of an immediate forced Sidekiq 7 upgrade or removal in 8.1. It is a next-release removal requiring a planned, separately assessed Sidekiq/Redis migration or adapter decision. Include native jobs and queue compatibility in that decision; do not bundle it invisibly into this Rails-only assessment.

### M3. Today's resolution selects JSON 3.1.0, incompatible with Rails 8.1.0's decoder

**Before — Source:** The baseline Ruby JSON 2.7.2 accepts the old options calling convention and more permissive parsing. **After — Resolution / Changelog / Source:** Active Support's new explicit JSON dependency permits **3.1.0**, which makes parser options keyword-only and rejects unknown options. See [keyword-argument commit](https://github.com/ruby/json/commit/ebf0f2901c162eb0b3008001a50ba378199a0a2f), [JSON history](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), and [released parse signature](https://github.com/ruby/json/blob/v3.1.0/lib/json/common.rb#L291-L298).

**Source:** Rails 8.1.0's [ActiveSupport::JSON.decode](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb#L24-L25) still calls `::JSON.parse(json, options)` with two positional arguments, even when options is empty. Its [Active Record JSON coder](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/coders/json.rb#L7-L20) also passes `escape: false` as a decoding option, which is not an accepted JSON 3 parser keyword. Changing only the positional forwarding would not address both issues.

**App:** Notes [serialize tags with JSON and use JSONB settings](file:///home/user/workspace/repo/app/models/note.rb#L12-L14), backed by [the schema](file:///home/user/workspace/repo/db/schema.rb#L99-L100); both reach Rails decoding. The [form reads/writes tags and highlight color](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L22-L38). The provider separately calls [JSON.parse directly](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52).

**Inference — Medium, source-confirmed mismatch, not executed:** Once the earlier boot/model API blockers are repaired, reading serialized tags or string-valued JSONB results reaches an incompatible call and raises `ArgumentError`; ordinary valid JSON is enough. The [target JSON type](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/type/json.rb#L14-L25) rescues `JSON::ParserError`, **not `ArgumentError`**, so this argument mismatch is not silently converted to nil. Choose a compatible JSON dependency constraint or framework version/fix and re-resolve; no pin or patch was added during this assessment.

**Additional input-dependent parsing change — Changelog / Inference:** Even after resolving that bridge incompatibility, direct provider parsing rejects duplicate keys and comments by default, and newer JSON releases reject previously ignored invalid escapes. A provider response with duplicate `title` keys previously used the last value; now the app records “not valid JSON.” Decide whether to reject those inputs, correct the provider, or explicitly opt into compatibility. The local stand-in [generates ordinary JSON](file:///home/user/workspace/repo/bin/citation-provider#L41-L50); no malformed real-provider responses or stored values were established. Do not infer that this failure occurs on the stand-in's valid response, or that every future resolution will choose this JSON version.

## 4. Low-risk changes: mechanical fixes and small presentation deltas

Each item below is **Low by inference** because it has a direct replacement or a narrowly scoped presentation effect. “Low” does not mean optional: several prevent boot or core requests from succeeding.

- **Changelog / Source / App — Enum keywords removed (8.0):** [Note's declaration](file:///home/user/workspace/repo/app/models/note.rb#L10) needs `enum :status, { draft: 0, ready: 1 }, prefix: true`; preserve the prefix and integer mapping ([release entry](https://github.com/rails/rails/blob/v8.0.0/activerecord/CHANGELOG.md#L64-L66)).
