Read the Rails component changelogs at the 7.1, 7.2, 8.0 and 8.1 release tags; compared the **7.0.8.7 and 8.1.0 source trees across all Rails components**; followed relevant changes to their commits, tests and final implementation. ## 2. High-risk changes

### H1. Invalid CSV imports can commit the import and earlier rows — Rails 7.2

**Before — Code:** 7.0.8.7 rolls back a written transaction when its block exits through a nonlocal `return`. **After — Changelog + Code:** 7.2 removes that rollback branch; 8.1 commits a normal non-exception exit, including `return`. Retaining `load_defaults 7.0` cannot restore the removed branch.

**Application use:** [Import#apply:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import, then saves rows sequentially and does `return false unless row.note.save`. [ImportsController:12–19](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L12-L19) treats false as a failed import. The existing [invalid-row request test:48–72](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L72) contains exactly the risky input: a valid first row and an invalid second row.

**What could go wrong — Inference, strong code evidence:** the response still reports failure/“nothing saved,” while the import, first note, rich text and possibly its citation remain committed. Retrying can duplicate earlier rows. This is stored-data behavior, not merely a changed return value. During migration, explicitly roll back on row failure while preserving the false/error result; review this contract before accepting a new default.

**Upstream:** [removal commit and tests](https://github.com/rails/rails/commit/eccc6061f4f3abdfdeb9a363987a898418d9498f), [7.2 Active Record changelog](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md).

### H2. Digest completion arguments are incompatible with old workers — introduced 7.1, mandatory 7.2

**Before — Changelog + Code:** Active Job passes BigDecimal through as a primitive; JSON-backed Sidekiq round-trips it into a decimal **String**. **After:** the mandatory `ActiveJob::Serializers::BigDecimalSerializer` stores a typed envelope and reconstructs **BigDecimal**. The 7.1 compatibility switch was temporary; it does not preserve the old writer on 8.1.

**Application use:** [User:34–56](file:///home/user/workspace/repo/app/models/user.rb#L34-L56) queues `reading_completion`, a BigDecimal; [DigestJob:4–7](file:///home/user/workspace/repo/app/jobs/digest_job.rb#L4-L7) forwards it. [DigestMailer:10](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L10) converts it with `BigDecimal(...)`, so the **new Ruby argument type alone does not break the mailer**.

**What could go wrong — Inference supported explicitly by changelog:** a 7.0 worker cannot resolve a new BigDecimalSerializer envelope and fails deserialization. New workers can still process old string arguments. This is directional incompatibility during a rolling deploy or rollback, not a claim that all existing jobs fail. Decide on a drain/cutover or a staged compatibility deployment before new web processes write these payloads; include retry/scheduled queues, not only the ready queue.

**Upstream:** [7.1 warning and serialization explanation](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md#L142-L155), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [8.1 serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/big_decimal_serializer.rb).

### H3. Digests silently switch from UTC days to the reader's local days — Rails 7.2

**Before — Code:** TimeWithZone job deserialization discards the sender's named zone and reconstructs the instant in the worker's `Time.zone` (UTC here). **After — Changelog + Code:** the payload includes the sender's named zone and deserialization restores it. Legacy payloads without a zone still fall back to the worker's zone.

**Application use:** [User:35–41](file:///home/user/workspace/repo/app/models/user.rb#L35-L41) queues a time in the reader's zone, but reserves one request per **UTC date**. [DigestMailer:7–12](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L12) uses the deserialized time directly for `to_date`, the `all_day` SQL range and the email subject. The [existing digest test:5–37](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37) supplies a useful boundary case.

**What could go wrong — Inference, strong code evidence:** a request at 2026-10-05 03:30 UTC / October 4 23:30 Eastern formerly selected October 5's UTC notes; new payloads select October 4's Eastern-day notes and label the email October 4. Reservation and selection days no longer agree with each other or with the UI's UTC promise. Old and new queued payloads can produce different digests on the same new worker. Decide whether UTC or local days are intended and normalize explicitly at the mailer boundary if preserving the contract.

**Upstream:** [zone-preservation commit](https://github.com/rails/rails/commit/18098ccc4c837278c42d9757dd2b1e0bdd2016e0), [8.1 serializer including legacy fallback](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb).

### H4. CSV preview annotations disappear — Rails 8.0 bug fix

**Before — Changelog + Code:** `HashWithIndifferentAccess#stringify_keys` effectively duplicates the hash; integer keys remain integers. **After:** it really stringifies integer keys too. Indifferent access converts symbols, **not integer lookups**, to strings.

**Application use:** [Import#annotations:37–41](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) indexes by integer CSV line numbers. [Preview:22,42–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys` then looks up `annotations[row.line]` using the integer again. [Existing request assertions:21–24](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L21-L24) require those annotations to be displayed.

**What could go wrong — Inference, strong code evidence:** the conditional becomes false and annotations vanish from preview without an error. They are still assigned to notes and saved; this is hidden preview information, not deletion of stored annotations. Keep keys/lookups in one representation rather than relying on the old bug.

**Upstream:** [commit, rationale for not backporting, and tests](https://github.com/rails/rails/commit/e8574542f88695329e7324f864b9048b0ba0da1b).

### H5. Import receipt DOI columns become blank — Rails 7.2

**Before — Code:** reading `record[:id]`/`read_attribute(:id)` maps to a custom primary key. **After — Changelog + Code:** it reads the literal `id` attribute; only `record.id` remains the primary-key abstraction. Upstream's custom-primary-key regression test explicitly expects nil for the old accessor.

**Application use:** [Import#receipt:63–69](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) writes `citation[:id]` into the DOI column. [Citations schema:55–62](file:///home/user/workspace/repo/db/schema.rb#L55-L62) uses `doi` as the primary key and has no `id` column. [ImportsController:26–28](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L26-L28) serves that generated CSV.

**What could go wrong — Inference, strong code evidence:** otherwise-successful receipts silently omit DOIs; downstream reconciliation loses citation identities. Existing [receipt expectation:43–45](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) captures the desired output. Use the semantic `doi` or primary-key `id` reader, not `[:id]`.

**Upstream:** [removal commit and nil-result test](https://github.com/rails/rails/commit/39997a0f049dfb3d94b28d1cb131b9136a1b7b0a).

### H6. The “24 hours later” reminder preview changes across DST — Rails 8.1

**Before — Code:** with the app's defaults, `TimeWithZone#to_time` produces a Ruby Time with the current **fixed UTC offset**. **After — Changelog + Code:** it preserves the full named time zone, including subsequent DST transitions. The compatibility setting no longer changes this behavior.

**Application use:** [Note:35–44](file:///home/user/workspace/repo/app/models/note.rb#L35-L44) calculates `reminder_at.to_time + 86_400`; [reminder partial:17–19](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L17-L19) displays it. [Existing DST expectation:6–21](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L6-L21) expects November 1, 2026 09:00 −04:00 after starting October 31 at 09:00 Eastern.

**What could go wrong — Inference from time-zone arithmetic:** the new representation is November 1 **08:00 −05:00**, not 09:00 −04:00. Both represent the same instant, so [postponement's `.to_i`:71–72](file:///home/user/workspace/repo/app/models/note.rb#L71-L72) still schedules exactly 86,400 elapsed seconds later. Do not mistake this for a one-hour change to the queued execution time. It is an unannounced change to the displayed offset/wall-clock contract; choose which representation the UI should promise.

**Upstream:** [8.1 compatibility removal](https://github.com/rails/rails/commit/c79dc282d687cff1c5dc81e19d27257dca5e6a80), [final `to_time`](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb#L497-L499).

### H7. Negative export-fragment TTL becomes a non-expiring cache entry — Rails 7.1

**Before — Code:** a negative `expires_in` produces an already-expired cache entry. **After — Changelog + Code:** Rails removes the negative expiration option and reports/logs the error. With retained 7.0 defaults `raise_on_invalid_cache_expiration_time` is false, so this is **not automatically an exception**. No replacement TTL is configured here, so the resulting entry has no expiration.

**Application use:** [export partial:25–36](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) always passes `export.expires_at - Time.current` for completed exports, including already-expired ones. Production enables fragment caching.

**What could go wrong — Inference:** expired export indicators become persistent FileStore entries rather than immediately-expiring entries, with error reports/logs during rendering. Impact is limited: the fragment normally contains the correct “Expired” state; this change alone does **not** make an expired download available or establish a stale-live-link bug. [Download controller:5–15](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) independently rechecks ownership and expiry before conditional responses. Review cache lifetime/resource retention and avoid writing a negative TTL. If defaults later move to ≥7.1, the same input raises instead.

**Upstream:** [change and default gate](https://github.com/rails/rails/commit/0ae0ab7e3ff040e1b04c600944ba4f643954760a), [8.1 option normalization](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L908-L944).

### H8. Plaintext conversions change stored Markdown and CSV previews — Rails 8.1

**Before — Code:** plaintext conversion includes script/style text, and ordered-list numbering uses each node's position among **all** children, including whitespace nodes. **After — Code + commits:** script/style content is omitted; numbering uses the element's index among element siblings. The iterative rewrite also avoids recursive stack overflow.

**Application use:** [Import:101–106](file:///home/user/workspace/repo/app/models/import.rb#L101-L106) accepts arbitrary CSV `body_html`; [preview:56–58](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58) extracts plaintext; [Export:77–81](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) uses plaintext to build Markdown, which [Export:66–71](file:///home/user/workspace/repo/app/models/export.rb#L66-L71) persists as a blob.

**What could go wrong — Inference, conditional on content:** exports of the same notes differ after upgrading. A newline-separated `<ol>` can have its old whitespace-inflated numbering corrected; imported script/style text previously present in exports disappears. This is probably desirable, but it changes data formats/artifact contents without an exception. Existing completed blobs are not rewritten by the gem upgrade; newly generated exports use the new conversion. Inspect representative imported HTML, whitespace-separated lists and attachment captions before approving output changes. No production content demonstrating these cases was examined.

**Upstream:** [script/style omission](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057), [iterative conversion and changed list test](https://github.com/rails/rails/commit/0a5faeaf71745b05d937b579a4da5bd90e0b6b58), [final implementation](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/plain_text_conversion.rb).

### H9. Rich-text parsing adopts HTML5 independently of the sanitizer default — Rails 7.1

**Before — Code:** Action Text creates Nokogiri HTML4 documents to parse fragments. **After — Code:** it chooses HTML5 documents/fragments when Nokogiri provides HTML5, otherwise HTML4. This selection is **not gated by `load_defaults` or `config.action_text.sanitizer_vendor`**. HTML5 is expected on the locked native Linux Nokogiri build; other platforms must be checked separately.

**Application use:** [Note:8](file:///home/user/workspace/repo/app/models/note.rb#L8) persists Action Text bodies; [Import:105–106](file:///home/user/workspace/repo/app/models/import.rb#L105-L106) accepts external HTML; [note form:48–51](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L48-L51) edits it. Action Text's content constructor/canonicalization and serialization use these fragments.

**What could go wrong — Inference, content-dependent:** malformed/nested/table HTML can be normalized differently, affecting rendering, plaintext, attachment discovery and what gets written on a subsequent save. Keeping the **sanitizer** on HTML4 does not prove identical parsing or stored HTML. The upgrade itself is not a bulk rewrite of existing rows. Compare representative saved/imported content and attachment round trips, especially malformed fragments, before deciding the differences are acceptable.

**Upstream:** [parser-switch commit](https://github.com/rails/rails/commit/55bca6b8e85cbe719e748f4cd6acd2a8c2accb14), [final unconditional selection](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text.rb#L47-L60), [HTML conversion](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/html_conversion.rb). This finding comes from **source**, not a claim that the sanitizer changelog alone documents it.

### H10. Resolved JSON 3 rejects provider responses formerly accepted — transitive dependency

**Before — Changelog + Code:** the Ruby-default JSON 2.7.2 parser accepts duplicate object keys/comments and tolerates invalid string escapes that later releases reject. **After:** JSON 3.1.0 defaults reject duplicate keys/comments; the intervening 2.17 change rejects invalid escapes. It also removes unsafe object-creation facilities, but no application use of those was found.

**Application use:** [Provider:42–52](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) parses external JSON without compatibility options and converts `JSON::ParserError` to `Provider::Error`; [Citation:28–36](file:///home/user/workspace/repo/app/models/citation.rb#L28-L36) catches that and **stores a failed enrichment status/reason**.

**What could go wrong — Inference, conditional:** a successful HTTP 200 formerly accepted by this integration can now become a recorded enrichment failure rather than metadata. Duplicate title/url keys no longer silently select a value. This is a beneficial strictness/security change with a potentially silent application-level status change, not proof that this provider currently emits nonconforming JSON. Inspect actual provider fixtures/contract and decide whether rejection is desired. It is additional to the unconditional API-removal problem in M1.

**Upstream:** [JSON 3.1.0 changelog, including 3.0 and 2.17 changes](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), [new parser implementation](https://github.com/ruby/json/blob/v3.1.0/ext/json/ext/parser/parser.c).

## 3. Medium-risk changes

### M1. `Rails.application.secrets` is removed — Rails 7.2

**Before — Code:** `Rails.application.secrets` loads custom settings from `config/secrets.yml`. **After — Changelog + Code:** the API is removed, with no automatic migration of custom configuration into credentials.

**Application use:** [Provider initializer:1–14](file:///home/user/workspace/repo/app/models/citation/provider.rb#L1-L14) uses `Rails.application.secrets.citation_provider.to_h` as its default argument. [Citation#enrich:28–32](file:///home/user/workspace/repo/app/models/citation.rb#L28-L32) constructs the provider without explicit settings.

**What could go wrong — Inference, strong code evidence:** provider construction raises NoMethodError; it is not converted to the expected provider-domain error, and enrichment jobs cannot perform lookups. Choose whether environment-backed configuration should move to `config_for` with a custom file, direct environment access, or encrypted credentials; migrate the tests/configuration consistently. Simply renaming the reader to `credentials` does not migrate values.

**Upstream:** [7.2 Railties removal](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61), [7.1 deprecation](https://github.com/rails/rails/blob/v7.1.0/railties/CHANGELOG.md#L165-L177).

### M2. Built-in Sidekiq adapter is deprecated and removed in the next release — Rails 8.1 → 8.2

**Before — Code:** Rails supplies the Active Job adapter used with Sidekiq 6.5.12. **After — Changelog + Code:** 8.1 still supplies it but warns that it will be removed in **8.2**, recommending Sidekiq ≥7.3.3's own adapter. The current adapter accepts Sidekiq ≥4.1, so the present lock is **not rejected merely for remaining on 6.5.12**.

**Application use:** [application.rb:22–24](file:///home/user/workspace/repo/config/application.rb#L22-L24) explicitly selects `:sidekiq`; [Gemfile:34–36](file:///home/user/workspace/repo/Gemfile#L34-L36) pins the old gem/Redis client. Production [disables deprecation reporting:75–76](file:///home/user/workspace/repo/config/environments/production.rb#L75-L76), so absence of warnings there is not evidence of future compatibility.

**What could go wrong — Inference:** deferring the adapter decision makes the next Rails upgrade a queue-backend dependency migration as well. Decide whether to stage a Sidekiq upgrade or change backends; Sidekiq's own Redis/argument/adapter requirements need a separate review. Do **not** apply Sidekiq 7's stricter native-job argument rules to the current Rails-only resolution: [Notebook:25–26](file:///home/user/workspace/repo/app/models/notebook.rb#L25-L26) still enqueues its symbol-keyed export options through unchanged Sidekiq 6.

### M3. Today's JSON resolution conflicts with Rails 8.1.0's decoder and column coder — transitive dependency

**Before — Code:** JSON 2 accepts an options hash as the second positional argument and ignores unknown parser options. **After — Changelog + Code:** JSON 3 requires keyword options and rejects unknown options. Rails 8.1.0's `ActiveSupport::JSON.decode` still calls **`::JSON.parse(json, options)`**, even when options is empty; JSON 3.1.0's signature accepts only one positional argument. Separately, `ActiveRecord::Coders::JSON#load` supplies `{ escape: false }`, which is not a supported parser keyword even if the positional/keyword mismatch is corrected.

**Application use:** [Note:12,86–91](file:///home/user/workspace/repo/app/models/note.rb#L12-L91) serializes text-column tags using `JSON`; after the mechanical `coder: JSON` fix, Rails substitutes its JSON column coder. Active Storage's [Blob metadata declaration](https://github.com/rails/rails/blob/v8.1.0/activestorage/app/models/active_storage/blob.rb#L19-L25) uses the same coder, exercised by [Export:66–74](file:///home/user/workspace/repo/app/models/export.rb#L66-L74) and the [blob partial](file:///home/user/workspace/repo/app/views/active_storage/blobs/_blob.html.erb#L1-L12). The broader decoder mismatch also reaches native PostgreSQL JSONB [note settings/store_accessor:13](file:///home/user/workspace/repo/app/models/note.rb#L13) through `ActiveRecord::Type::Json`, and Rails' JSON cookie/message decoding paths; [ApplicationController:7–17](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L17) relies on the session cookie.

**What could go wrong — Inference from source call chains; not executed:** Rails JSON decoding is expected to raise **ArgumentError for two positional arguments instead of one**, not merely for bad stored JSON. Even after a keyword-forwarding fix, column-coder loads still need the unsupported `escape` option removed. Tags, settings and blob metadata can fail loading; cookie/token paths also need checking rather than assuming this is confined to one model. Bundler allows the combination because Rails' JSON dependency has no upper bound. Choose a tested compatible JSON 2.x constraint or a Rails version/compatibility change that addresses both mismatches; the requested 8.1.0 pin itself does not solve them. Confirm after authorization to install/run. A successful resolution is insufficient.
