## 2. High-risk changes

### H1. An invalid CSV import can commit its earlier rows — Active Record 7.2

- **History / framework code:** In 7.0.8.7, leaving a transaction block with a non-local `return` rolls back its writes. Rails 7.2 removes that behavior: non-local return commits unless there is an actual exception/rollback. Keeping 7.0 defaults does not retain it. See the [removal commit](https://github.com/rails/rails/commit/eccc6061f4f3abdfdeb9a363987a898418d9498f).
- **Application code:** [Import#apply:50–60](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) saves the import and preceding rows, then executes `return false` when a later note fails validation. [ImportsController:12–19](file:///home/user/workspace/repo/app/controllers/imports_controller.rb#L12-L19) renders an error preview, which says “Nothing has been saved.”
- **Inference:** A valid first row followed by an invalid second row leaves a partial import, notes, and associated records despite the failure response. The existing [all-or-nothing request test:48–72](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L48-L72) names exactly this case; it was read, not run. Make rollback explicit while preserving the method's false/error contract before upgrading.

### H2. Digest dates and selected notes switch from UTC days to reader-local days — Active Job 7.2

- **History / framework code:** The old `TimeWithZoneSerializer` stores an instant but deserializes in the job's current zone. The new serializer includes the named zone and restores it; old payloads without that field still fall back to the job's zone. See [PR #50240](https://github.com/rails/rails/pull/50240) and the [7.2 Active Job changelog](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md).
- **Application code:** [User#request_digest:34–41](file:///home/user/workspace/repo/app/models/user.rb#L34-L41) sends a reader-zone timestamp but reserves a UTC day. [DigestMailer:7–12](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L7-L12) derives both subject date and SQL date range from the deserialized timestamp.
- **Inference:** A request at 2026-10-05 03:30 UTC by an Eastern-time reader changes from an October 5 UTC digest to an October 4 Eastern-time digest. The reservation remains October 5 UTC, so the delivered window and deduplication rule disagree. Old/new payloads or workers can produce different windows. The existing [digest test:5–37](file:///home/user/workspace/repo/test/controllers/digests_controller_test.rb#L5-L37) exercises this boundary. Decide whether to preserve UTC-day digests explicitly or deliberately redesign both rules together.

### H3. New digest jobs cannot be decoded by Rails 7.0 workers — BigDecimal serialization

- **History / framework code:** Rails 7.0 treats BigDecimal as a primitive; a JSON-backed queue round-trip turns it into a string. Rails 7.1 introduced a tagged `BigDecimalSerializer` with an opt-in for rolling upgrades; 7.2 removed that compatibility switch and uses the serializer unconditionally. The [introducing commit explicitly describes old-worker failure](https://github.com/rails/rails/commit/bc1f3233384601fa8720ee164bced84ffbf3acf2); see also the [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md).
- **Application code:** [User:41,54–56](file:///home/user/workspace/repo/app/models/user.rb#L34-L56) queues a BigDecimal completion fraction through Sidekiq. [DigestMailer:10](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L10) already accepts the string/decimal conversion; that is not the main failure.
- **Inference:** A Rails 8.1 producer can enqueue a job a 7.0 worker cannot deserialize; rollback to 7.0 can strand such jobs too. A single-version test adapter does not establish rolling-deploy safety. Plan a compatible intermediate serialization phase or drain/isolate queues and coordinate producer/worker cutover. This is separate from the BigDecimal gem's arithmetic changes.

### H4. CSV receipt DOI fields become blank — custom primary-key reads removed in 7.2

- **History / framework code:** `read_attribute(:id)` and `record[:id]` previously redirected to a custom primary key. They now read the literal `id` attribute; `record.id` remains the primary-key accessor. See [7.1 deprecation](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md), [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md), and the [target primary-key test](https://github.com/rails/rails/blob/v8.1.0/activerecord/test/cases/primary_keys_test.rb#L48-L53).
- **Application code:** [Import#receipt:63–69](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) exports `citation[:id]`; [citations' schema:55–62](file:///home/user/workspace/repo/db/schema.rb#L55-L62) has only the DOI primary key, not an `id` column.
- **Inference:** Receipt generation succeeds but silently emits empty DOI cells. Use `citation.doi` or `citation.id` to retain the existing export contract. The [receipt assertion:43–45](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L43-L45) covers the desired output.

### H5. CSV preview annotations disappear — indifferent-hash stringification in 8.0

- **History / framework code:** `HashWithIndifferentAccess#stringify_keys` used to preserve integer keys; it now stringifies all keys. Upstream deliberately did not backport this long-standing behavior change: [PR #53125](https://github.com/rails/rails/pull/53125), [8.0 changelog](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md#L30-L45).
- **Application code:** [Import#annotations:38–40](file:///home/user/workspace/repo/app/models/import.rb#L38-L40) keys annotations by integer source-line number. The [preview:22,42–44](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) stringifies the hash but still indexes it with `row.line`, an integer.
- **Inference:** Integer lookups return nil and annotations silently vanish from the preview; persisted note annotations are not deleted. Keep integer keys or consistently use string keys. The [existing preview assertions:21–24](file:///home/user/workspace/repo/test/controllers/imports_controller_test.rb#L21-L24) already express the visible contract.

### H6. “24 hours later” reminder previews change across DST — `to_time` in 8.1

- **History / framework code:** With this app's old defaults, `TimeWithZone#to_time` returned a Ruby Time with a fixed UTC offset. Rails 8.1 always preserves the full timezone object; setting the former preservation option no longer restores offset-only behavior. See [8.1 removal/deprecation](https://github.com/rails/rails/blob/v8.1.0/activesupport/CHANGELOG.md#L15-L22) and [target implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb#L497-L499).
- **Application code:** [Note:35–44](file:///home/user/workspace/repo/app/models/note.rb#L35-L44) adds 86,400 seconds to `reminder_at.to_time`; the [reminder partial:17–19](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L17-L19) displays the result.
- **Inference:** Starting at October 31, 2026, 09:00 Eastern, the next-day preview changes from November 1 09:00 −04:00 to November 1 08:00 −05:00. **The instant and postponed epoch do not change**: [postpone_reminder:71–72](file:///home/user/workspace/repo/app/models/note.rb#L71-L72) uses `to_i`. The displayed-time contract does change, as documented by [the current assertion:19–21](file:///home/user/workspace/repo/test/controllers/reminders_controller_test.rb#L19-L21). Decide whether the improved local-zone display is desired rather than accidentally changing scheduling to “same wall-clock time tomorrow.”

### H7. Expired export fragments lose their expiration — negative cache TTL handling in 7.1

- **History / framework code:** Previously a negative `expires_in` made an already-expired cache entry. New code removes the negative option and reports/logs an error, or raises if `raise_on_invalid_cache_expiration_time` is enabled. With retained 7.0 defaults it reports, then uses the store's default expiration—none in this configuration. See the [7.1 cache changelog](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md) and [target option handling](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb#L909-L944).
- **Application code:** The [export partial:25–36](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L36) always passes `export.expires_at - Time.current`, including when viewing an expired export.
- **Inference:** An expired indicator can become a non-expiring fragment, accumulating FileStore entries and error reports instead of being immediately expired. This is **not a demonstrated download-authorization bypass**: [ExportDownloadsController:5–15](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L5-L15) checks authoritative expiry independently. Adopting 7.1 defaults later turns this same path into an exception. Avoid passing a negative TTL, for example by not caching already-expired indicators.

### H8. Local sessions and stored attachment signatures can become invalid — conditional on signing-key setup

- **History / framework code:** Rails 7.0 development/test use `tmp/development_secret.txt`; later Rails uses `tmp/local_secret.txt`, and 8.1 checks `SECRET_KEY_BASE`/credentials before the local fallback. The [upgrade guide explicitly warns about broken sessions and attachments](https://github.com/rails/rails/blob/v8.1.0/guides/source/upgrading_ruby_on_rails.md#L169-L179); the [target key lookup](https://github.com/rails/rails/blob/v8.1.0/railties/lib/rails/application/configuration.rb#L526-L545) supplies the precedence detail.
- **Application code:** Authentication uses the Rails session ([ApplicationController:7–17](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L17)); rich text contains signed blob references ([Note:8,95–97](file:///home/user/workspace/repo/app/models/note.rb#L8-L97), [attachment test:20–25](file:///home/user/workspace/repo/test/models/note_test.rb#L20-L25)). Local Disk data persists between boots.
- **Inference / uncertainty:** If the effective key changes, local sign-ins are lost and existing rich-text attachments can render as missing. Actual keys and secret environment values were deliberately not inspected. Preserve the effective old key or plan verification-key rotation where appropriate; merely renaming a file is insufficient if a different environment/credentials key takes precedence. **No production key rotation is implied by the gem upgrade** when the same configured production key is retained.

### H9. Plain-text exports and previews change for imported HTML — Action Text fixes

- **History / framework code:** Two source-diff findings affect `to_plain_text`: (a) script/style contents, previously included as text, are now omitted ([commit](https://github.com/rails/rails/commit/bd0729ce37310c737e163c4f3f76db80d4c63057)); (b) ordered-list numbering now indexes element siblings rather than all sibling nodes, as part of an iterative traversal that also prevents stack overflow ([commit](https://github.com/rails/rails/commit/0a5faeaf71745b05d937b579a4da5bd90e0b6b58)). These differences are in the exact released-source comparison, not inferred from a generic sanitizer upgrade.
- **Application code:** Arbitrary CSV HTML enters at [Import:101–108](file:///home/user/workspace/repo/app/models/import.rb#L101-L108), previews call `to_plain_text` at [preview:56–58](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L56-L58), and stored Markdown exports use it at [Export:77–81](file:///home/user/workspace/repo/app/models/export.rb#L77-L81).
- **Inference:** Newly generated exports of the same stored note can differ: embedded script/style source disappears, and whitespace-separated ordered-list items no longer get numbering inflated by intervening text nodes. This is generally an improvement, but it changes a persisted/downloadable representation without an error. Review representative imported HTML before accepting new export expectations. Existing exported files are not rewritten. The presence of affected stored HTML is unverified.

### H10. Content attachments have a different HTML/data contract — conditional on imported/stored attachment markup

- **History / framework code:** The old `ContentAttachment` recognizes special `vnd.rubyonrails.*.html` attachments, including a named horizontal rule. The new implementation accepts HTML content types with a nonblank `content` attribute and renders that content; editing also sanitizes the attribute. See the [7.1 Action Text change](https://github.com/rails/rails/blob/v7.1.0/actiontext/CHANGELOG.md), [7.2 sanitization fix](https://github.com/rails/rails/blob/v7.2.0/actiontext/CHANGELOG.md), and [target class](https://github.com/rails/rails/blob/v8.1.0/actiontext/lib/action_text/attachables/content_attachment.rb).
- **Application code:** [Note:8](file:///home/user/workspace/repo/app/models/note.rb#L8), [CSV assignment:101–108](file:///home/user/workspace/repo/app/models/import.rb#L101-L108), [rich-text editor:48–51](file:///home/user/workspace/repo/app/views/notes/_form.html.erb#L48-L51), and [Markdown conversion:77–81](file:///home/user/workspace/repo/app/models/export.rb#L77-L81) expose these formats without an application-specific attachment adapter.
- **Inference / uncertainty:** Legacy special attachment markup lacking `content` can become a missing attachment; equivalent new HTML-content input can be rendered/exported differently. This applies to content attachments, **not every ordinary signed blob attachment**. No fixtures prove use of that special format, and no production rows were inspected; treat this as a targeted stored-content check, not a confirmed incident. The explicit Trix 1.3.5 override also needs an intentional editor-version decision rather than assuming the newly resolved Trix gem is being served.

### H11. Some database reads now reconnect and retry instead of surfacing connection failure

- **History / framework code:** Rails 7.2 permits retrying known-idempotent Arel SELECTs; 8.1 extends this to association and existence queries. PostgreSQL's “no connection to the server” `PG::UnableToSend` is classified as retryable. See [7.2 Active Record history](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md), [8.1 association-query change](https://github.com/rails/rails/blob/v8.1.0/activerecord/CHANGELOG.md#L582-L591), and [target reconnect/retry implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/connection_adapters/abstract_adapter.rb#L1049-L1113). Default connection retries are one and no retry deadline is configured here.
- **Application code:** This reaches normal model/association reads, such as [current-user lookup:7–8](file:///home/user/workspace/repo/app/controllers/application_controller.rb#L7-L8) and [notebook lookup:10–11](file:///home/user/workspace/repo/app/controllers/notes_controller.rb#L10-L11), under [database.yml:17–22](file:///home/user/workspace/repo/config/database.yml#L17-L22).
- **Inference:** During a disconnect/failover, a request can take longer and succeed after reconnecting rather than expose the first error; a later read can observe newer data. This is normally desirable resilience but is a silent connection/error-handling change under the requested high-risk rubric. It is **not** evidence that arbitrary writes, the app's transaction blocks, or its mail delivery will be replayed: retries are constrained by query safety and restorable connection/transaction state. Review timeout and failure-observability expectations if those matter operationally.

## 3. Medium-risk changes

### M1. Citation provider configuration uses the removed `Rails.application.secrets` API

- **History:** Deprecated in 7.1, removed in [Rails 7.2](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md#L61-L63).
- **Application code / before:** [Citation::Provider:13–14](file:///home/user/workspace/repo/app/models/citation/provider.rb#L13-L14) reads `secrets.citation_provider`; [secrets.yml:6–18](file:///home/user/workspace/repo/config/secrets.yml#L6-L18) maps environment variables into those settings. [Provider tests:117–122](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L117-L122) also mutate that API.
- **After / inference:** Default provider construction raises `NoMethodError` instead of resolving settings. Enrichment can remain pending while jobs fail/retry. The fix requires choosing credentials, ordinary environment-backed configuration, or `config_for`, not just renaming a method. Preserve `CITATION_PROVIDER_*` deployment semantics, literal credential strings, and the local stand-in settings; update the test seam to match that decision.

### M2. The built-in Sidekiq adapter is deprecated and disappears in Rails 8.2

- **History / framework code:** Rails 8.1 still ships the adapter but warns it will be removed in 8.2; upstream directs users to Sidekiq **7.3.3 or newer**, which provides its own adapter ([8.1 changelog](https://github.com/rails/rails/blob/v8.1.0/activejob/CHANGELOG.md#L19-L23), [adapter warning](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb#L36-L41)).
- **Application code / before:** [application.rb:24](file:///home/user/workspace/repo/config/application.rb#L24) selects that adapter; [Gemfile:35–36](file:///home/user/workspace/repo/Gemfile#L35-L36) pins Sidekiq 6.5.12 and redis 4.8.1. Before, this was a supported built-in path without the removal warning.
- **After / inference:** The Rails-only resolution **does not upgrade Sidekiq** or remove the adapter yet. Plan a separate Sidekiq/Redis-client compatibility decision before Rails 8.2, especially for [direct Redis reservation operations](file:///home/user/workspace/repo/app/models/user.rb#L34-L44) and [native export enqueueing](file:///home/user/workspace/repo/app/models/notebook.rb#L24-L29). This is medium because removal is announced for the next release, not a claim that Sidekiq 6.5 cannot resolve with Rails 8.1.

### M3. The newly resolved JSON 3.1 parser rejects previously accepted provider responses

- **History / dependency code:** Compared with Ruby's bundled JSON 2.7.2, JSON 3 changes defaults to reject duplicate object keys and JavaScript comments; intermediate versions also stopped ignoring invalid string escapes. See [JSON 3.1.0 change history](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md), including the 3.0.0 and 2.17.0 entries.
- **Application code / before:** [Provider#metadata_from:42–52](file:///home/user/workspace/repo/app/models/citation/provider.rb#L42-L52) calls plain `JSON.parse`; old permissive parsing could accept those responses and use the resulting title/URL.
- **After / inference:** Those inputs now raise `JSON::ParserError`, which the application turns into a visible failed enrichment through [Citation#enrich:28–36](file:///home/user/workspace/repo/app/models/citation.rb#L28-L36). Decide whether the provider must send strict JSON or whether narrowly scoped compatibility options are warranted. No evidence shows the real provider sends these inputs, so the impact is conditional. Ordinary generated tag arrays and job hashes do not demonstrate this problem; their behavior should not be called broken merely because JSON has a new major version.

## 4. Low-risk / mechanical changes

Each line includes the affected call and direct replacement or bounded effect. Low here does **not** mean “the application boots unchanged.”
