# Margin Notes: Rails 7.0.8.7 → 8.1.0 assessment

**Decision: feasible, but not a Gemfile-only upgrade and not ready to deploy.** Keep `config.load_defaults 7.0` for the first framework upgrade, prepare portable fixes on 7.0, and use 7.1 → 7.2 → 8.0 → 8.1 checkpoints. Adopt new defaults separately, after the rollback window closes. Ruby 3.3.6 already satisfies Rails 8.1.0's >=3.2 requirement.

No working application source, dependency lockfile, database, queue, cache, or storage was changed. Experiments used disposable archives of [the inspected application revision](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7), private databases, a dedicated Redis server, and copy-local runtime/storage directories. The only repository metadata addition is the required local exclusion for `/.amp/in/`; all deliverables are ignored artifacts.

### Critical behavior: atomic CSV imports

Affected: [Import#apply:50–61](file:///home/user/workspace/repo/app/models/import.rb#L50-L61). On a later invalid row it exits a transaction with `return false`. Rails 7.2 removed rollback-on-non-local-return behavior. This is **not protected by keeping load_defaults 7.0** on 8.1.

**E:** outside fixture transactions, a CSV whose first row is valid and second has a blank title returns false on both versions. Baseline persists 0 imports/0 notes; target persists **1 import and the first note**. This is actual partial data loss of the promised atomicity, not merely a changed return value. Existing HTTP tests stop at the missing-preview-annotation assertion before exercising this path.

**Recommendation:** explicitly raise `ActiveRecord::Rollback` on an unsaved row and return a separately preserved false outcome, or return the transaction's explicit success value with false for rollback. Preserve row validation errors for the preview. Do not use a block-local break/throw as a rollback substitute. **This preparation works on 7.0**; ActiveRecord::Rollback is supported there. This recommendation was source-reviewed, not implemented/tested as a repaired variant.

**P:** public apply endpoint with first valid row introducing a citation and attachment, later invalid row; counts for Import, Note, Citation and ActionText records must all remain unchanged. Repeat with first row invalid, all valid, and a database constraint failure. Audit any real imports attempted by a newer deployment before a rollback; a binary rollback cannot undo already committed partial batches.

### Critical behavior: digest days and job formats

Affected: [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L44), [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb), [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L10).

1. **TimeWithZone now retains the sender's zone.** **E:** 2026-10-05 03:30 UTC sent as 2026-10-04 23:30 America/New_York becomes UTC October 5 in a 7.0 worker but stays local October 4 in 8.1. The mailer's `.to_date` and `.all_day` consequently switch date and note membership while the Redis reservation is still October 5 UTC. Existing digest test detects the subject change. This is an unconditional serializer change, not a new-default toggle.
2. **BigDecimal has a structured serializer.** **E:** the real 7.0 Sidekiq payload stores completion as `"0.6667"`; 8.1 stores `_aj_serialized: ActiveJob::Serializers::BigDecimalSerializer`. The 8.1 reader accepts the old string. The 7.0 reader fails on the new serializer with ActiveJob::DeserializationError. A passing test adapter run would not establish real JSON compatibility; both were explicitly exercised. [Serializer sources][twz81], [7.1 transition guidance][aj71].

**Recommendation, portable to 7.0:** normalize the mailer's received requested_at to UTC **before both** the date and all_day calculation; also enqueue a UTC Time and completion as an explicit decimal string (e.g. `.to_s("F")`). Consumer normalization matters for already-queued zoned payloads, not just new requests. The mailer already uses BigDecimal to parse completion, so a string preserves the production contract. Keep digest reservation keys/TTL stable and do not flush Redis to address a format problem.

**P:** JSON-backed mixed-writer/mixed-reader matrix, with a two-thirds completion and non-UTC times on both sides of UTC/local midnight, plus notes that distinguish the UTC day from the reader's day. Verify subject, exact membership, percentage and duplicate-request behavior. Old already-queued jobs must still run. If structured BigDecimals were already emitted, do not roll back workers to bare 7.0 until those payloads are consumed, quarantined for compatible workers or compatibly re-encoded. Scheduled/retry/dead sets count, not just the ready queue.

Alternative staged route: 7.1 readers understand the new decimal serializer but initially emit the legacy form; deploy those readers everywhere first, then enable the serializer, then advance to 7.2+. This does **not** make a rollback to unprepared 7.0 safe. The explicit-string preparation avoids this dependency altogether.

### Required behavior decision: reminder preview across DST

Affected: [Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L45), [reminder view](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20). Rails 8.1's TimeWithZone#to_time retains the actual zone, not merely the current fixed offset.

**E:** starting October 31, 2026 at 09:00 -04:00, adding 86,400 seconds yields November 1 **09:00 -04:00** on 7.0 and **08:00 -05:00** on 8.1. Both represent the same instant and postpone by exactly 24 elapsed hours. The displayed wall time/offset changes; the current request test expressly expects the old preview. Retaining load_defaults 7.0 does not restore the old conversion.

**Recommendation:** intentionally show the postponed instant in the reader's zone using `reminder_at + 24.hours`, update the fixed-offset test/documentation, and retain the elapsed-hours scheduling contract. This expression works on 7.0 too but is an intentional display change. If exact current output is instead required, use an explicit fixed-offset Time such as `reminder_at.to_time.getlocal(reminder_at.utc_offset) + 86_400`. Do not use `1.day` and accidentally change elapsed duration. **P:** both spring and autumn transitions, compare displayed offset/wall time **and** enqueued epoch. [8.1 removal][rn81], [to_time source][twzsource].

### Dependency-resolution finding: JSON 3

**E:** conservative `bundle update rails` selected json 3.1.0, allowed by the target gemspec. The app's sessions and Note.settings jsonb then fail in ActiveSupport::JSON.decode because [Rails 8.1.0 passes parser options positionally][jsondecode]. That parser no longer accepts the second positional argument. Pinning `json < 3` in the experiment resolved 2.21.2 and removed those errors. This is a reproducible dependency interaction, not a general claim that 8.1 cannot handle JSON.

**Recommendation:** for the exact requested 8.1.0, constrain JSON below 3 and retain/review the resolved lockfile. Do not silently substitute a newer Rails patch to hide the result; evaluate such a target separately. A JSON <3 constraint is compatible with the current Ruby/7.0 parser use, but was not tested as a new baseline dependency variant. **P:** session login/logout, settings jsonb, tag JSON, citation response JSON, and a clean lockfile reinstall on each deployment platform. Do not rely on a transient installed-gem set.

2. Stabilize digest **consumer** UTC semantics and **producer** UTC Time/decimal-string arguments; retain job class names and GlobalID identifiers. Validate the live JSON boundary, not only the in-memory adapter. Decide/test DST preview presentation without changing 86,400-second postponement.
3. Preserve tags as JSON text and preferences as YAML text. Inventory/anonymize representative old rows, Action Text bodies, SGIDs, blob metadata/files, export files and expiration state. Snapshot database **and** local Disk storage coherently; a database backup alone does not restore attachment files. Do not purge preexisting blobs or scheduled reminders as part of the framework upgrade.
4. Record secret_key_base provenance without revealing its value. Local 7.0 uses `tmp/development_secret.txt`; 7.1+ uses `tmp/local_secret.txt` when generating a local key. Preserve the key on the development instance if existing local attachments/cookies matter. Production must retain exactly the existing effective key when moving away from secrets; its actual credential source was not inspected/decrypted.

### Phase B — framework checkpoints, old defaults retained

1. On upgrade branches/disposable environments, move through latest suitable patch releases of 7.1, 7.2 and 8.0, then the exact requested 8.1.0. Resolve/review each lockfile and deprecation log. At 7.1 change serialization to coder keywords, test exception mode to :none and retry wait symbol to :polynomially_longer. These are not cross-compatible drop-in edits on 7.0. Run/review `bin/rails app:update` rather than accepting generated replacements over app configuration.
2. At target constrain JSON <3 and keep `load_defaults 7.0`. Review security/patch advisories for the exact requested release before real deployment; this assessment is not an audit or endorsement of shipping an old .0 patch in 2026.
3. Before shared-service rollout, take the planned coherent backup and export a **non-destructive inventory** of Sidekiq queue/schedule/retry/dead sets and job class/argument formats. Use compatible readers first, then producers. Coordinate workers and web processes; stopping ready queues alone doesn't drain long-lived scheduled reminders. Run old-writer/new-reader and new-writer/rollback-reader cases with actual job envelopes and SGIDs.
4. Canary sign-in, notes/search/highlights/tags/rich text, import previews + failed apply + receipts, activity reports, reminders across DST, UTC digests, citation failure/retries, and export generation/cancel/download/cache/expiry. Complete unit/request, eager-load, production build and browser gates before declaring ready.

### Phase C — defaults, separate deployments

After all readers have upgraded and rollback requirements are explicit, adopt reviewed 7.1, 7.2, 8.0 and 8.1 defaults in small deployments. First satisfy section 3 prerequisites. Keep legacy message metadata/writers/cache format while a bare 7.0 rollback is still required, or provide a tested compatibility bridge. Do not treat a one-way old→new success as a rollback guarantee.

### Rollback constraints

- Before new defaults/wire formats, rollback to the **prepared** 7.0 app should preserve JSON tags, YAML preferences, integer enum values, DOI foreign keys, epoch seconds, native ExportJob arguments and original Active Storage files. This is the recommended design; a full deployment rollback has **not** been executed.
- New structured decimal jobs cannot be handed to bare 7.0. Keep compatible workers or transform only verified synthetic-tested payloads; don't clear Redis, delete scheduled reminders or discard digest reservations. New job wrapper names from a future Sidekiq upgrade need their own compatibility check.
- New signing envelopes can break rollback readers. Embedded Action Text SGIDs and permanent blob redirect URLs may outlive sessions; a brief cookie grace period is insufficient. Preserve old writer configuration or keep a compatibility bridge for as long as those references remain. Regenerating stored signed references, if chosen, is a separate audited data change with backup and an inverse plan.
- Shared cache entries are disposable, unlike queues, reservations, SQL rows and storage. Retain a compatible writer format or use an isolated cache namespace per generation; only explicitly disposable cache data may be expired. The checked-in production config does not specify a shared Redis cache; don't confuse its Sidekiq Redis with one.
- Partial imports, edited rich-text markup, delivered mail and completed external requests cannot be undone by reverting gems. Repairing any effects needs its own authorized data reconciliation. Existing mail delivery and attachment access limitations are not caused by this upgrade and are not silently fixed here.

## 6. Completion gates and remaining questions

**Go/no-go gate:** a corrected target must pass the existing 46-test suite, new atomic-import/real-wire regressions, mixed-version compatibility matrix, eager-loading, production-like asset boot/build, and browser workflows. Current target experiments intentionally remain red; no upgrade implementation has been supplied.

Before deployment, determine: actual production secret source and stable key; process topology and shared cache backend; provider configuration; database/server versions and data samples; real queued/scheduled/retry/dead payload inventory; shared/local file-storage topology; required rollback duration; and whether to adopt newer Trix or preserve it as a separate task. Production mail host/delivery are not configured in this sample, so a genuine delivery test requires explicit staging configuration. No need to block local planning on those answers, but they block a production readiness claim.

Initial signature experiments used unequal keys: Rails 7.0 test ignored ENV SECRET_KEY_BASE and generated its local key. Experiments use schema loads, not a historical-data migration rehearsal.
