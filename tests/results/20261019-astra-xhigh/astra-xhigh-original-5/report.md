# Margin Notes: Rails 7.0.8.7 → 8.1.0 assessment

**Recommendation: proceed as a staged compatibility upgrade, not a Gemfile-only deployment. Keep `config.load_defaults 7.0` initially.** There are unconditional API removals and behavioral changes even with old defaults; adopt later defaults separately. No working application files were changed. Diagnostic changes were made only in disposable copies.

The highest-risk findings are **partial CSV imports**, **changed digest calendar days and incompatible queued BigDecimal arguments**, **serializer changes that can silently write a different database format**, and **persistent attachment signatures that must survive rollout and rollback**.

## Scope and evidence

Inspected the actual controllers, models, jobs, mailers, views, routes, initializers, schema/migrations, locked dependencies, tests, and repository guidance. Compared Rails tags **7.1.0, 7.2.0, 8.0.0, 8.1.0**, plus installed 7.0.8.7 source, rather than treating current upstream `main` as the target. Sources are linked below.

Evidence labels:
- **Executed:** exercised in the isolated variants described below.
- **Source:** determined from application and versioned framework code, not a successful application execution of the proposed fix.
- **Proposed:** a release gate still to execute; not claimed as passing.

## 1. Runtime and dependency plan

The checked-out Gemfile and lockfile agree with the request: Rails **7.0.8.7**, Ruby **3.3.6**, PostgreSQL driver **1.6.0**, Puma **5.6.9**, Sidekiq **6.5.12**, redis-rb **4.8.1**, Pagy **8.6.3**, Faraday **1.10.4**. `config/application.rb:12` loads **7.0 defaults**.

- **No required Ruby upgrade:** Rails 8.1.0's gemspec requires Ruby ≥ 3.2.0; 3.3.6 satisfies it. Keep Ruby fixed while upgrading Rails. The disposable database server was PostgreSQL 15.19; the deployed PostgreSQL/Redis versions remain unverified.
- **No inherent Rack 3 / Sidekiq 7 / Puma 6 requirement:** Action Pack 8.1.0 permits Rack ≥ 2.2.4. The executed resolver retained Rack **2.2.24**, Puma **5.6.9**, Sidekiq **6.5.12**, redis-rb **4.8.1**, selecting rack-session **1.0.2** and rackup **1.0.1**. Keep these upgrades separate unless deployment testing identifies a concrete need. Dependency resolution alone does not certify the worker/server combination.
- **Required constraint for the exact requested target with today's resolution:** Rails 8.1.0 introduces an unconstrained `json` dependency; this experiment resolved **3.1.0**, whose keyword-only options break Active Support 8.1.0's positional `JSON.parse(json, options)` call. This affected sessions, tags, and Active Storage metadata. Constrain JSON to a verified 2.x release (`json < 3` resolved 2.21.2 here), commit the lockfile, and check dependency/security policy before delivery. Do not silently substitute a different Rails version. This constraint is compatible in intent with 7.0's JSON 2.7.2 runtime, but the full 7.0 suite with 2.21.2 was not run.
- Keep the current concurrent-ruby pin during the 7.0 preparation stage; removing it can introduce the older Rails/logger loading problem. No reason to mix that cleanup or Minitest 6 adoption into this upgrade.

**Discriminating validation:** install from the candidate lockfile on the deployment OS; decode existing JSON tags and blob metadata, sign in and follow the session cookie, perform a native export and an Active Job through a real isolated Sidekiq worker, start Puma, and precompile/serve assets. Retain `bundle list`/lockfile and Ruby/Redis/PostgreSQL versions. See [dependency source](https://github.com/rails/rails/blob/v8.1.0/actionpack/actionpack.gemspec), [Ruby requirement](https://github.com/rails/rails/blob/v8.1.0/rails.gemspec), [JSON call](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb), and [JSON 3 changes](https://github.com/ruby/json/blob/v3.1.0/CHANGES.md).

### C. Imports: atomicity, annotations, and receipt data

1. **Required, high priority — transaction semantics.** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) returns from inside `transaction` when a row cannot save. Rails 7.0 rolls back this nonlocal exit; Rails 7.1 new defaults opt into commit and **7.2 removes rollback-on-return altogether**. Keeping 7.0 defaults does not protect 8.1. **Executed:** valid first row + invalid second row returned false in both versions, but 8.1 persisted one Import, Note, Citation and RichText; 7.0 persisted none.
   - **Recommendation:** abort with `ActiveRecord::Rollback`, and make the transaction's success result determine the method's boolean result. For example, put `true` at the end of the transaction block and return `transaction { ...; raise ActiveRecord::Rollback unless row.note.save; ...; true } == true`. Do not raise Rollback but retain an unconditional `true` after the transaction.
   - **7.0 preparation:** yes; explicit rollback is supported. Preserve row validation errors for preview. No data migration is needed, but rollback of application code cannot undo partially imported data already accepted by an unsafe release.
   - **Validation:** bypass preview and POST a batch whose first row creates a new DOI/rich body and whose second row fails. Assert all four record counts unchanged and row errors still displayed. Repeat with failure after more than one valid row and with a genuinely valid batch. Existing test assertions fail earlier on missing annotations in 8.1, so they did not reach the atomicity assertion. [7.2 change](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md).

2. **Required — preview annotations disappear.** [Import#annotations](file:///home/user/workspace/repo/app/models/import.rb#L37-L42) has integer source-line keys. [Preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys` but then indexes by integer. Rails 8.0 now actually stringifies integer keys in HashWithIndifferentAccess. **Executed:** lookup becomes nil.
   - **Recommendation:** remove `stringify_keys` and keep the integer-keyed map through this view (or consistently use string keys at both ends). **7.0:** yes. No stored annotation migration.
   - **Validation:** two different annotations at lines 2 and 4 with a blank line and a quoted multiline field; show both on the correct row, escaped as plain text, then verify persisted annotations. [8.0 change](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md).

3. **Required — receipt DOI silently becomes blank.** [Import#receipt](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) uses `citation[:id]`, but `citations.doi` is the primary key and there is no `id` column. Rails 7.2 removed this `read_attribute(:id)` fallback. **Executed:** note retained its DOI but receipt CSV emitted an empty DOI.
   - **Recommendation:** use `citation&.doi` (or the supported primary-key reader `.id`). **7.0:** yes. Preserve DOI spelling/case; do not introduce normalization as part of the upgrade.
   - **Validation:** download a receipt with repeated DOI, a differently cased DOI and an uncited row; assert exact corresponding cells. Stored references need no schema change. [7.2 removal](https://github.com/rails/rails/blob/v7.2.0/activerecord/CHANGELOG.md).

### D. Reminders and digests: preserve instants, days, and queue compatibility

**Reminder scheduling — required.** [Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L56-L68) supplies an integer `reminder_epoch` as `wait_until`. Rails 7.2 removes numeric `scheduled_at`; 8.1 serialization calls `.utc.iso8601`. **Executed:** `undefined method utc for Integer`.
- Pass `Time.at(reminder_epoch).utc` to `wait_until`; leave the stored epoch column and reminder job-id deduplication intact. **7.0 preparation: yes.**
- Validate imported epoch **1,793,451,617**, not a round-hour-only input; assert the exact Sidekiq scheduled timestamp, past-time behavior, rescheduling, stale-job no-op, deleted note discard, and failed enqueue retaining previous reminder state. Existing tests use only the test adapter; a real JSON-backed queue remains a gate.

**Digest calendar day — required to retain the application's UTC-day contract.** [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L34-L56) reserves a UTC Redis date but passes a reader-zoned TimeWithZone. [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L2-L10) implicitly trusts deserialization to convert that argument to UTC. Rails 7.2 preserves the serialized named time zone.
- **Executed:** request at 2026-10-05 03:30 UTC / October 4 23:30 New York changes the digest subject from October 5 to October 4, while reservation still belongs to October 5. The content query also changes to the local day.
- **Recommendation:** normalize `requested_at` to UTC **inside the mailer/job consumer before both `to_date` and `all_day`**, and preferably send a UTC time from the publisher as well. Consumer normalization is essential for work already queued. **7.0 preparation: yes.** Do not change the reservation key or switch only the subject.
- **Validation:** notes on either side of UTC midnight and local midnight, in both east- and west-of-UTC zones; use real JSON transport and legacy/new payloads; assert date, included/excluded note titles, and one reservation per UTC date.

**BigDecimal serialization — required mixed-version policy, not a need to rewrite the mailer.** Active Job 7.1 introduces BigDecimalSerializer (initially opt-in); 7.2 always uses it, and 8.0 removes the compatibility configuration. **Executed:** 7.0 sends JSON string `"0.6667"`; 8.1 sends a serializer-tagged object and restores BigDecimal. Old 7.0 cannot load that serializer. `BigDecimal(params[:completion])` already accepts the new value on this Ruby; converting it there alone does not solve deserialization failure.
- **Recommendation:** prepare 7.0 producers to enqueue `reading_completion.to_s("F")`, keeping a stable decimal string contract during the entire upgrade/rollback window. Keep consumer acceptance of strings and BigDecimal. **7.0 preparation: yes.** Do not convert to Float and lose exact decimal meaning.
- If new-format jobs have already been written, stop old consumers; retain a compatible worker until those jobs and retries finish, or deploy a specifically tested backward reader before rollback. A 7.1-only `use_big_decimal_serializer = false` switch is **not** an 8.1 solution.
- **Validation:** 2-of-3 ready notes, and all producer/consumer combinations (7.0→7.0, 7.0→8.1, 8.1→8.1, 8.1→7.0) through actual JSON queue transport. Include retry payloads, not only freshly constructed job arguments. Existing Active Job tests never exercised Sidekiq's JSON conversion.

**DST preview — mandatory behavior decision, not a scheduling-instant regression.** [next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L40-L45) uses `reminder_at.to_time + 86_400`. In 8.1 `to_time` always preserves the receiver's named zone; the former offset-preserving behavior is gone even with old defaults.
- **Executed:** October 31 09:00 −04:00 previews November 1 **08:00 −05:00** rather than **09:00 −04:00**. Both are exactly 86,400 seconds later. Keeping the existing display would require explicitly converting to a fixed-offset Ruby Time, e.g. `time.utc.getlocal(time.utc_offset)`, before addition; this works on 7.0 too.
- **Recommendation:** retain “24 elapsed hours”, accept the new accurate reader-zone display, and update the old-offset expectation/documentation deliberately. A portable `reminder_at + 24.hours` can make that intent explicit on 7.0 as a separately reviewed behavior change. Do not use `1.day` to mean 24 elapsed hours across DST.
- **Validation:** spring-forward and fall-back, assert both the exact epoch delta and displayed offset/wall-clock value. [job changes](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [8.1 time implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb).

### E. Expired export fragments — fix even before changing defaults

[The export partial](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L37) supplies `expires_in: export.expires_at - Time.current`. Expired exports therefore pass a negative TTL.
- **Executed:** Rails 7.0's MemoryStore immediately misses after a negative-TTL write. Rails 8.1 with old defaults reports the invalid TTL, drops the expiration option and retains the value; with 7.1+ strict-expiration defaults it raises ArgumentError. Thus this is **not solely an optional-default exception**.
- **Recommendation:** never pass a negative TTL. A minimal compatible choice is `expires_in: [export.expires_at - Time.current, 0].max`; alternatively do not cache the already-expired branch. **7.0 preparation: yes.** Do not merely suppress the warning or turn off strict validation.
- **Validation:** caching enabled, cold and warm fragments just before, at, and after the deadline; an already-expired export must render without an exception and without an unbounded-expiry write. The download still must recheck ownership and `downloadable?` before any 304. The current cache test does not inspect the rewritten expired entry's TTL. [cache implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/cache.rb).

## 4. Assets, stored rich text, and signatures

[Layout](file:///home/user/workspace/repo/app/views/layouts/application.html.erb#L9-L14) explicitly loads vendored **Trix 1.3.5**; [importmap](file:///home/user/workspace/repo/config/importmap.rb#L8) loads Action Text from the installed Rails gem. Upgrading Rails therefore does **not** automatically upgrade the editor this application actually loads. This resolution installed `action_text-trix 2.1.19` via Action Text 8.1's `~> 2.1.15` dependency, but the layout still names the old vendor file.

- **Recommendation:** treat editor alignment as an explicit browser-validated part of the candidate, not an assumed effect of Bundler. Either establish that the retained editor works with the new Action Text bridge, or switch the layout/assets coherently to the supported resolved Trix version, without loading two editors. Do not remove the old script before testing replacement imports/assets. This was **not browser-tested**; no claim that Trix 1.3.5 necessarily breaks solely because of the Rails change.
- **Current compatibility:** do not assume a Trix 2 asset change is a safe 7.0 preparatory deployment; test that combination separately or do it with the target. Keep Sprockets/importmap unless an actual conflict is found.
- **Validation:** production asset precompile and HTTP asset requests; create rich text, attach an image/file by direct upload, reject >1 MB embedded blob, open an **old** linked/attached note, edit a separate field and save, reload, then export its text. Include details/summary: the repository already documents that Trix flattens these when saved, which is a pre-existing limitation, not a new Rails regression. Do not silently rewrite old bodies while migrating.

**Preserve signing identity.** Rails 7.1 changes the development/test key file from `tmp/development_secret.txt` to `tmp/local_secret.txt`; preserve its contents when retaining local data. Keep production `secret_key_base`, app/GlobalID identity, digest/cookie settings, and storage service names stable. Current cookies already use JSON and the 7.0 key-generator SHA256 defaults; no automatic 6.1→7.0 cookie-rotation recipe is needed here. Do test cookies both ways rather than inferring compatibility from the generic verifier probe.

Action Text stores signed attachment identifiers in rich-text HTML, while embedded blob URLs do not expire. A new signature format written by a new web node can persist long after the deployment; waiting for sessions to expire does not make rollback safe. Keep old message serializer/envelope writers during the rollback window. Any eventual format change must have compatible readers/rotations or a tested migration/re-signing strategy for stored references. Do not rotate keys merely to fix a deployment error. Keep old assets and blob files reachable through rollback; back up SQL **and** Disk storage.

## 5. Queue rollout and optional Sidekiq changes

- **Do not infer automatic enqueue-after-commit from the 7.2 feature announcement.** Tagged 7.2.0 starts the job class attribute at `:never`; 8.1.0 starts it at **false**. This app sets no override. The exact target source does not automatically defer these jobs. If adopting deferral, use the target's boolean class setting, not removed `:never/:always/:default` values or the removed global config.
- This matters for [Citation#request_enrichment](file:///home/user/workspace/repo/app/models/citation.rb#L11-L23) and [Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L50-L82): they enqueue under a database row lock and rely on immediate enqueue failure to roll back the changed state. Opting into after-commit enqueue can leave pending state or a new reminder id committed when Redis fails. Keep current semantics during compatibility work; test refusal before commit and deferred failure separately if changing them. A durable outbox/reconciliation policy would be a separate design, not an automatic upgrade refactor.
- `Notebook#request_export` deliberately commits the Export before native `ExportJob.perform_async`; Active Job deferral settings do not affect this native job. Preserve that order and cancellation/job-id contracts.
- Rails 8.1's built-in Sidekiq adapter is **deprecated, not removed**; its warning recommends Sidekiq **≥7.3.3** for the gem-owned adapter before Rails 8.2. That is an optional follow-up for this exact target. [Adapter source](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/queue_adapters/sidekiq_adapter.rb), [target deferral](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/enqueuing.rb), [7.2 deferral](https://github.com/rails/rails/blob/v7.2.0/activejob/lib/active_job/enqueuing.rb).
- **If Sidekiq is upgraded**, audit its separate versioned guide before choosing the version: native export options currently use `{ format: "markdown" }` (symbol key), and Sidekiq 6 already warns that Sidekiq 7 strict JSON arguments will reject them. Prepare `{ "format" => "markdown" }` on 6.5; the worker already reads string keys. Also, `User#request_digest` relies on redis-rb's boolean `sadd`: a client returning integer 0 makes duplicate requests truthy in Ruby. Do not reuse that condition under a new Redis client without adapting it to the actual API. Pinning redis-rb 4.8.1 for other consumers does not force Sidekiq 7's pool to keep that API. These are **conditional Sidekiq/client risks**, not executed Sidekiq 7 results.

### Concrete deployment / rollback sequence

1. **Prepare on 7.0.8.7**: explicit import rollback; `.doi` receipt reader; consistent annotation keys; explicit highlight forwarding; positional enum; split routes; correct singular notebook filter; unbound form; string joining; Time-valued scheduling; explicit UTC digest consumer; decimal-string producer; nonnegative cache TTL; provider configuration boundary. These preparations use current-version APIs. Add behavioral assertions before upgrading; do not ship the new `serialize`/retry-symbol/exception-mode syntax yet.
2. **Staged development/testing checkpoints:** follow the upstream minor-step sequence **7.0 → 7.1 → 7.2 → 8.0 → 8.1.0**, using appropriate patch releases for intermediate checkpoints. Intermediate exact patch versions were not resolved or executed here. At 7.1 switch serializer keywords, retry symbol, and exception mode. Inspect deprecations in development/test; production currently disables them. Review `app:update` diffs instead of overwriting configuration or adopting new generators wholesale.
3. **Before mixed-version traffic:** all consumers must include UTC normalization; all producers must write the chosen stable decimal string. Keep job class names, queue names, argument ordering, GlobalID names, and the current reminder `job_id` semantics. Keep YAML/JSON database formats and message/cache writers compatible. Inventory Sidekiq immediate queues, scheduled set, retries, and dead jobs that might be manually replayed. Far-future reminders mean “queue currently empty” is not enough.
4. **Deploy workers/readers before new publishers when formats cannot remain old.** Prefer the stable publisher contract above so rolling back does not require translating queued jobs. Check real queue transport in an isolated environment before doing this. Do not clear scheduled reminders, retries, or digest reservations; deleting queues to get a green deploy is data loss. Redis digest reservation keys expire after two days and should remain the same during the upgrade.
5. **Keep optional format/default adoption out of the first deployment.** Confirm green full suite plus browser/worker/cache/migration gates, canary actual use, then adopt defaults individually. For 7.1 cache-format adoption use a versioned cache namespace/path or a controlled cache flush after old readers are gone; caches are disposable, SQL/queues/blob storage are not. Do not flush Redis wholesale: it contains queues and reservations, not this application's fragment cache.
6. **Rollback**: rollback only to a release with compatible consumers and persisted formats. With new BigDecimal payloads, retain new-capable workers or supply a tested backward reader before old workers resume. With new message signatures embedded in notes, retain compatible verification; cache clearing alone is insufficient. Restore old-compatible cache namespace, retain blob files and old assets, and do not reverse migrations or erase accepted user writes as an automatic rollback step. If an unsafe import release ran, separately reconcile partial imports rather than assuming code rollback repairs them.
