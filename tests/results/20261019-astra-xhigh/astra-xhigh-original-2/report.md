# Rails 7.0.8.7 → 8.1.0: Margin Notes upgrade plan

## Decision

**Feasible, but not a version-pin-only upgrade. Do not deploy the requested version until the required repairs and queue-format preparations below are complete.** Initially keep `config.load_defaults 7.0`; adopting 8.1 defaults is a separate operation, not a prerequisite for running Rails 8.1.0.

This assessment inspected actual app code, configuration, migrations, tests, locked gems, Rails' versioned upgrade guide, and source/changelogs at tags 7.1.0, 7.2.0, 8.0.0, and 8.1.0, against the installed 7.0.8.7 source. It does not certify security support for the exact 8.1.0 patch or audit the deployed environment.

The working application was not upgraded or edited. All execution occurred in disposable copies with private services. The recorded experimental patches only unmask later failures; **they are not a complete implementation or a deployable upgrade**.

### Most consequential findings

- An invalid CSV import changes from rollback to **partial commit**, even with 7.0 defaults. The target probe returned `false` while committing one import, note, citation, and rich-text body.
- A new Rails digest payload containing `BigDecimal` cannot be read by a Rails 7.0 worker. Separately, preserved time zones change the digest's date and selected notes away from the documented UTC-day contract.
- The existing Action Text allowlist initializer prevents boot. Removed model, routing, form, secret-configuration, and job APIs cause further failures.
- New defaults expose additional issues in YAML preferences, immutable slugs, PostgreSQL date results, and cache expiry. They are not all unconditional Rails 8.1 failures.
- The original dependency constraints **resolve** with Rails 8.1.0 and Ruby 3.3.6. However, resolution today selected JSON 3.1.0, whose keyword-only parser is incompatible with this exact Rails patch. A JSON 2.21.2 comparison removed that obstruction.

## Required changes before the target deployment

“7.0-ready” below means whether the proposed preparation is compatible with 7.0.8.7. Unless explicitly marked observed, this is a source-based conclusion, not a completed preparatory test run.

### 1. Repair import atomicity before any new-runtime writers

**Affected:** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L44-L61). **Applies:** a later row fails after earlier rows saved. Rails 7.1 introduces configurable commit-on-nonlocal-return; 7.2 removes the rollback behavior. Retaining 7.0 defaults cannot restore it on 8.1.

**Recommendation:** do not `return false` out of a transaction. Use exception-driven rollback on invalid saves, then translate `ActiveRecord::RecordInvalid` into the existing `false` result outside the transaction. Preserve each row's validation errors. If the method is allowed inside another transaction, use a savepoint (`requires_new: true`) so rescuing the error does not leave earlier batch writes in the enclosing transaction. Do not broaden rescue to suppress unrelated database failures.

**7.0-ready:** yes. **Validation:** submit valid first row with a new DOI and invalid second row; assert *all four* counts (Import, Note, Citation, ActionText::RichText) unchanged, including from a fresh connection outside transactional fixtures. Also run under an enclosing transaction. Observed original: deltas `[0,0,0,0]` on 7.0, `[1,1,1,1]` on 8.1. Existing request tests stop first at missing annotation assertions, so currently fail before checking this downstream problem. Prevent the bad writes rather than relying on rollback of application code to repair them.

### 2. Preserve the digest's UTC contract and make queue arguments cross-version safe

**Affected:** [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L27-L57), [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb), [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L6-L12).

**Applies:** non-UTC readers near day boundaries; mixed-version workers or rollback with queued digests. From Rails 7.2, TimeWithZone serialization preserves the zone; old payloads omit it. Rails 7.1 introduces a gated BigDecimal serializer; 7.2 makes it mandatory, and 8.0 removes the obsolete toggle. These changes are independent of retained defaults on 8.1.

**Recommendation:** explicitly convert `requested_at` to UTC in `DigestMailer` before both `to_date` and `all_day`. Prepare `reading_completion.to_s("F")` at the enqueue boundary while still on 7.0; the mailer already converts it with `BigDecimal(...)`. Keep that JSON-safe string format through the rollback window. Do not merely update the expected digest subject to the reader's local date: that would contradict the Redis reservation day and the UI's documented UTC behavior.

**7.0-ready:** yes for both. **Validation:** enqueue at 2026-10-05 03:30 UTC for an Eastern reader (local October 4), with notes on both UTC dates and both sides of local midnight. Check the UTC subject, exact included notes, duplicate reservation behavior, and nontrivial completion `0.6667`. Exercise a real JSON round trip, not only the Active Job test adapter. Observed target subject changes October 5→October 4 without the repair. Observed original/new payloads have different date/type semantics; 7.0 rejects the new decimal serializer. Stage these fixes on every worker as well as every web process.

### 4. Decide reminder display behavior explicitly

**Affected:** [Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L35-L45), [preview partial](file:///home/user/workspace/repo/app/views/notes/_reminder.html.erb#L16-L20), and the DST request test.

**Applies:** crossing DST with `TimeWithZone#to_time`. Rails 8.1 always preserves the receiver's zone; the prior fixed-offset behavior cannot be restored just by retaining 7.0 defaults. **Observed:** October 31 09:00 −04:00 plus 86,400 seconds displays November 1 **08:00 −05:00**, instead of **09:00 −04:00**. Both represent epoch 1,793,538,000.

**Recommendation:** for a behavior-preserving upgrade, explicitly create a fixed-offset `Time` before adding seconds, e.g. `reminder_at.utc.getlocal(reminder_at.utc_offset) + 86_400` (**7.0-ready: yes**). Alternatively, approve the more natural local-zone display as a separate behavior change and update the documentation/test. Do not change postponement to “same local clock tomorrow”: that would change the promised 24 elapsed hours. Validate both spring and fall boundaries, displayed offset, stored epoch, and which replacement job sends mail. No epoch backfill is needed.

### 5. Constrain the exact target's JSON dependency

**Affected:** [Gemfile/lock](file:///home/user/workspace/repo/Gemfile), tag reads, sessions, Active Storage metadata, and other JSON decoding.

**Applies:** resolving this exact old Rails patch against the currently available JSON 3.x releases. Rails 8.1.0 calls `JSON.parse(json, options)`, while observed JSON 3.1.0 requires keyword options. A successful bundle resolution is insufficient.

**Recommendation:** keep this evaluation's `json < 3` compatibility constraint for the exact 8.1.0 target and lock a tested 2.x version; the comparison resolved **2.21.2**. Do not globally update every dependency. **7.0-ready:** the constraint is consistent with its existing JSON 2.7.2 runtime; a new 2.x resolution should still be tested on 7.0. A later Rails patch may eliminate the need, but that has not been evaluated here.

**Validation:** both tag and blob metadata reads, session round trip, and full suite against the final lock. JSON 2 removed the widespread argument-count errors, but remaining application failures are documented above.

## Defaults and optional adoption: do not combine with the first runtime rollout

### A. Notebook YAML preferences and immutable slug

**Affected:** [Notebook](file:///home/user/workspace/repo/app/models/notebook.rb#L7-L19), [permitted parameters](file:///home/user/workspace/repo/app/controllers/notebooks_controller.rb#L38-L40), [settings form](file:///home/user/workspace/repo/app/views/notebooks/_form.html.erb).

With retained 7.0 defaults, `serialize :preferences` still uses YAML and readonly assignment remains ignored for persistence. **Adopting 7.1 defaults** sets the default column serializer to nil and enables readonly-assignment errors. A normal settings submission includes the unchanged slug, which raises too—not just a malicious changed slug. Both conditions were reproduced in focused class probes.

Before enabling these defaults, explicitly retain YAML with `serialize :preferences, coder: YAML` on 7.1+, and stop permitting/submitting `slug` on edits; the server already derives it on creation. Slug parameter/form preparation is **7.0-ready**. The coder keyword is not honored by 7.0: for preferences its existing YAML default happens to provide equivalent behavior, but defer the explicit-coder declaration until 7.1 rather than relying on an ignored option. Do not convert existing YAML to JSON as an incidental cleanup. Validate old YAML hashes/nulls and heading edits across old/new readers, plus both unchanged and tampered slug submissions. Check the raw stored representation. No preference data conversion is required for the recommended plan.

### B. Cache expiration needs a code fix even before adopting strict errors

**Affected:** [export availability fragment](file:///home/user/workspace/repo/app/views/exports/_export.html.erb#L25-L37). **Applies:** caching enabled and rendering an already-expired export.

`expires_at - Time.current` becomes negative. In the target, retaining old defaults **logs/reports and removes the invalid TTL**, allowing a non-expiring entry; new 7.1 defaults raise instead. Both behaviors were observed. Correcting negative TTL generation is part of preserving behavior; enabling the stricter error setting remains optional.

Compute the remaining lifetime once; cache only when it is positive (for example with `cache_if` and that same positive `expires_in`), and render already-expired indicators uncached. This preparation works on 7.0. Merely switching to `expires_at:` is **not** sufficient: the target converts an absolute deadline into a relative TTL and rejects past deadlines too. Validate a cold miss for an already-expired record, a warm live entry across its deadline, exact boundary, and another reader's access. The authoritative download check must remain before conditional handling. No cache should authorize access.

### C. PostgreSQL date decoding

**Affected:** [Notebook#daily_note_counts](file:///home/user/workspace/repo/app/models/notebook.rb#L33-L41). **Applies only when** adopting `active_record.postgresql_adapter_decode_dates = true` (7.2 defaults). The retained-default target still returns ISO strings; a newly constructed opted-in adapter returned a Date and `Date.iso8601(day)` raised TypeError.

Use `day.to_date` on the returned Date or ISO string (**7.0-ready**, both support it in Rails), or retain the old decoding option initially. Validate distinct UTC dates around midnight with a non-UTC reader, counts, order, and empty days on the real pg adapter, not SQLite. Do not infer this break merely from the gem version.

### D. HTML5 sanitizer and editor asset adoption

**Affected:** Action Text initializer, stored `action_text_rich_texts.body`, [Trix 1.3.5 classic script](file:///home/user/workspace/repo/app/views/layouts/application.html.erb#L9-L14), [import map](file:///home/user/workspace/repo/config/importmap.rb), and [Trix stylesheet directive](file:///home/user/workspace/repo/app/assets/stylesheets/actiontext.css#L1-L6).

Rails 7.1 defaults opt into HTML5 sanitization on supported platforms. The runtime upgrade also introduces the `action_text-trix` gem (resolved 2.1.19), but the layout **still loads vendored Trix 1.3.5**. The gem bump does not automatically replace that explicit script. The `trix` stylesheet can therefore come from a newer version while JavaScript remains old. This mismatch is a browser-validation risk, not a demonstrated editor failure.

Keep HTML4 initially and avoid rerunning installers blindly. Separately choose a tested aligned Trix JS/CSS pair and update the asset manifest/import loading consistently; do not load two Trix versions. Run production asset precompilation and browser create→save→reload→edit for links, image/file attachments, pasted hostile HTML, and existing details/summary bodies. Compare rendered output and *stored HTML before/after editing* under both sanitizer vendors. Existing details/summary flattening by Trix is documented behavior, not an upgrade-caused discovery. No browser execution or production asset build was done here; there are no implemented system test files.

### E. Enqueue-after-commit is not automatically enabled on this target

**Affected:** [Citation#request_enrichment](file:///home/user/workspace/repo/app/models/citation.rb#L14-L24), [Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L55-L68), and their row-lock/enqueue-failure contracts.

Rails 7.2's new defaults can delegate after-commit deferral to the adapter. Do not extrapolate that description to all Rails 8.1 applications: the 8.1 source and actual probe show `ActiveJob::Base.enqueue_after_transaction_commit == false` here. Rails 8.1 removes the old symbolic values and global option; a per-job boolean is the relevant API.

Keep current timing initially. If adopting deferral, account for Redis failure occurring **after** database commit: pending citation/reminder state could remain even though enqueue fails, rather than rolling back as the app promises. Use an explicit durable delivery/reconciliation design before changing that contract, not just a global flag. The native `ExportJob` is outside Active Job and unaffected. Validate transaction commit/rollback, actual adapter failure, pending state, returned job IDs, and worker startup before/after the lock releases. Deferral itself is **not a 7.0 preparation**.

### F. HTTP freshness is not a demonstrated response-status regression here

**Affected:** [ExportDownloadsController](file:///home/user/workspace/repo/app/controllers/export_downloads_controller.rb#L4-L16). Rails 8.0 defaults enable `strict_freshness`, preferring ETag when validators conflict. Source comparison confirms Rails' branch changes, but the resolved Rack 2 middleware already gives ETag priority.

**Observed actual stack:** both baseline and target return 304 for a matching ETag plus an old Last-Modified condition; toggling target strict freshness still returns 304. Cache-Control remains `max-age=0, private, must-revalidate`; expiry still redirects (302). Thus no forced cache-header rewrite is justified. Before adopting defaults, keep discriminating tests for matching/nonmatching ETags, conflicting dates, authorization and expiry with conditional headers. If measuring the change in blob-download work, instrument storage reads rather than asserting only the final status.

### G. Other new defaults/generators

No forced switch to Propshaft, Solid Queue/Cache/Cable, a generated authentication system, Kamal, Thruster, YJIT, or a different thread count is necessary. This app deliberately uses Sprockets, Sidekiq/Redis, custom password/session handling, and Puma's explicit thread setting. No application Active Record encryption, UJS imports, custom ActiveStorage::BaseController subclasses, mailer preview path, or autoload-path `require` usage was found. Those upgrade-guide sections do not justify changes here.

Rails 8.1 sorts schema columns on dump; review that as generated-file ordering, not a database data migration. Existing Active Storage schema already has service_name, nullable checksum, and variant_records. Retain historical migration versions; exercise schema creation and pending migrations, rather than rewriting historical migrations or running database-reset commands. The schema loaded successfully in the target experiment. The 8.1 path-relative redirect setting has no identified offending redirect: existing actions use route helpers/root-relative paths. No application `render json:` endpoint was found, so new JSON response escaping defaults are not a reason to rewrite these HTML controllers; still check framework upload JSON in browser validation.

## Stored data, mixed versions, and rollback

1. **Persisted rows:** retain status integer mapping, DOI primary keys, JSON tags, YAML preferences, and jsonb settings. Inventory and sample actual data with authorized, read-only access before release; this assessment intentionally did not read the working database. Maintain old-reader/new-writer fixtures for JSON/YAML. Do not “fix” the serializer signature on 7.0: the probe proves it can change writes to YAML. If an unsafe variant ever ran, restoring code alone would not repair partial imports or incorrectly encoded tags. The import's original CSV is not persisted, so automatic reconstruction of missing rows cannot be assumed.
2. **Queues:** inventory default, scheduled, retry, and dead work, not just queue depth. Reminder jobs may be scheduled far into the future. Preserve job class names, queues, GlobalID app/model identity, and IDs. The Time argument conversion changes new scheduling, not the stored reminder epoch or an already-enqueued job's Sidekiq timestamp. Existing native ExportJob options have already been JSON-normalized to string keys; keep worker compatibility.
3. **Digest bridge:** deploy explicit UTC interpretation and decimal-string arguments on **all 7.0 producers/consumers first**. Only then introduce new producers. Old payloads remain readable by 8.1; without the bridge, new decimal payloads cannot return to old workers. Keeping the string protocol is simpler than backporting Rails serializer classes. Do not rely on a removed `use_big_decimal_serializer` flag on 8.1. If new-format jobs already exist, isolate/finish them on compatible workers or explicitly transform and verify payloads under an approved operations procedure; do not clear queues.
4. **Signatures and sessions:** preserve `secret_key_base`, derivation/digest settings, session key, and verifier configuration across all processes and rollback. Development/test switches from `tmp/development_secret.txt` to `tmp/local_secret.txt` in 7.1; copy/rename the existing key rather than generating a new one if old local attachments/sessions must survive. Do not print it. Production key sourcing must be verified independently; no live production key was inspected.
5. **Message/cache format defaults:** keep 7.0 cache format and legacy message serialization/metadata during mixed 7.0 operation. Rails 7.1 adds new message serializer/metadata and cache formats with newer-reader fallbacks; that does **not** establish old-reader compatibility. Blob signed URLs and permanent Action Text attachment SGIDs matter beyond an ordinary session TTL. Before changing writers, test signatures generated by each version against both runtimes using the same synthetic key, real stored rich text, blob downloads, and session cookies. Cookie serialization is already JSON in this app; do not conflate that with every message-verifier payload. These end-to-end cross-signature tests remain proposed.
6. **Cache rollout:** the repository uses local/default production caching, development memory/null stores, and test null stores—not a configured Redis application cache. If deployment shares a file cache or overrides that configuration, confirm it explicitly. Old cache readers may miss new-format entries; use a release-specific namespace/cold cache when adopting the new format, or wait until rollback no longer requires old readers. Never delete queues/reservations as part of cache invalidation.
7. **Storage/assets:** retain the actual Disk volume, blob keys, service names, and old fingerprinted assets while mixed clients finish. “Rollback” must not replace persistent storage with an empty release directory. Validate saved old attachments and newly written attachments after reverting application code. No automatic rich-text rewrite or file purge is required.
8. **Sidekiq scope:** Rails 8.1 still contains a working deprecated Sidekiq adapter; client enqueue was observed with Sidekiq 6.5.12. Source says the built-in adapter is removed in 8.2 and recommends Sidekiq ≥7.3.3. This is future work, not a proven Rails 8.1 resolver blocker. Full worker-process compatibility has not been exercised. If upgrading Sidekiq separately, first assess JSON strictness (`Notebook#request_export` currently sends a symbol-keyed options hash), Redis return semantics for digest reservations, and error classes. Do not combine that unassessed migration with this runtime upgrade.

## Recommended delivery sequence and release gates

1. **Baseline and inventory.** Retain the exact current lock and an application/database/storage rollback snapshot through the normal approved backup process. Confirm actual production PG/Redis versions, mail delivery, secret sourcing, cache overrides, persistent storage mounts, and queue retention. Those facts are not established by this sample repository.
2. **7.0-compatible preparation release.** Repair import rollback; normalize digest day and decimal wire values; fix routes, enum, highlight forwarding, notebook filter, nil form option, secret access, string joining, DOI reads, annotation keys, and Time scheduling. Make the explicit reminder-display choice. Fix the fragment deadline. Optional slug/date preparation can also run on 7.0. Run the same behavior tests before changing Rails.
3. **Version ladder.** Follow upstream's minor-by-minor process: 7.0 patch baseline → 7.1 → 7.2 → 8.0 → exact 8.1.0. Resolve and record an exact lock for each selected intermediate patch; these intermediate *runtimes* were not executed here. Keep `load_defaults 7.0`. On 7.1, change tag coder signature, retry symbol, and exception mode. Review `app:update` diffs manually; do not accept generated infrastructure changes wholesale. Watch deprecations outside production, where this repository suppresses them.
4. **Target candidate validation.** Run `bundle check`, `bin/rails zeitwerk:check`, full request/model suite, actual Sidekiq worker execution/retries/schedules, production-mode boot and asset precompile, and browser workflows. Keep the exact JSON constraint/lock used. Add or extend regression tests for the contracts identified above; do not change expected data to match accidental regressions. No system/browser suite currently exists to establish editor/upload compatibility.
5. **Mixed-version rehearsal.** In isolated services, run the old-prepared and new candidate against a cloned representative dataset and shared *test* queue/storage. Test old→new and new→old queue payloads, cookies/SGIDs/blob URLs, raw serialized columns, export jobs already in flight, future reminders, stale replaced reminders, and provider retry state. Inject enqueue failure and verify database state. Stop at any unexplained change, even if ordinary tests pass.
6. **Rollout then defaults.** Upgrade compatible consumers before enabling any new-format producers, preserve the bridge through rollback, and monitor failures/queue lag/partial import writes/digest dates/attachment rendering. Adopt defaults one setting at a time only after the runtime is stable and the relevant data/rollback tests pass. Global `load_defaults 8.1` is the end of that process, not its first step.

**Still unverified:** a complete fixed 8.1 application, intermediate runtime suites, production boot/deployment configuration, real Sidekiq worker lifecycle and retry consumption, security advisories for this exact target/lock, cross-version session/SGID/blob signatures, production asset builds, browser/editor behavior, real historical serialized-data samples, and actual backup/rollback operational procedures. These are release gates, not claims of success.
