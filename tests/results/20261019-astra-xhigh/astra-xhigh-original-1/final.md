# Rails 7.0.8.7 → 8.1.0: Margin Notes upgrade plan

## Decision

**Feasible, but not a Gemfile-only upgrade. Keep `config.load_defaults 7.0` for the framework upgrade, make compatibility changes first, and adopt newer defaults in separate deployments.** The most consequential risks are partial CSV imports, mixed-version Active Job payloads, and persistent Action Text attachment signatures—not just boot failures.

This is an assessment, not an implementation. No tracked application files or working application services/data were changed. Diagnostic edits and writes occurred only in disposable checkouts with dedicated PostgreSQL/Redis instances and copy-local storage/cache. The application is **not upgraded** and the target suite is **not green**.

Reviewed application revision: [ab732f5](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7). Framework source was pinned to **v8.1.0**, not the changing `8-1-stable` branch. The online `/v8.1/` guide currently describes a later patch, so exact-version source and its bundled upgrade/release notes controlled this assessment.

### Evidence labels

- **Executed:** observed in the isolated application or a documented diagnostic probe.
- **Source:** traced application code against versioned framework code; not necessarily exercised end to end.
- **Proposed:** acceptance check still required before deployment.

## 1. Runtime and dependency boundary

The app pins Ruby **3.3.6**, Bundler **2.5.22**, Rails **7.0.8.7**, `pg` **1.6.0**, Sidekiq **6.5.12**, Redis gem **4.8.1**, Pagy **8.6.3**, Faraday **1.10.4**, and `concurrent-ruby` **1.3.4**. It uses PostgreSQL, Sprockets/importmap, Action Text, Disk Active Storage, CookieStore sessions, Sidekiq, and file/test mail delivery. It loads Rails **7.0 defaults**.

**Executed:** conservative resolution of Rails 8.1.0 succeeded without upgrading Sidekiq, Redis, Puma, Pagy, Faraday, or the asset pipeline. It kept Rack **2.2.24**, Puma **5.6.9**, Sprockets Rails **3.5.2**, and added `rack-session` **1.0.2**, `rackup` **1.0.1**, and `action_text-trix` **2.1.19**. Rails 8.1.0's actionpack gemspec permits Rack ≥ 2.2.4; Ruby ≥ 3.2 is required, which the pinned Ruby already satisfies. **Do not introduce a Rack 3/Sidekiq upgrade as an assumed prerequisite.**

A real resolver hazard appeared: the unconstrained new `json` dependency selected **3.1.0**, but Rails 8.1.0's `ActiveSupport::JSON.decode` calls `JSON.parse(json, options)` with a positional options hash. JSON 3.1.0 rejects that with `ArgumentError`. This broke session decoding and model JSON handling. A disposable `gem "json", "< 3"` constraint resolved **2.21.2** and removed that obstruction.

**Recommendation:** for the exact requested Rails release, constrain JSON to a compatible 2.x version and retain the resolved lockfile. Do not confuse Bundler success with runtime compatibility. The constraint admits the baseline's JSON 2.7.2; the complete Rails 7.0 bundle with newly resolved JSON 2.21.2 was not tested. Keep the existing unrelated pins initially. Review support/security status separately before a real production deployment; this assessment is not a security approval for the old exact patch 8.1.0.

**Proposed validation:** clean install from the committed lockfile; test JSON decoding, signing in and making a second authenticated request, reading existing JSON tags, updating jsonb highlight settings, and loading both production web and worker processes. Keep the existing `concurrent-ruby` pin during preparation rather than introducing an unrelated dependency change.

Sources: [actionpack gemspec](https://github.com/rails/rails/blob/v8.1.0/actionpack/actionpack.gemspec), [railties gemspec](https://github.com/rails/rails/blob/v8.1.0/railties/railties.gemspec), [JSON decoding](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb). Exact resolved dependencies and JSON failure trace are retained in the evidence directory.

## 4. Stored data, queued work and rollback

### Durable database/storage data

- No mandatory schema or data-format migration was identified for these application tables. Keep JSON tags, YAML preferences, jsonb settings, integer enum values, DOI primary keys, reminder epochs and all associations unchanged. Audit representative **existing** values before deciding to tighten types. Production data was not inspected.
- Existing Markdown export files do not need regeneration to replace string `sum`. Keep blobs/files and their deadlines. Existing rich-text attachment HTML contains signed identifiers; these are durable data, not disposable cache.
- Preserve `secret_key_base` across web/worker releases. Rails 7.1 renames the local development/test secret file from `tmp/development_secret.txt` to `tmp/local_secret.txt`; copy the **same secret**, do not regenerate it. Audit production's existing secret source separately; the provider's `secrets.yml` contains no application signing key, and encrypted credentials were not opened.
- **Executed with the same synthetic signing key:** 7.0 and 8.1 using 7.0 defaults accepted each other's blob IDs and SGIDs. With 8.1 defaults, the target accepted old identifiers, but 7.0 raised while decoding new identifiers. This disproves the assumption that “the new version can read old data” proves rollback safety.
- **Session cookies were different:** in that same matrix, the app's JSON CookieStore cookie authenticated in both directions, even for the 8.1-defaults variant. Do not claim all cookies break just because general signed-message defaults change. Repeat using actual deployment session options/key provisioning before launch.
- Once newer signatures are persisted in rich text, draining queues or restoring the old signing key is insufficient to roll back to an unprepared 7.0 reader. Keep legacy message output until the old-version rollback window closes, or deliberately build/test a reader-compatible bridge before new writers. Do not “repair” all notes by blindly resaving them through Trix.

### Jobs and reservations

- Active Job's test adapter does not reproduce Sidekiq's JSON round trip. Real Redis enqueue was exercised here; a live worker fleet was **not** run.
- Deploy the decimal-string producer and explicit UTC mailer on **all** old-version web/worker processes first. Existing 7.0 DigestJobs already have string completion in Redis and remain readable by the new framework. The target successfully deserialized the old zoned-time and decimal-string payloads in the probe.
- Before mixing or rolling back, inventory immediate queues, scheduled set, retries, dead jobs and jobs currently executing. Unprepared 8.1-produced decimal payloads cannot go to 7.0 workers. Prefer preventing them. If any exist, retain capable consumers or plan a narrowly scoped payload transformation while producers/workers are controlled; do not purge queues or recreate jobs without preserving IDs/counters.
- For `NoteReminderJob`, existing Sidekiq scheduled scores are epochs; correcting new `wait_until` calls does not require rescheduling old reminders. Rails 7.0 job envelopes omit the newer `scheduled_at` field; target source permits it to be absent. Verify an **actual old scheduled envelope** with a target worker, and vice versa for rollback. Preserve both Active Job `job_id` and the note's `reminder_job_id`: replacing jobs indiscriminately defeats the stale-job suppression logic.
- Citation jobs carry GlobalIDs to DOI-primary-key records. Preserve class names, DOI values, Active Job wrapper names and retry execution counters. Test an already-retrying job after deployment, not only a freshly queued successful provider request.
- Native `ExportJob` remains a Sidekiq job, with integer export ID and string-key options after JSON. Existing queued jobs should use the repaired generator; test queued, working/retried and cancelled exports. Do not change its job class or options format during the Rails upgrade.
- Keep the daily Redis reservation keys on UTC days and retain their two-day lifetime. Changing the digest's day to the reader's local day would mismatch reservations and message content.
- Enqueue-after-transaction-commit must **not** be adopted blindly. `Citation#request_enrichment` and `Note#schedule_reminder` currently rely on synchronous enqueue failure rolling back state under a row lock. Rails 8.1 source defaults the job-level flag to **false**, so automatic deferral is not an inevitable effect of this upgrade. Enabling it would commit pending/reminder state before an enqueue failure, changing the contract. Leave it off initially; if later selected, explicitly redesign and test failed enqueue, rolled-back transactions and an early-starting worker. `ExportJob` is native Sidekiq and has separate enqueue semantics.
