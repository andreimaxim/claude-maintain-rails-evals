# Margin Notes: Rails 7.0.8.7 → 8.1.0 upgrade plan

**Recommendation:** proceed as a staged compatibility project, not a Gemfile-only update. Keep `config.load_defaults 7.0` during the framework upgrade, fix the unconditional changes below, and adopt newer defaults separately. Keeping old defaults does **not** preserve all old behavior.

Assessed on 2026-10-19 against [the application snapshot](https://github.com/andreimaxim/claude-maintain-rails-sample/commit/ab732f534dce525ae70f1d31aac6908a1ab3d8f7). No working application files, databases, queues, or stored files were changed. Experiments used disposable copies, a dedicated PostgreSQL cluster and Redis process, and copy-local cache/storage. The report and evidence are local, uncommitted artifacts.

## 1. Scope and evidence

The executable baseline is Ruby 3.3.6, Rails 7.0.8.7, Rails 7.0 defaults, PostgreSQL/pg 1.6.0, Sidekiq 6.5.12, redis-rb 4.8.1, Puma 5.6.9, Sprockets, importmap, Action Text, and local Disk storage. Actual usage was traced through models, jobs, controllers, ERB, configuration, schema/migrations, and every existing test file; architectural documentation was cross-checked against code rather than treated as proof.

Upstream review used the exact Rails tags **v7.0.8.7, v7.1.0, v7.2.0, v8.0.0, v8.1.0**, including release notes, component changelogs, defaults and API implementations. See sources below. Intermediate latest patch releases have not been run; their exact patches should be selected and locked when executing the staged plan.

### B. CSV imports: atomicity, annotations and receipts

1. **Partial commit on validation failure:** [Import#apply](file:///home/user/workspace/repo/app/models/import.rb#L50-L60) uses `return false` inside `transaction`. Rails 7.0 rolls back this non-local return; 7.1 can opt into committing, and 7.2+ commits regardless of keeping 7.0 defaults. An executed valid-first/invalid-second import returned false on both versions, but record deltas `[Import, Note, Citation, RichText]` were **[0,0,0,0] on 7.0 versus [1,1,1,1] on 8.1**.
   - **Recommendation:** use `save!` for rows and rescue the expected `ActiveRecord::RecordInvalid` outside the transaction to return false with row errors retained, or explicitly raise `ActiveRecord::Rollback` and return a separately recorded failure result. Never depend on `return` for rollback. This can be prepared on 7.0. If this operation is made callable inside a joinable outer transaction, explicitly define savepoint ownership too.
   - **Validation:** submit a structurally valid CSV with a valid row first and invalid row second **directly to apply/create**, without preview or an enclosing test transaction; assert no imported rows, citations, rich texts or import record persisted. Also test a later attachment-size rejection and successful multi-row import. A valid first row is essential.
2. **Annotations disappear:** [Import#annotations](file:///home/user/workspace/repo/app/models/import.rb#L37-L41) uses integer line keys; [preview](file:///home/user/workspace/repo/app/views/imports/preview.html.erb#L22-L44) calls `stringify_keys` then looks up integers. Rails 8.0 now stringifies *all* keys of HashWithIndifferentAccess; previously its override left integer keys unchanged. **Executed request failures.** Remove the unnecessary `stringify_keys` and keep integer indexing. This works on 7.0; alternatively consistently use strings on both sides, but do not change only the lookup on 7.0.
   - **Validation:** distinct annotations on lines 2 and 4, including an empty line/quoted multiline field and literal `<b>`/`&`; assert each annotation stays with its source row and is escaped.
3. **Receipt DOI silently becomes blank:** [Import#receipt](file:///home/user/workspace/repo/app/models/import.rb#L63-L69) reads `citation[:id]`, but the schema's primary key is `doi`. Since 7.2, `[:id]` no longer redirects to a custom primary key. **Executed:** `citation.id` and `.doi` remained correct, `citation[:id]` became nil, and CSV omitted the DOI. Use `citation&.doi` (or `.id` if intentionally generic), compatible with 7.0.
   - **Validation:** download CSV for both a DOI-bearing row and a row without DOI; check exact DOI spelling, including mixed case. Do not infer CSV correctness from the HTML receipt, which already uses `.doi`.

The existing import integration tests fail at the annotation preview first, so their later atomicity and CSV assertions do not currently reveal the additional target failures. Separate these release checks so an earlier failure does not hide the data-integrity issue.

Sources: [7.1 transaction transition](https://github.com/rails/rails/blob/v7.1.0/activerecord/CHANGELOG.md), [7.2 transaction implementation](https://github.com/rails/rails/blob/v7.2.0/activerecord/lib/active_record/connection_adapters/abstract/transaction.rb), [8.0 hash change](https://github.com/rails/rails/blob/v8.0.0/activesupport/CHANGELOG.md), [8.1 attribute read implementation](https://github.com/rails/rails/blob/v8.1.0/activerecord/lib/active_record/attribute_methods/read.rb).

The Active Support override was removed in 7.1; native Ruby sum starts at zero and raises. **Executed.** Use `fragments.join` (or an explicit string identity); works on 7.0. Validate exact Markdown for an empty notebook and a multi-note notebook, title normalization, ordering, cancellation and attachment filename. Preserve already completed export blobs; no conversion is required for existing Markdown files. [Source](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md).
- **Secrets removal:** [Citation::Provider](file:///home/user/workspace/repo/app/models/citation/provider.rb#L1-L15), `config/secrets.yml` and the [provider test setup/subprocess](file:///home/user/workspace/repo/test/controllers/citation_enrichments_controller_test.rb#L40-L58) use `Rails.application.secrets`, removed in 7.2. **Executed test setup failure; production caller also directly uses the removed API.** Move the provider configuration to `config.x.citation_provider` populated from ENV as Ruby strings, retaining local stand-in defaults and the production-unconfigured behavior. Update test injection and child-process setup together. This works on 7.0. Credentials are another supported choice, but do not introduce a key rotation as part of this migration. Remove secrets.yml only after moving its sole configuration responsibility. Validate `00123` and a password containing colon/space/hash survive byte-for-byte; a naive unquoted ENV→YAML rewrite can corrupt them. Run both web and worker boot paths and the loopback provider tests. [Source](https://github.com/rails/rails/blob/v7.2.0/railties/CHANGELOG.md).
- **Retry algorithm name:** [CitationEnrichmentJob](file:///home/user/workspace/repo/app/jobs/citation_enrichment_job.rb#L4-L9) uses `:exponentially_longer`, deprecated in 7.1 and removed in 7.2. Validate persistent 503 yields at most six HTTP requests (Faraday retry × Active Job attempts), the first two waits fall in the existing jitter ranges, terminal failure is recorded, and a 401 is not retried. The current target suite fails on secrets before reaching this retry error. Existing queued retries retain execution counters; preserve class/exception names and arguments rather than re-enqueuing them as fresh jobs. [Source](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md).

### D. Reminders: scheduling API and DST display

[Note#schedule_reminder](file:///home/user/workspace/repo/app/models/note.rb#L51-L69) passes integer `reminder_epoch` to `wait_until`. Numeric `scheduled_at` was deprecated in 7.1 and removed in 7.2. **Executed failure: undefined `utc` on Integer.** Pass `Time.at(reminder_epoch).utc`; leave the stored epoch and job-ID replacement logic unchanged. This is safe to prepare on 7.0, which converts time objects to queue timestamps.

[Note#next_day_reminder_at](file:///home/user/workspace/repo/app/models/note.rb#L40-L45) separately relies on old `TimeWithZone#to_time` offset behavior. In 8.1 it preserves the **zone**, unconditionally. The executed example changed the preview from **2026-11-01 09:00 −04:00** to **08:00 −05:00**; both are exactly 86,400 elapsed seconds after 2026-10-31 09:00 Eastern. This is not an epoch shift, nor a calendar-day postponement.

- Preserve the documented fixed-offset preview with explicit fixed-offset Ruby Time construction (`Time.at(reminder_epoch).getlocal(reminder_at.utc_offset) + 86_400`), which also works on 7.0; or deliberately adopt the more accurate local-zone preview and update the comment/test. Do not change to `1.day` unintentionally: that changes the promised elapsed-time interval around DST.
- Validate spring-forward and fall-back, exact scheduled timestamp after JSON storage, an imported integer epoch, a past time, rescheduling and an old scheduled job's no-op behavior. Preserve `reminder_job_id` on queue failure and verify deleted-note discard with a real worker. Test mode alone does not prove persisted scheduling or failure timing.

Sources: [7.2 Active Job removals](https://guides.rubyonrails.org/v7.2.0/7_2_release_notes.html), [8.1 TimeWithZone implementation](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/time_with_zone.rb).

### E. Digests: UTC business day and incompatible queued decimal format

Affected path: [User#request_digest](file:///home/user/workspace/repo/app/models/user.rb#L27-L57) → [DigestJob](file:///home/user/workspace/repo/app/jobs/digest_job.rb) → [DigestMailer](file:///home/user/workspace/repo/app/mailers/digest_mailer.rb#L2-L10).

1. **Day changes independently of framework defaults.** Redis reservations explicitly use the UTC day, but the mailer derives its subject/range from whatever timezone the job deserializer returns. Rails 7.2 preserves the serialized named zone; 7.0/7.1 deserialized into the worker's zone. At 2026-10-05 03:30 UTC in New York, the executed target mail subject became **October 04** instead of **October 05**, despite a reservation for October 05.
   - Normalize `requested_at` to UTC **in the consumer before both `to_date` and `all_day`**. This works on 7.0 and handles already queued old/new representations. Keep the established UTC contract instead of quietly changing reservations to local days.
   - Validate notes on opposite sides of UTC midnight and local midnight, including a DST transition. Subject, included note IDs and reservation day must agree. Existing digest test catches the day change, but not every stored payload variant.
2. **BigDecimal serializer prevents rollback/mixed consumption.** 7.0 JSON queues turn the decimal into a string; 7.1 introduced a named BigDecimal serializer behind a transition flag, and 7.2 made it unconditional. The 8.0 removal of `use_big_decimal_serializer` means retaining 7.0 defaults is not an escape hatch. **Executed cross-version:** 8.1 reads 7.0's string, but 7.0 raises `ActiveJob::DeserializationError` for 8.1's `ActiveJob::Serializers::BigDecimalSerializer` envelope.
   - Before new producers ship, pass `reading_completion.to_s("F")` to DigestJob. This works on 7.0 and 8.1, matches today's actual Redis payload, and the existing mailer already accepts it via `BigDecimal(...)`. Keep the three-argument job signature. Alternatively use an explicit staged serializer-reader deployment, but that is more work here.
   - Validate JSON encode/decode, not only `perform_enqueued_jobs`: 0, a repeating fraction such as 2/3 rounded to 0.6667, and 1; assert displayed percentage and date. Test old producer→new consumer and new producer→rollback consumer. On 7.0 the test adapter keeps BigDecimal objects and misses the Redis string conversion.

Already queued jobs with the new envelope must be drained by capable workers, isolated from 7.0 workers, or deliberately converted with an audited procedure before a rollback. Preserve retry/schedule sets and the two-day digest reservations; blindly clearing reservations can send duplicate emails. The mailer conversion already accepts both String and BigDecimal, so changing it solely for the new type is unnecessary.

Sources: [7.1 BigDecimal transition](https://github.com/rails/rails/blob/v7.1.0/activejob/CHANGELOG.md), [7.2 unconditional changes](https://github.com/rails/rails/blob/v7.2.0/activejob/CHANGELOG.md), [8.1 time serializer](https://github.com/rails/rails/blob/v8.1.0/activejob/lib/active_job/serializers/time_with_zone_serializer.rb).

### F. Exact dependency resolution, not assumed major-version blockers

Ruby 3.3.6 satisfies Rails 8.1.0's Ruby ≥ 3.2 requirement. The requested Rails version **resolved with existing Sidekiq 6.5.12, redis-rb 4.8.1, Puma 5.6.9, pg 1.6.0 and Rack 2.2.24**. Rackup 1.0.1 and rack-session 1.0.2 were selected. Therefore neither Rack 3 nor an immediate Sidekiq/Puma major upgrade is a demonstrated requirement. Keep `concurrent-ruby 1.3.4` during the 7.0 stage rather than broadening this upgrade needlessly.

There is, however, an **executed resolution-time compatibility problem** with the exact requested release: its unconstrained JSON dependency resolved JSON 3.1.0. [Rails 8.1.0 decoding](https://github.com/rails/rails/blob/v8.1.0/activesupport/lib/active_support/json/decoding.rb) calls `JSON.parse(json, options)`; the installed JSON 3.1.0 accepts keyword options. A focused `ActiveSupport::JSON.decode("[]")` reproduced `ArgumentError`. Add a tested JSON < 3 constraint for this exact target and lock the result (the lab resolved **2.21.2**). Do not silently change the requested Rails version. Validate cookies/session reads, stored JSON tags, settings and provider JSON. Adding an upper bound is compatible in principle with the current Ruby's JSON 2.x, but the existing baseline suite was not rerun with JSON 2.21.2 explicitly added.

The baseline and both target resolutions are retained as complete lockfiles. The conservative resolution also changed net-imap 0.6.7→0.6.8 and introduced Rails' new transitive dependencies, including `action_text-trix 2.1.19`; review the complete lock diff, not just the rails line.

Zero is truthy in Ruby. Verify supported return/error APIs in the selected version instead of blindly copying redis-rb methods. Also check Redis's version floor, concurrency/pool size and old job wrapper names. No Sidekiq 7 worker was tested here. [Versioned Sidekiq guide](https://github.com/sidekiq/sidekiq/blob/v7.3.3/docs/7.0-Upgrade.md).

Do not couple this request to switching Sprockets→Propshaft, Sidekiq→Solid Queue, Disk storage, authentication generators, Solid Cache/Cable, Kamal, or new CI infrastructure. Those are new-app defaults/features, not prerequisites for this application's upgrade.

## 4. Stored data, rolling deployment and rollback

### Database and stored files

- Preserve schema meanings: status integers, DOI primary keys, epoch seconds, reminder job IDs, JSON tags/settings, YAML preferences, Action Text HTML and blob records. The identified changes do not require a destructive schema migration.
- Before staging, restore an anonymized, representative snapshot into isolated resources, including old tag/preference bytes, attachment-bearing HTML and a completed export file. A fresh schema plus fixtures cannot establish data-format compatibility.
- Audit and remediate partial imports only if an affected version has actually processed them; do not delete rows merely because the code path is risky. No live data inventory was performed here.
- Preserve `secret_key_base` and key derivation across deployments. The 7.1 development/test file changes from `tmp/development_secret.txt` to `tmp/local_secret.txt`; transfer the existing local key securely if retaining local sessions/attachment signatures. Never print or commit it. Production's actual key source and deployment secret handling remain unverified; this repository's secrets.yml contains provider configuration, not a demonstrated production signing-key setup.
- Keep existing storage roots/blobs reachable by both web and workers during a real rollout. Do not run destructive reinstallation or purge tasks. No new private-file policy is supplied by the Rails upgrade; existing public signed blob URLs and upload-abuse limitations are pre-existing concerns.

### Signed messages, cookies and caches

7.1 defaults change Active Support message serializer to `:json_allow_marshal`, message metadata format, and cache format to 7.1. Old messages/cache entries can be read by newer code; **that does not establish the reverse direction**. Generic verifier changes matter to Active Storage blob signed IDs and Action Text signed GlobalIDs, not only login cookies. This application already uses JSON cookies and SHA256 key derivation under 7.0 defaults; do not prescribe a 6.1→7.0 digest rotation again.

During a mixed 7.0/new fleet or rollback window, retain legacy message writes/metadata and cache format 7.0 rather than flipping all defaults. On 7.1+, explicitly retain `active_support.message_serializer = :marshal`, `use_message_serializer_for_metadata = false`, and `cache_format_version = 7.0` if independently enabling other defaults; these newer knobs are not a same-value 7.0 preparation. Do not infer that JSON session cookies alone prove all blob/SGID formats are safe.

Proposed validation: using the same test key, database and disposable blob store, carry an old login cookie, blob signed URL and embedded attachment SGID into the new app, then generate each on the new app and read it on the rollback app; test expiry/purpose rejection too. Retain legacy write formats until both directions are proven or rollback to 7.0 is intentionally closed. Attachment references can be long-lived, so “wait for cookies to expire” is not sufficient. These exact application signature tests have **not** been executed here.

Production has no cache-store override, so the framework FileStore default applies unless deployment configuration changes it; development uses MemoryStore only when caching is enabled, otherwise NullStore. Redis here is a queue/reservation store, not Rails.cache. If a cache directory is shared across versions, keep format 7.0 through rollout, then switch in a later release or namespace/clear only disposable cache entries. Never flush Sidekiq Redis to clear a Rails cache. [Cache format transition source](https://github.com/rails/rails/blob/v7.1.0/activesupport/CHANGELOG.md).

### Queue and side-effect choreography

1. **Deploy compatible consumers first on 7.0:** explicit UTC digest handling; preserve String/BigDecimal input acceptance, existing job signatures, GID model names and job IDs. Prepare compatible producer payloads (decimal strings and Time scheduling) and other 7.0-safe fixes.
2. Capture queue inventory: pending/default jobs, in-flight workers, retries, scheduled reminders (possibly far in the future), dead jobs eligible for retry, and native exports. Include framework analysis/purge jobs. A momentarily empty ready queue is not a drain.
3. Prefer version-isolated queues/workers or a coordinated producer pause while verifying the serialized matrix. Never permit unprepared 7.0 workers to consume new BigDecimal envelopes. Check actual wrapper names if separately upgrading Sidekiq.
4. Keep digest reservation sets through deploy/rollback, retain reminder IDs so superseded jobs no-op, and let export cancellations/status checks continue to arbitrate. Enrichment retries must retain attempt counters. Emails are not exactly-once: existing reminder/digest retries can duplicate delivery after partial side effects; do not replay blindly.
5. Before rollback, stop new-format producers, classify/drain or isolate incompatible queued work, and ensure rollback code reads anything the new version wrote to database, blob references and signed messages. Keep the compatibility prep release as the rollback destination, not an arbitrary older build.

## 5. Proposed execution order and acceptance gates

1. **Baseline/preparation on 7.0.8.7.** Keep Ruby fixed. Add only 7.0-compatible fixes from section 2: explicit allowlist, positional enum and ordinary highlight aliases, split routes, unbound form, singular filter, import atomicity/annotation/DOI access, export join, ENV-backed provider config, Time scheduling, explicit digest UTC consumer and decimal-string producer. Fix negative TTL and stop accepting the hidden slug. Decide the DST display contract explicitly. Retain the old serializer declaration, old retry name and boolean test exception mode until the next stage.
2. **7.1 checkpoint.** Choose/lock a suitable 7.1 patch; run `app:update` only in the upgrade branch/disposable workspace and review its diff rather than overwrite application configuration. Switch serializer declarations, retry name and test exception mode to the supported APIs. Keep application defaults at 7.0 and new wire-format writes disabled. Resolve deprecations; test current and historical data representations.
3. **7.2, then 8.0, then exact 8.1.0 checkpoints.** Lock each resolution, rerun boot/eager-load, model/request tests, isolated real-worker and payload compatibility checks. Do not rely on the defaults pin for transaction exits, TimeWithZone arguments, BigDecimal, or the 8.1 `to_time` change. For the exact target retain the verified JSON < 3 constraint unless a separately approved Rails patch removes that need.
4. **Production-shaped staging before rollout.** Run production boot and Sprockets precompile with dummy/local services, a safe test key and no real mail/provider credentials. Validate Trix assets/direct uploads in a browser, imports, filters/pagination, exports including cached expiry/conditional headers, citation retries and scheduled/digest execution. Restore representative old data and test rollback reads. No production deployment configuration or actual historical data was available for this assessment.
5. **Roll out with compatibility settings.** Use the queue/signature choreography above. Watch deserialization errors, partial imports, receipt DOI omissions, pending enrichments, reminder schedule failures, digest day/duplicates, readonly exceptions and export/cache errors. Do not call success based only on HTTP health or a green unit suite.
6. **Adopt defaults separately.** Enable each relevant 7.1/7.2/8.0/8.1 default with its own check; defer format-changing defaults until old readers/rollback are retired or explicitly compatible. Finally set `load_defaults 8.1` only after reviewing the cumulative defaults. Update the existing architecture/testing documentation at implementation time, not now.

## 6. Remaining questions / limits

- What production PostgreSQL/Redis versions, queue topology, persistence, cache sharing and Disk storage mounts actually exist? The repository has no verified deployment; production mail delivery/link host is also not configured here.
- Are there historical YAML-tag writes, custom YAML objects in preferences, long-lived attachment SGIDs, or new-format jobs from a previous attempted upgrade? None were inspected outside disposable data.
- Should the DST postponement preview retain its documented fixed-offset presentation or deliberately show the reader's new local offset? Either can preserve the same 24-hour elapsed interval; this needs an explicit behavior choice during implementation.
- Do external clients/bookmarks use semicolon-separated query parameters or unusual leading-bracket keys? The app's own forms do not, but Rails 8.1 removes those parser compatibilities; inspect real request examples if such clients exist.
